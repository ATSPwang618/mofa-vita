# 性能实测与优化史

所有数字来自实机（PS Vita，请求 444/222/222 MHz）的 `performance.log`，每次 100–300 秒、
1000–6000 帧。对比基线是首版全量 DXT 包（平均 4.8 FPS、对白 13 FPS）。

## 现状

| 场景 | 帧时间 | 帧率 |
|---|---:|---:|
| 对白/静止 | 22–46 ms | **22–45 FPS** |
| 一般场景 | 40–60 ms | 17–25 FPS |
| 重场景（逐帧动画，约 5% 时间） | 约 190 ms | **5 FPS** |
| 全程平均 | — | **19–21 FPS** |

## 重场景 190 ms 的实测构成

| 项 | 每帧 |
|---|---:|
| 渲染 pass 数 | 39 |
| 每 pass 开头的 `sceGxmFinish` | 约 2 ms × 39 ≈ **78 ms** |
| 绘制提交（`draw_cpu` + `draw_gxm`） | **0.2 ms** |
| 清屏 | 0.1 ms |
| GPU 实际工作（`finish` 等待之和） | 12 ms |
| 呈现（present） | 约 25 ms |

结论：**瓶颈不是绘制提交的效率，而是「每切换一次渲染目标就要一次驱动同步」的结构成本。**
这也解释了为什么降低材质分辨率没有帮助：GPU 填充只占 12 ms。

## 有效的优化

| 措施 | 实测效果 |
|---|---|
| uniform 句柄缓存 | 提交时间 133.8 → 41.6 ms |
| 每 pass 只做一次同步（去掉重复 finish） | 明显 |
| 画布 960×540 → 720×405 | 对白 12.2 → 19.5 FPS |
| **舞台复用**：绘制列表哈希相同且无转场/幽灵/噪声时跳过重画 | 对白 13 → **28–45 FPS**；全程 +60% |
| 后台读盘 + 24 MiB 环形缓冲 | 纹理准备 670 → 6 ms/条 |
| 三显示缓冲 | present 25 → 15 ms |
| 几乎零 uniform（haze/LUT 尺寸走插值器与常量） | 每次绘制省 3–5 次驱动调用（约 4 ms/帧） |
| 透明四边形剔除、同状态合批 | 少量 |
| 换行字符表对齐上游 `kinsoku::WITCH` | 断行与 Switch 一致 |

其中**舞台复用**是收益最大的一项，且不改变任何渲染语义：只有当绘制列表（纹理指针、位置、
颜色、合成透明度）与上一帧完全一致、且 `stage_dirty` 为假、无 ghost/转场/噪声层时才跳过。
实测 60% 的帧满足条件（对白场景 75–95%）。

## 无效或有害的尝试

| 方案 | 结果 |
|---|---|
| 去掉每 pass 的 `sceGxmFinish`（全去） | 部分场景黑屏 |
| 只按 RAW 依赖决定是否 finish | 黑屏 |
| 再加 WAR 依赖 | 仍黑屏（存在未建模依赖） |
| 图层组展平（丢弃遮罩） | 发光特效露出精灵矩形边框 |
| 逐层乘遮罩（`fs_sprite_mask`） | 与整组合成不等价，背景整片消失 |
| 中性组直画（纯白全屏遮罩） | 全作 0 命中 |
| 图集化 | 94% 绘制来自 >512×512 纹理，无法共享图集页 |
| 分段缓存静态图层 | 变化图层仅 40% 连续，收益 <10% |
| 降低材质分辨率 | 瓶颈是 pass 同步，不是填充率 |

## 测量方法

日志每 5 秒一行 JSON，关键字段：

- `exec_us` / `present_submit_us`：CPU 命令执行与呈现提交
- `gpu_finish_us` / `gpu_finish_calls`：等待 GPU 的时间与次数
- `gpu_end_scene_calls`：pass 数
- `gxm_draws` / `quads`：绘制次数与四边形数（`quads/draw` 判断合批空间）
- `begin_target_us` / `clear_us` / `draw_cpu_us` / `draw_gxm_us`：pass 内分段
- `stage_repeats`：舞台复用命中（总帧:重复帧）
- `pass_need`：按依赖模型需要 finish 的 pass 数（仅统计）
- `quads_small/mid/large`：按纹理面积分桶（判断图集化空间）

诊断方法：先看 `gpu_end_scene_calls` 与 `gpu_finish_us` 是否同比例增长——是则瓶颈在 pass 同步；
再看 `draw_cpu/gxm` 是否可忽略——通常可以，不要凭「帧时间 - GPU 时间」估算 CPU 绘制成本。
