# 已知限制与未验证项

适用范围：`perf/render` 基线 `d734b38` 加本地修复，2026-11-04 整理。当前交付版本为 `540p-d734b38-uifix-20261104`。这里区分当前实现、历史设备记录和本次尚未验证的内容。

本次书库/图录改用 raw KATL 单成员读取，675 张实文件、零 NX 解压和分配上界已验证；Vita ARM/VPK 与 114 项渲染回归通过。尚未部署实机，不能由宿主内存测试推断设备峰值或菜单切换耗时，也不能承诺损坏存储和其他失败永不发生。需要配套更新三份资源文件，见 [17](17-书库与图录加载修复.md)。

## 1. 当前画质包的验证边界

当前运行资源已离线缩小 20,181 个潜在 RGBA 大图条目，单张原生分配不超过 1 MiB；逐条解码与独立 DXT 验证通过。PNG 工程仍保留较高分辨率输入；旧高清化的尺寸/数量属于历史输入。最新用户实机日志确认 prebudget 已运行，并暴露出额外的 old frame 分配失败；用户后续日志已确认 targetfix 在设备运行；本次 uifix 尚未推送设备。不能把单图限额表述成所有图层工作集或驱动都绝无失败，见 [14](14-演出材质离线显存限额.md)。

- scene、组 pixel/mask 和 composite 固定 960×540，最终在 960×544 屏幕居中输出；代码只有 native540 一条正式构建档。
- 21,237 个剧情图片条目已从原图重做。全量阶段新增的 21,185 张，经实际游戏归档读取器和 GXT 解码器逐图验证；另有最初 52 张的独立比较记录。
- 241 项 host 测试、ARM 构建、VPK 身份检查属于构建与离线证据。摘要见 [13-native540-art-quality.json](evidence/13-native540-art-quality.json)。
- **当前画质包尚未完成实机画面、帧时间和显存峰值回归。** 增加部分源纹理采样像素会提高单图占用，保持缓存上限不能直接证明帧率不变。

启动视频更新继承全图库的图片验证；视频与当时程序的构建身份见 [启动视频更新记录](evidence/14-logo-media-update.json)，当前程序见 [读档与转场目标恢复记录](evidence/20-save-load-target-recovery.json)。新 MP4 已完整 PC 解码，实机播放仍需确认。

先前 Scene 3 / PC 1148 加载 `YAM_A_00_01_01` 时出现原生分配失败。最新 core 又确认 PC 2368 的 `YAM_A_00_01_06_02_02` 在帧准备准入阶段需 4,171,776 B、只有 4,128,768 B，从错误升级为 panic/abort。当前已修正可复现的纹理页碎片和空页计费，增加可选表面回收及未提交帧回退，通过 106 项渲染 host、5 个纹理池用例/89 项检查、95 个压缩上传用例、27 个复制/目标生命周期用例及 ARM 构建。实机是否通过对应进度、菜单恢复及连续快进仍待复测；core 不含完整页内对象，无法唯一重建现场全部碎片。见 [11](11-高清纹理显存与崩溃修复.md)。

2026-11-03 的读档 core 确认 `old frame` 创建失败后直接 panic（CDRAM `0x80024309`）。本次已接入备用目标复用、实际分配失败后的可选缓存回收、有限重试和未提交帧恢复；菜单可选效果及缩略图也处理分配失败。114 项渲染 host 与 64 轮捕获释放检查、ARM/VPK 和全资源 SHA 验证通过；仍待原进度的设备复测，详见 [15](15-读档与转场目标分配恢复.md)。

本次 BGM 队列由 200 ms 增至一秒，单路 PCM 池增加 300 KiB MAIN，语音仍为 200 ms。29 项音频测试及 ARM/VPK 验证通过，覆盖 reader 被阻塞时的有限供给、样本顺序和混音控制响应；尚待第二章同进度实机复测。扩大队列只能覆盖已填充缓存以内的供给停顿，不能证明底层 I/O/调度问题消失，见 [16](16-BGM预读缓冲调整.md)。

## 2. 历史实测应按版本理解

r2/r3/r4 真机捕获使用 480×270 scene + 720×404 composite；其 FPS、EndScene 和 pass 数只能作为当时的结构证据。当前 960×540 的性能不能由这些数字外推。

[渲染文档](02-渲染与GPU后端.md) 也记录了 2026-11-01 的后续 540p 优化及设备复核，包括流文件探测、音效准备、视频启动和文字缓存。它们发生在本轮全图库素材更新之前，不能代替新包的同场景 A/B。

历史 PS fetch 编译失败同样不能直接描述当前每台设备：实际是否启用需核对该次启动的编译、反射、patch、capability 与 shader 缓存身份，并进行像素比较。不能仅凭开关包含 `ps-fetch` 就宣称路径已接纳。

## 3. 内存与画面边界

- `ATTRIBUTE2=12` 与 256 MiB newlib heap 分别记录在 SFO 和构建收据中；它们不等于所有内存都能给纹理使用。
- 场景与离屏目标保持 960×540，显示为 960×544。当前剧情彩色图在保留逻辑尺寸和完整内容的前提下，单张按 RGBA 行距/页计费不超过 1 MiB。原 GXT 单边 2048、1,036,800 总像素是解码器的硬上限，不能用它替代当前更严格的素材预算。
- GPU 源纹理、调色、文字、组缓存、视频帧等各受原预算约束。需要观察真实 native 分配与 pin/退休状态，不能把不同缓存 gauge 简单相加。
- GXM 硬件存在 P4/P8 RGBA 调色板纹理，但当前资源加载与后端尚未接入。PNG 改为索引色后仍解码 RGBA，不能自动减少 GPU 占用。离线排查与颜色精确保留边界见 [12](12-透明调色板纹理排查.md)。
- 全剧情、透明边缘、调色、软遮罩、语言条带、读档/快进和长时间连续播放仍需设备覆盖；局部截图或 host 解码通过不能代表全部演出正确。

## 4. 设备与素材前提

- 需要能运行自制应用的 PS Vita，以及 GXM、Display、Audio、Jpeg、AvPlayer 等系统服务。Cg 扩展代码通过 taiHEN 查询并核对模块；不同固件/插件组合仍需设备验证。
- TITLE ID 为 `KNIF00540`，固定中文 ID2。素材、存档、shader 缓存分别位于 `ux0:data/WitchontheHolyNight/` 下的 `assets/`、`saves/`、`shader-cache/`。
- 仅接受 [08-素材与安装](08-素材与安装.md) 所列清单对应的 codec9 包。原始 Switch 数据、旧 codec8/270p 包不能直接混入；素材更改后必须同步内嵌元数据并重编 EBOOT。
- 同 TITLE ID 的升级沿用同一外部存档路径；不要把 `saves/` 当作可再生成的构建缓存。

## 5. 构建与工具限制

- 需要本机 VitaSDK 核心、固定 Rust `nightly-2026-05-28`、CMake、Ninja、Bash、Git 和 Python。Windows 通过 WSL 构建。
- 随仓库提供的 7 个静态库记录了对应 SDK provenance；跨 SDK core 的 ABI/链接兼容性应实际构建验证。
- 离线构建需要已经安装工具链和 Cargo 依赖。源码构建不需要外部游戏素材；运行和素材元数据更新需要匹配数据。
- `read-vita-performance.py` / `test-vita-performance.py` 仍依赖不入库的本地 `vita_audit_log.py` / `render-audit/`。干净检出时这些分析工具不能开箱即用，见 [06](06-性能采集与分析.md)。
- 模拟器集成工具需要另外准备 Vita3K、固件与控制接口；不能用 PC/模拟器耗时作为 Vita 实机速度。
- 已移除依赖过期文档的 Windows ZIP 打包、交付、旧清理和旧素材校验入口。现有工具按 [tools/README.md](../tools/README.md) 分类使用。

## 6. 日志与版本

构建脚本的 release 默认 `KNIFE_VITA_QUIET=1`。当前本地画质包显式使用 `QUIET=0`、`KNIFE_PERF_CONSOLE=1`，因此可经 VitaDeck/CatLog 接收控制台性能窗口，版本身份为 `540p-d734b38-uifix-20261104`。不会自动在素材目录创建 `performance.log`。

比较日志前先核对版本、素材 SHA、渲染尺寸、优化 mask、时钟和采集开关；worker scope 与主线程可重叠，嵌套计时不能直接相加。
