# 全图库透明度与 P4/P8 调色板排查

日期：2026-11-02。扫描时本地引擎为 `540p-d734b38-poolfix-20261102`，当时素材未重编码。以下结论来自当时运行包和唯一可编辑图片工程的只读扫描；机器可读摘要见 [17](evidence/17-texture-alpha-palette-audit.json)。后续 prebudget 部署已离线缩小潜在大图，当前运行包的尺寸和占用以 [14](14-演出材质离线显存限额.md) 为准；PNG 输入工程的像素未变。

## 扫描范围与精确保留规则

扫描可编辑工程中的全部 **29,842 张图片**，逐文件核对工程清单 SHA-256，再读取实际像素。包含 29,724 张 PNG 与 118 张 JPEG；24 个原始 `.mzp` 条目及 `.dat/.bin` 属于非图片导出，不把它们当 PNG 解码。对应检查 6 组运行时 `.hed/.mrg` 中的纹理格式、物理尺寸和归档别名，另直接解码了未出现在图片工程里的 7 张 4×4 全透明占位纹理。

P8 精确候选要求整张图片最多 **256 种不同 RGBA 四元组**，P4 要求最多 16 种。颜色计数包含 alpha：同一 RGB 的多个透明度分别占项。这里的“精确”相对于当前工程像素；其中部分 PNG 已由 DXT 解码得到，并不表示恢复了原始 Switch 纹理的所有颜色。

另行统计把 alpha=0 像素的不可见 RGB 统一为零的情况。这通常不改变常规混合后的可见图像，但不是逐像素完全一致，不能混入精确候选；原始 RGB、raw 访问或其他特殊采样语义仍需检查。

| 图片类型 | 图片数 | 可精确 P8 | 其中可精确 P4 |
|---|---:|---:|---:|
| 完全不透明 | 4,549 | 86 | 29 |
| 含半透明像素 | 25,272 | 785 | 21 |
| 只有全透明/全不透明两种 alpha | 4 | 2 | 2 |
| 整图全透明 | 17 | 17 | 17 |
| 合计 | **29,842** | **890** | **69** |

因此，精确 P8 候选中有 **804 张带透明度**。此外 27 张半透明图片在统一全透明像素下的 RGB 后可放入 P8，单列为视觉候选。其余图片若转成最多 256 个 RGBA 项需要量化，不能承诺保持所有渐变、阴影和透明边缘。

## 当前包不是全部 RGBA 驻留

工程的 PNG 是编辑载体，运行时还有 KIMG/GXT 编码。去除同一归档 locator 的别名后，检查的 29,754 个实际纹理成员为：

| 运行时表示 | 独立成员数 | 当前含义 |
|---|---:|---|
| DXT1 | 4,270 | 不透明原生块纹理，4 bpp |
| DXT5 | 19,925 | 含 alpha 的原生块纹理，8 bpp，包含 7 个占位成员 |
| PNG/JPEG 解码路径 | 5,559 | 通常生成 RGBA8；特定 raw 灰度 PNG 可走已有 R8 |

全库没有发现“实际全不透明却编码为 DXT5”的图片。现有原图重建工具已检查 alpha，不透明图选 DXT1，有透明度选 DXT5，见 `tools/quality540/rebuild_scene_art.py:encode`。

普通原生 DXT 上传直接保存块数据，GPU 采样时解压；它不会先整张展开到 RGBA。需要 CPU 调色、strip 或 raw 像素处理的条目会走展开路径，因此同一资源是否产生 RGBA 峰值还取决于请求语义。本次崩溃立绘 `YAM_A_00_01_06_02_02` 超过 256 种 RGBA，不能直接变成精确 P8；调色输出约 3.98 MiB 的问题见 [11](11-高清纹理显存与崩溃修复.md)。

## 原生透明调色板可行，但需要贯通加载路径

本机实际 VitaSDK `psp2/gxm.h` 声明了 `SCE_GXM_TEXTURE_FORMAT_P4_ABGR`、`P8_ABGR` 及 RGBA/ARGB/BGRA 等变体，也声明了 `sceGxmTextureSetPalette`；调色板地址对齐要求为 64 B。使用含 alpha 的颜色项，透明素材可以保留每项透明度并由 GPU 采样。

当前 `knife-platform-vita/src/gxt.rs` 只接纳 PVRTC4、DXT1、DXT5，`knife-core/src/format/gxt_decode.rs` 的像素 fallback 只实现 DXT1/DXT5。要获得 P4/P8 驻留收益，需要离线索引编码、加载器与格式校验、原生调色板所有权和对齐、纹理/调色板共同退休，以及 CPU grade/strip/raw 的兼容路径。只把 PNG 存成索引色，当前加载器仍会展开；先调色板再转 DXT5，最终仍按 DXT5 占用。

同样 backing、不计 mipmap/补边/页对齐时：

| 格式 | 像素数据 | 调色板 |
|---|---:|---:|
| RGBA8 | 32 bpp | 无 |
| RGB24 | 24 bpp | 无；当前原生图片路径不直接保留 RGB24 |
| P8 + RGBA 调色板 | 8 bpp | 256×4 = 1,024 B |
| P4 + RGBA 调色板 | 4 bpp | 16×4 = 64 B |
| DXT5 | 8 bpp | 无 |
| DXT1 | 4 bpp | 无 |

RGBA8→RGB24 的理论像素减幅是 25%；RGBA8→P8 在适合的图上接近 75%，还要算调色板和 backing。但 **P8 对 DXT5 没有像素码率优势，P4 对 DXT1 也没有**，不能按图片数量直接乘出显存节省。

精确 P8 的 890 张导出图去别名后对应 884 个运行时成员：723 个 DXT5、51 个 DXT1、110 个解码条目。额外 7 个占位成员亦可精确索引，但每个原始 DXT payload 只有 16 B，索引加调色板反而可能更大。110 个解码候选中有 60 个灰度 PNG，需要先排除当前 raw/R8 用法；另外是 49 个 RGBA PNG 和 1 个 JPEG。部分 DXT5 候选能精确 P4，可再作小范围对照。

扫描报告提供了全部候选路径和统一 PoT backing 下的 payload 估算。它没有测量场景同时驻留、内核分配、R8 请求语义、调色副本及渲染目标，不把全图库估算相加当作实际空闲显存增加。类似 MZP 的归档条目只有几十 KB，也只能说明文件层压缩；GPU 侧仍需分别计算索引、调色板、布局和分配粒度。

## 后续实施顺序

1. 优先选择仍走 RGBA 的精确候选：菜单文字、注意图、有限颜色 UI；核对是否本来就在用 R8，再比较 P4/P8 与现格式。
2. 保持原尺寸、坐标、采样和透明度；以当前 RGBA 解码像素逐像素比较调色板往返，超过颜色数限制就保留现格式。
3. 直接上传索引和 RGBA 调色板，按现有 native owner、pin 和退休机制共同管理。需要 CPU 像素访问的请求继续走明确定义的兼容路径。
4. 在设备上比较读取、准备、上传、CDRAM 峰值及透明边缘/线性过滤。先验证少量候选，再决定是否扩大。

本轮只完成排查与崩溃修复，不声称已接入 P4/P8，不修改 PNG 或运行包图片，不降低分辨率，也没有采用全库有损 256 色量化。

复现扫描需 Python 3.9+、Pillow、NumPy 和本机两套匹配素材，命令：

```powershell
python tools/audit-vita-texture-formats.py --assets dist/Witch-on-the-Holy-Night-Chengkong-540p-Vita/assets --project dist/Witch-on-the-Holy-Night-Chengkong-540p-Compact-image-source --output .work/alpha-palette-audit.json --jobs 4
```

脚本输出元数据 JSON 和压缩逐图记录，不生成图片副本。包含透明及全透明素材，图集成员用归档 locator 与成员序号识别，避免重复/乱码名称误合并。
