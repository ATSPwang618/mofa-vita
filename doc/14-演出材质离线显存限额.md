# 演出材质离线显存限额

2026-11-02，按项目所有者要求，提前处理整库中可能在调色、raw 或语言条带请求中展开成 RGBA 的大图。选择依据是素材本身的尺寸和类型，不依赖已出现过的报错、某次实机覆盖或静态调色名单。

本页记录 11-02 离线资源处理。11-03 的 `540p-d734b38-targetfix-20261103` 继续使用相同素材，只修复读档/转场的动态目标分配，见 [15](15-读档与转场目标分配恢复.md)。

当时配套构建标识为 `540p-d734b38-prebudget-20261102`。这次程序只更新素材绑定元数据和构建标识，继承此前 poolfix 的引擎实现。没有新增运行时缩放路径。当前场景/合成画布仍为 960×540、输出为 960×544、60 FPS 上限。

## 选择与处理规则

扫描全部 6 个图片归档，共 33,900 个归档条目；KATL 另逐成员解析。将四个剧情图库 `jallpac`、`jallpachd`、`allpacml`、`allpachdml` 的彩色图全部视为可能需要 RGBA 的输入。静态脚本扫描得到 249 个场景、4,164 个调色图名，只作为参考，不作为缩小范围的白名单。

统一限制每张完整图解码后按原生行距、页对齐计费的 RGBA 分配不超过 **1,048,576 B**。普通图还限制在 960×540 内；语言条带按每栏不超过 960×540 处理，同时限制整张解码 owner 的字节数。保持宽高比例，保留完整画面与原 KIMG `logical` 坐标，不裁掉长图的画外内容。

这个规则是提前降低潜在工作集的保守选择。因此一张当前可能走 DXT 直传的背景，只要在 RGBA 路径中超限，也会被缩小；正常显示时同样使用缩小后的图片。不能把这次描述成“只降低特定效果瞬间的清晰度”。

原 DXT 图使用可编辑 PNG 的匹配像素输入，经 Lanczos 缩小后编码一次 DXT1/DXT5；透明图保留 alpha。原 PNG 的色彩契约保留，少量 JPEG 输入在缩小后保存为 PNG，避免再次 JPEG 编码。4 栏语言图逐栏裁出、分别缩放、按相同顺序组合，防止重采样跨栏混色。

本机可编辑 PNG 中的 DXT 导出图已经包含前次压缩的损失，因此这次缩小并重编码属于额外一代有损处理。它优先落实占用上限，不宣称无损，也不宣称恢复了原始未压缩美术。

灰度/原生控制蒙版、微小控制纹理、UI/字体及开机感谢页保留原数据。蒙版原本可走 R8，UI/字体也不属于此次图库高清化造成的超大立绘源。它们仍受既有解码与分配预算约束，不计入“剧情彩色图单张 1 MiB”承诺。

## 工具与复现

入口见 [limit_runtime_art.py](../tools/quality540/limit_runtime_art.py)、[verify_runtime_art.py](../tools/quality540/verify_runtime_art.py)。依赖 Python、Pillow、numpy、`ispc_texcomp==1.0.1`，源图片与归档由使用者自备。

```powershell
python tools/quality540/limit_runtime_art.py --assets <当前assets> --project <可编辑PNG工程> --output <新扫描目录> --scan-only
python tools/quality540/limit_runtime_art.py --assets <同一assets> --project <同一PNG工程> --plan <扫描目录>/scan.json.gz --output <新暂存目录> --jobs 4
python tools/quality540/verify_runtime_art.py --assets <同一assets> --staged <暂存目录> --plan <扫描目录>/scan.json.gz
```

输入保持只读。暂存目录只包含受影响归档与新清单，不复制全包。逐图清单在 `resample-report.json.gz`，记录原/新尺寸、格式、行距分配、输入 SHA、输出 SHA、解码 CRC、语言栏数和归档索引。安装资料由验证后的暂存文件更新到唯一运行目录，完成后不保留整套旧资源或暂存资源副本。

生成启动 profile 时，`generate_vita_asset_profile_540.py` 会对带 `offline_story_memory_budget` 契约的包调用 [预算检查](../tools/vita_image_metadata.py)，扫描四个剧情归档的元数据。如果后续高清化工具重新引入超限彩色图，生成步骤会报错，要求先离线预处理。这个检查在 PC 端执行，不增加 Vita 每帧工作。

可编辑 PNG 工程继续保留一次较高分辨率输入。它现在是离线重采样的输入工程，不再声称与部署图逐像素同尺寸；重新打包必须再次应用本规则。运行包已经使用缩小后的归档，不会从 PNG 工程读取较大图片。

- 对旧高清素材应用新预算检查时，在首张超限图即拒绝；新包全部检查通过。

上述是 11-02 的离线资源和解码验证；11-03 用户提交的日志与 core 已确认设备实际运行 prebudget，后续发现的 old frame 动态目标分配问题见 [15](15-读档与转场目标分配恢复.md)。每张潜在 RGBA 大图的上限已经在数据中落实，不需要通过逐段实机运行来寻找应缩小的素材。有限显存的同时活跃图层、离屏目标与驱动仍有总量限制，不能从单图限额推导出任何脚本工作集都绝不失败。此前 poolfix 的回收、帧准备准入和完整画面回退继续保留。
