# 书库与图录加载修复

2026-11-04，本地版本 `540p-d734b38-uifix-20261104`。本次修复 Extra 页面的大图集读取与缓存生命周期，继承已有渲染、剧情材质限额和 BGM 一秒预读。源码仍在 `perf/render`，没有提交或推送。机器可读记录见 [22-extra-ui-direct-ranges.json](evidence/22-extra-ui-direct-ranges.json)。

## 日志定位与证据边界

用户提供的 `log.txt` 中，书库在 frame 76445 已完成两份来源准备，随后图录入口在 frame 77320、77910、78489、79079 连续失败。失败页号为 38，`ui_source_failed` 累计从 1 增至 4。图录来源 `CG_PARTS.NXZ` 需 25,037,579 B 解压输出，存储范围为 9,525,248 B；附近窗口还存在较多 CPU 源缓存和 deferred GPU 驻留。

这组证据定位到了进入图录前的整包来源准备。原日志没有保留具体的 malloc / pinned-budget 错误链，因此不能把某一个底层错误码当成已观测事实；也不能把 GPU 缓存字节直接当成 malloc 可用量。本次移除这个大块输出的强制需求，同时补充具体错误日志。

仅从预热列表删掉 `CG_PARTS` 不够：原 `AtlasCache::range()` 内部仍调用 `whole()`。把它直接换成压缩范围读取也不合适，因为 NX 是整条流，每张缩略图仍会从头解压整份图集。

## 资源布局与加载行为

用 `prepare_vita_ui_ranges.py` 在 PC 上去除以下四个图集的**外层 NX**，继续使用已有 `.hed/.nam/.mrg` 和 KATL/KIMG 格式：

| 条目 | 成员数 | 原扇区范围 | 新 raw KATL 扇区范围 |
|---|---:|---:|---:|
| `CG_PARTS.NXZ`，index 49 | 401 | 9,525,248 B | 25,038,848 B |
| `ARCHIVE_PARTS_EN.NXZ`，index 61 | 69 | 3,166,208 B | 15,190,016 B |
| `ARCHIVE_PARTS_ZC.NXZ`，index 62 | 69 | 3,170,304 B | 15,190,016 B |
| `ARCHTHUMB_PARTS.NXZ`，index 65 | 136 | 4,327,424 B | 8,753,152 B |

675 个 KIMG 的名字、顺序、偏移、尺寸、逻辑坐标、编码和 SHA-256 逐项一致；另外 30 个非空 UI 条目的存储字节保持一致，NAM 完全一致。条目仍沿用 `.NXZ` 名字，实际读取以头部和生成索引的 `direct` 标记为准。

`allui.mrg` 从 37,550,080 B 变为 81,532,928 B，增加 **43,982,848 B，约 41.95 MiB**。这是磁盘容量换取直接定位读取；PNG/DXT 本身没有重新编码，也没有降低画质。剧情、音视频、字体和可编辑 PNG 工程没有变化。

程序注册图集时只建立惰性纹理句柄，实际用到成员才读取。`Archive::read_direct_range` 先检查 header、extent 和范围，拒绝仍带 NX 压缩的来源；`ByteStage::load_direct_bounded` 保留有界等待和原始错误。关闭 `shared-atlas` 优化时，标记为 `direct` 的图集仍走此路径，不允许回到整包分配。

纹理继续走既有按需上传和原生缓存。直接 DXT 路径仍上传编码数据，PNG 成员继续使用现有解码路径。本次没有提高显存缓存、改变 GXM 合成或调整帧率。

## 生命周期与日志

进入 Extra 页面的准备状态时：

1. `WTex::release_extra_except` 释放其他 Extra 页面的纹理描述与映射。
2. `Assets::vita_release_extra_ui_sources` 清理其他页的缓存描述和闲置整包来源。
3. `AtlasCache::discard_idle` 只删除无人引用的 owner 与队列中的推测工作；活跃任务、预留预算和活跃 ByteView 不受影响。
4. 可选 render target 通过已有 `vita_release_optional_render_targets` 与 GXM retirement 回收。

新增 `ui_source_event`，包含 `build`、`page`、`status`、`source_cache_bytes`、`resident_deferred_bytes`、`heap_headroom` 与 `detail`。`pending` 表示开始准备，`ready` 表示必需来源准备好，`failed` 保留具体错误链。raw 成员在实际绘制时才读取，`ready` 不代表预先加载了全部图片。错误文本最多保留 768 个字符；普通正常路径不会逐帧打印此事件。

完整桌面游戏测试存在原有 `GROUP_SHAPES` 条件编译问题，本次没有修改其渲染逻辑来绕过；定向 harness 直接引入生产 byte worker、cache、ByteView 和索引，ARM 全游戏编译则使用真实 Vita 条件分支。

## 从既有包再生成

在 WSL / Linux 的项目根目录运行，输出目录须不存在，先暂存再替换：

```bash
python3 tools/prepare_vita_ui_ranges.py --assets <既有assets> --output <暂存assets>
python3 tools/prepare_vita_ui_ranges.py --assets <暂存assets> --check
python3 tools/generate-vita-atlas-index.py <暂存assets> knife/knife/data/vita_atlas_index_540p.rs --base-assets <既有assets>
python3 tools/generate-vita-stream-index.py <暂存assets>/vita-540p-assets.json knife/knife/data/vita_stream_index_540p.txt
python3 tools/generate_vita_asset_profile_540.py --assets <暂存assets> --base-assets <既有assets>
python3 tools/test-vita-extra-ui.py --assets <暂存assets> --output <新的测试目录>
```

生成 profile 会校验 raw UI 契约，防止后续封装工具无意恢复外层 NX。暂存输出只有变化归档、清单和报告，不是完整素材包；程序与三份资源必须配套发布。旧的全包只换 EBOOT 步骤仅适用于此前未更改素材清单的版本。
