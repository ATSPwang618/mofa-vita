# 2026-11-05：重场景 op7 专用着色器

候选构建：`stage-effect-r3-heavy-ps7-20261105`。本轮优先处理 scene38 中约 5～6 FPS 的连续重绘场景；r2 的三项实验保持撤回。画布和合成目标继续使用 960×540，素材、特效顺序、同步及缓存预算沿用现有版本。

## 定位依据与收益边界

上一份实机日志的 frame8077→8108、PC1246 窗口有 31 帧重绘、0 帧复用，6.076 FPS，render 约 162.65 ms/帧。对应 r1 为 6.076 FPS、162.67 ms/帧，不能认定 r2 提速。完整比较见 [20](20-r2实机复核与回退.md)。

该窗口实际提交的 PS 运算为 op1 59 次、op6 31 次、op7 141 次、op13 62 次、op19 62 次。op7（DodgeAlpha）是次数最多、仍走通用 shader17 的运算，平均每帧 4.55 次。本轮直接优化其像素程序；draw 次数不是像素覆盖量或 GPU 独占时间，不能据此推算提速百分比。

## 实现与回退

- 增加运行时 shader29，入口 `fs_ps7_fetch`。继续调用完整的 `ps_source(i)`，保留 haze、soft、rule、group mask、Fill、NoAlpha、预乘处理及其参数，移除通用程序对其余 PS 运算的选择。普通图层和 group composite 的 op7 都可使用；其他运算原路由不变。
- 原式逐句保留：`k=max(1-a*s,0)`、`raw=min(d/k,1)`、目标分量为零时输出零。正 alpha 输出 alpha=1，零/负 alpha 返回原目标四通道；最终仍按每次 draw 做 UCHAR4/UNORM8 存储。没有跨 draw 合并或改写量化顺序。
- shader29 单独检查运行时编译、metadata、注册、Opaque/UCHAR4 patch 与 capability。不可用时沿既有 shader17、再到快照 shader14 回退。full-source 程序允许 `tex2` 和 `soft_lut`，不能误用 plain shader 的无 haze/soft 限制。
- 增加 `ps-op7` 优化开关，位 28，`all` 默认包含；路由仍同时要求 `ps-fetch`。同一个 EBOOT 可用 `all -ps-op7` 单独关闭新路径。原 normal group19 与 blend-chain 资格保持原样。
- 新增 native `draw_ps7` 计数，追加在计数表末尾；启动能力行增加 `ps_fetch7_29`。原 `ps_op7` 继续记录真实执行运算，便于核对 29 是否接管了目标重场景。

没有新增整屏纹理或缓存。新增程序本身需要少量 shader 内存；完整源代码 SHA 改变后，旧缓存会自动失效并重新编译，不必手动删除 `shader-cache/`。

实机优先复测原 PC1246 最慢窗口，确认：

1. 启动版本为 `stage-effect-r3-heavy-ps7-20261105`，VitaDeck 能持续接收带版本日志。
2. `ps_fetch7_29=1`，同段 `draw_ps7` 随 `ps_op7` 增加；否则属于安全回退，不能声称专用路径运行。
3. 比较相同 scene/PC、全重绘窗口的 render/work、batch wait 和 FPS，并检查闪烁、颜色及透明边缘。对白复用比例不同的总体平均 FPS 不作本轮收益结论。
4. 若最重场景仍无实用改善，撤回本轮专用路由，保留定位证据，再评估 group 有效覆盖裁剪。不会把“能力开启”或“host 测试通过”当成提速证明。

构建交付时未连接实机执行新 shader。后续用户提供实机日志，已确认29成功编译和执行，PC1246全重绘窗口约6.076→7.034 FPS、render约162.65→140.27 ms；有小幅收益但仍卡顿，不代表达到20 FPS或全场景改善。对照、日志完整性和边界见 [22](22-op7专用shader实机复核.md)。
