## 末尾故障的证据链

12:57:59及12:58:31均报告：

```text
scene=40 pc=690
frame preparation: Vita frame resource preparation failed before submission:
loading shared atlas view: bounded source allui:7:
allocating bounded NX output:
memory allocation failed because the memory allocator returned an error
```

直接失败点是`knife-core/src/format/nx.rs`的`Vec::try_reserve_exact(unpacked)`。这是CPU输出缓冲分配失败，在纹理解码/上传之前。它不是此次shader编译失败的证据，也不能据此断言显存已满。

本地运行包与内嵌索引确认allui:7是`DISP_PARTS_ZC.NXZ`，50个成员；压缩输入1,198,023字节（1.14MiB），整图集输出17,562,705字节（16.75MiB），最大单成员1,048,672字节（约1MiB）。allui.hed/nam/mrg均匹配当前本地manifest；没有验证设备上文件逐字节身份，但日志是分配错误而非校验或解压错误。

关键时间线：

- 12:55:55窗口成功加载同一图集，atlas_load约968.65ms，NX full约871.198ms。
- 12:56:10窗口首次看到stage_read_failed从0变1；之后一直是1。同一时间段已发生源缓存回收。无法从累计计数精确还原失败瞬间，但与后续唯一的allui:7错误一致。
- 12:57:59菜单准备才暴露上述错误。12:58:00报告heap_headroom约88.30MiB，kernel CDRAM free约40MiB；12:56:10的headroom约94.13MiB。它们是窗口快照，不是分配瞬间，也没有最大连续空闲块统计。
- `AtlasCache::fail`保存错误；`poll`先返回已保存错误；`whole/range`不会主动重试。DISP路径没有调用`retry_failed`。预热同样跳过已有failed条目；普通资源上下文重置也不清空这个记录。
- 末尾菜单状态3/5来回，代码中5确实是存读档子界面处理。输入和UI状态机仍在运行，但菜单帧准备失败后回显旧画布，于是看上去进不去。退回主界面再进入后12:58:31又报同一错误。

**确定存在的逻辑缺陷：临时分配失败被缓存，UI需求路径没有恢复它，且恢复入口本身依赖失败的UI资源。** “建议重新读档”的提示因此没有保证可执行。

碎片化/连续大块申请受限是首要怀疑，尚非日志已证明的唯一原因。`heap_headroom`实际是配置堆上限256MiB减mallinfo.uordblks，并不等于最大连续可分配块。当前32MiB总余量压力阈值不能检测此类失败；初次失败也可能包含未捕获的临时峰值。没有证据证明长期单向泄漏或新增shader使堆总量耗尽。

## 建议优先修复

1. **将大UI图集外层NX改为可按成员读取的raw KATL。** 项目已为CG_PARTS/ARCHIVE_PARTS/ARCHTHUMB_PARTS实现这一模式，但DISP还没纳入。推广到DISP等大UI图集，保留每张KIMG/PNG/DXT的全部字节、尺寸与alpha。中文DISP单项存储增长15.6074MiB，可免除每次必须整块申请16.75MiB输出的依赖。仍需计算成员读取、转移和解码峰值，不能声称总峰值严格只有1MiB。更新archive、manifest和内嵌索引必须同批交付。
2. **错误分型和有界恢复。** 保留TryReserveError类别，分开处理暂时OOM/IO与数据损坏。真实UI需求可触发一次协调后的冷缓存回收和重试，不能每帧无限重试、清掉活跃任务或伪造Ready。整包失败不能把可读的小成员永久封死。
3. **可用的应急菜单。** 资源错误时读档/返回入口独立于完整剧情Stage及失败图集；只允许保存最后已提交且有效的存档点，不能将半完成资源状态写成存档。预留很小的文字/按钮恢复资源，避免要求用户去打不开的菜单读档。
4. **故障时观测。** 记录请求的stored/output字节、分配类别、源缓存和调色缓存、重试代次、回收前后统计；不要把配置headroom当作连续分配成功保证。

当前应先保住存读档恢复通道，再进行上面的重场景GPU优化。本轮保留r10程序和资源原样，分析证据见[37-r10-long-hardware.json](evidence/37-r10-long-hardware.json)。
