# 实包素材与内存复制分析

后续诊断真机日志已完成归因及优先级重排，见[真机日志耗时归因与优化计划](12-真机日志耗时归因与优化计划.md)。本篇保留最初静态分析的基线与证据口径。

结论：**存在多余的 CPU 内存复制、重复读取/解压和 GPU 整面复制，而且其中一些会把预读的工作重新搬回渲染主线程。** 当前证据不能把低 FPS 全部归因于 CPU→GPU 上传：已经驻留的纹理不会每帧重新上传；PS 背景快照、组 scratch 和最终合成的复制主要发生在 GPU 内部。必须同时减少资源路径的浪费和渲染路径的同步。

本篇接续 [Artemis 渲染与 MJA 对照分析](09-Artemis渲染与MJA对照分析.md)，只读分析用户提供的实际素材。没有修改引擎、重新打包素材或声称获得真机加速。

- 工具：[scan-assets.py](../../tools/render-audit/scan-assets.py)，Python 标准库，无需图像解码器；完整逐图索引保存在忽略目录 `.work/render-audit/asset-textures.csv`。

## 复制边界先分清

| 路径 | 实际工作 | 是否持续发生 |
| --- | --- | --- |
| PNG/JPEG → C 输出 → Rust Vec | 完整 RGBA CPU 缓冲复制 | 新加载、重载；驻留命中没有 |
| Rust 像素/压缩块 → 映射 CDRAM | CPU `memcpy` 写入最终 GPU 可见存储 | 上传/更新时；不是每个 draw 都上传图片 |
| PS backdrop、组 scratch、stage → scene | GPU 采样绘制；某些未渲染线性源走 transfer | 相应命令每帧执行，可持续成为瓶颈 |
| canvas → 显示缓冲 | GPU 绘制并转换输出颜色 | 每次 present |
| `read_target` / readback | 等待后由 CPU 读取像素 | 截图或显式 DEV readback；普通 present 未发现整屏读回再上传 |
| effect 顶点 → MAIN 映射 arena | 每个提交一次顶点 `memcpy` | 每帧，但量远小于整屏纹理 |

`block_alloc` 把同一个内存块映射给 GXM；C 的纹理 descriptor 直接指向 `t->pixels.base`。因此最后一次 `memcpy` 已经是 CPU 写最终 GPU 存储，后面没有另一层隐藏的 GL 上传。也不能把 `sceGxmFinish` 算成一次像素复制。

## 最严重的资源问题：UI 每个子图都重新解压整份 atlas

调用链是 [assets.rs](../../knife/knife/src/assets.rs) 的 `ui_textures`（约 1162 行）→ `ByteStage::request`（约 174 行）→ [archive.rs](../../knife/knife-core/src/format/archive.rs) 的 `read_uncompressed_range`（约 319 行）：

```text
主线程：read(i) 读取并解压整个 KATL
        parse_atlas 返回其中各 KIMG 的借用切片
        对每张子图 request(i, offset, len)
后台：  为每个 key 新建线程
        重读整个 NXCX → 从头到尾解压 → 只保留所需 KIMG
```

这个 range 接口节省了“同时保留完整解压 atlas”的空间，但**没有节省 NX 的完整读取和解压**：它用 8 KiB scratch 处理全部流，只在目标区间复制输出，最后还要验证完整流。当前不分当前页面是否会采样，登记 atlas 时就给所有子图发起请求。

下面是“每个子图请求均成功执行一次”的源码工作量模型，**不是已经在 Vita 上测到的 I/O 或同一时刻占用量**。线程启动失败、提前消费及其他时序会改变实际结果；首次读取、需求端重复请求还未计入表中。

| 实包 atlas | 子图数 | 单次磁盘条目 / 解压输出 | 逐子图预读合计磁盘请求 | 逐子图解压输出合计 |
| --- | ---: | ---: | ---: | ---: |
| `TITLE_PARTS_ZC` | 14 | 0.720 / 6.259 MiB | 10.077 MiB | 87.631 MiB |
| `DISP_PARTS_ZC` | 50 | 0.748 / 19.592 MiB | 37.410 MiB | 979.588 MiB |
| `CG_PARTS` | 401 | 6.024 / 25.106 MiB | 2,415.648 MiB | 10,067.549 MiB |
| `ARCHTHUMB_PARTS` | 136 | 2.800 / 8.514 MiB | 380.835 MiB | 1,157.896 MiB |

例如 `CG_PARTS`：`401 × 26,325,662 = 10,556,590,462 B` 解压输出处理量，约 **9.83 GiB**；源归档条目本来只需读取约 6 MiB、解压约 25 MiB 一次。这是从实包尺寸和明确调用链得到的放大，不是泛泛猜测“有很多 memcpy”。

其余放大因素：

- `ByteStage` 的 24 MiB 只限制已完成的 entries。没有线程数、队列数、在途字节或 generation 上限。`Storage::read_range` 在取得文件锁**之前**分配并清零整个读取 Vec，排队线程也可能已经持有大缓冲；不能用 24 MiB 宣称整条预读链内存有界。
- 同一 archive 的 seek/read 受文件 Mutex 串行保护；增加数百个线程不会并行读同一个文件，反而增加分配、调度、解压竞争。
- 需求端 `stage.take` 未完成就直接再读，没有等待/合并同一个在途任务；后台任务仍会继续。首次命中会消费 entry，以后 GPU 再被淘汰时不保证有新的 staged 数据。
- `CG_PARTS` 的全部 KIMG 约 25.10 MiB，已经略超 24 MiB staging cap；若没有同步消费，不能全部留在 staging。这里也没有必要为了将来可能用到的 401 张图先启动 401 个独立任务。

最直接的修正是使用已解压的 atlas：一个有预算的共享 owner 加子范围，或者按需求把当前页/当前窗口的 KIMG 移交给固定 worker。压缩 atlas 只解压一次，后续缓存未命中才有界重读。共享 owner 必须按实际整块大小计费；不能多个范围漏算或重复计费。

不能因此直接去掉所有外层 zlib：例如 `DISP_PARTS_ZC` 从 19.592 MiB 缩到 0.748 MiB，原样改为 raw 会让整条目读盘量约增大 26 倍。应先修正重复读取/解压和需求粒度，再以真机卡速、解压时间比较 raw、单图压缩或有索引的分块布局；不能只看到 DXT 已压缩就假定外层 NX 没有价值。

## GXT 预读成功后，首次实际使用仍然回主线程读第二遍

普通 CG 的实包 codec 8 路径：

```text
image worker / demand:
  Archive::read → NXCX 解压 → Pixels::GxtAlter { encoded: Vec }
finish_image / upload_pixels:
  defer_gxt_altered_reload(&encoded) 只解析并登记描述符
  encoded 被释放，未上传，也未留给首次 prepare
render / prepare_deferred:
  DeferredBytes::Reload → archive.read_uncompressed_range(...)
  再读 NXCX、再解压 → create_gxt_texture → memcpy 压缩块到 CDRAM
```

证据是 `assets.rs` 约 964、1059 行，`vita.rs` 约 1269、2263 行。该 CG GXT 分支的 loader 直接读 archive，**没有走 ByteStage**。所以图像 worker 提前读完不代表首帧上传已准备好；它做过的 I/O/解压可能没有消除任何主线程 I/O。这不是 GPU 上传了两次，而是首次上传前读、解压了两次。

UI 的 GXT 分支还有两个 CPU 拷贝点：

1. `ui_textures` 先无条件执行 `Arc::<[u8]>::from(image)`，但 codec 8 分支没有使用这个 retained owner。源码层面是一次构造后释放；优化构建是否完全消除此分支工作应以最终汇编/计数为准。
2. ByteStage 完成时 `Vec<u8> → Arc<[u8]>`，取出时 `bytes.to_vec()` 再复制回 Vec，最后 C 才复制 payload 到 CDRAM。`Arc::clone` 只加引用；这里的 `Arc::from(Vec)` 则重新分配并移动字节，可由 [Rust 标准库实现](https://doc.rust-lang.org/src/alloc/sync.rs.html#4072-4098) 的 `allocate_for_slice_in` / `copy_nonoverlapping` 复查。两者不能混为一谈。

可把 deferred 输入改为统一的“有界 owner + range”，让 `with_bytes` 借用已经存在的内容；上传完成前 pin owner，完成后决定保留或释放。无需为了借用切片再复制成另一种容器。GXT 的解析器本身返回借用 payload，没有整张转码/解压 RGBA，这部分设计应保留。

非 GXT CG 的 `adopt_image_reload` 已复用首次上传，这是正确的；但它登记时仍启动一次备用 ByteStage 读取，即便纹理一直驻留、从未需要重载。预读触发点应由真实驻留缺失及近期需求决定。

## PNG/JPEG 确有额外完整像素缓冲复制

[assets.rs](../../knife/knife/src/assets.rs) 的 `decode_native_image` 约 1649 行明确执行 `image.pixels().to_vec()`；不是 Vec 所有权移动。随后 [effects_backend.inc](../../knife/vita/effects_backend.inc) 的 `kv_gxm_texture_create_ex` 约 198 行清零 CDRAM、逐行复制。

软件 PNG/JPEG：

```text
解码 → C malloc RGBA
     → 完整复制到 Rust Vec，释放 C owner
     → 完整复制到最终 CDRAM source
     → 若需默认 Alter，再由 GPU 烘焙到另一张 CDRAM target
```

硬件 JPEG 成功时，[jpeg_hw.c](../../knife/vita/jpeg_hw.c) 约 122–183 行还会：

```text
JPEG 编码流 → 临时 CDRAM stream
硬解 YUV → 临时 CDRAM work → CSC 的临时 CDRAM RGBA
        → 逐行复制到 C malloc RGBA
        → 复制到 Rust Vec
        → 复制到最终 GXM CDRAM source
```

所以硬解成功后仍有 **三次完整 RGBA 复制**，以及一次编码流复制；598 个 JPEG 槽位并不意味着每个都满足硬解 profile 或每次硬解都会成功，fallback 必须分开统计。

以一张未裁语言条、960×540 RGBA8 为例：P = 2,073,600 B，当前线性 CDRAM 分配 A = 2,097,152 B。

| 源码操作 | 软件解码 + GPU Alter | 硬件 JPEG + GPU Alter |
| --- | ---: | ---: |
| 完整 RGBA memcpy 目的字节合计 | 2P = 3.955 MiB | 3P = 5.933 MiB |
| 显式像素清零 | C 输出 P + source A + target A ≈ 5.978 MiB | source A + target A = 4 MiB |
| 解码/CSC 自身的输出写入、PNG 过滤、grade、GPU clear/bake | 另计 | 另计 |

表里的 memcpy 数值按“复制的数据大小”计；读源和写目标都消耗带宽，不能把该数值直接当实测总线流量。CPU grade 变体可能省掉 Alter，但增加 CPU 像素处理；语言 strip 可能先解码 960×1080，再 `copy_within` 选择半段，因此不能对所有图片机械套同一公式。

优先消除 C owner → Rust Vec 这一层，可用带 C 析构器的独占像素 owner 跨 worker 移交，或者明确的 decode-into 接口。现有 `DecodedImage` 刻意是 `!Send`，需要重新审计所有权；不能直接把任意 C malloc 指针伪装成 Rust Vec。

继续减少硬解复制时，可让 CSC 写入符合硬件与 GXM pitch 契约的最终存储，或从临时 CSC 输出**一次**拷贝到最终纹理。宽度、pitch、GPU 正在采样的生命周期及错误回收决定是否可直接写；不是给现有接口换一个指针就完成。PNG 直接解码进 GPU 可见内存是否更快也需比较 CPU 缓存/行访问成本，先删除中间 owner 拷贝通常更稳妥。

## 每次分配都清零，加上 256 KiB 粒度会放大换帧成本

`kv_gxm_texture_create_compressed` 对每张纹理：单独分配 CDRAM memblock → 映射 → `memset(整个对齐块)` → `memcpy(完整 GXT 压缩 payload)`。写过的 payload 区马上又被覆盖。

实包例子：

| 资源 | 有效上传数据 | 当前 CDRAM 占用/清零 | 意义 |
| --- | ---: | ---: | --- |
| `CG_PARTS` 401 张 DXT1 缩略图 | 合计 25.0625 MiB | 100.25 MiB | 每张 64 KiB payload 占 256 KiB，4 倍放大 |
| `MOUSE_PARTS_ZC` 两张 GXT | 合计 4,112 B | 524,288 B | 清零量约为 payload 的 127.5 倍 |
| `KOJ_L_01_01_*` 名称族 30 张 | 当前格式上传合计 791,040 B | 7,864,320 B | 20 PNG + 10 GXT，约 9.94 倍放大 |
| `SOU_N_01_08_*` 名称族 35 张 | 当前格式上传合计 2,615,808 B | 9,175,040 B | 32 PNG + 3 GXT |

名称族仅按 NAM 后缀汇总，不证明它们构成一次 motion 的完整序列或会同时驻留。PNG 的数字按未裁剪 RGBA source 计，未加临时 Alter target。

deferred GPU 预算为 32 MiB。按当前独立块分配，单是 401 张缩略图全部常驻就需要 100.25 MiB；只考虑该预算，最多容纳 128 张 256 KiB 的纹理。若有正确对齐的池内子分配，它们的 payload 合计约 25 MiB，有机会放进同一预算。这是**分配布局导致的额外淘汰/重读/上传压力**，而不是用户看到的全部纹理都必须每帧上传。真正是否抖动仍由当前页面和场景工作集决定。

可按规格复用块，进一步在较大 CDRAM block 中对纹理子分配，按采样地址/格式所需对齐保留 offset。纹理销毁变为释放子区间，共享 block 最后才 unmap/free；回收仍要经过 GPU completion。不能把 256 KiB memblock 粒度直接当成每张纹理的地址对齐要求，也不能绕过 GPU 仍在读的旧槽。

池化还要同步修改 `allocation_bytes` 和 admission 的记账方式，按实际池占用/可复用区间计费；只改 C 分配、不改 Rust 每张纹理向上取整的预算，32 MiB 逻辑限制仍会在原位置挡住容量。

压缩纹理可避免清零马上会被完整 payload 覆盖的部分，只初始化需要的 padding。线性 render target、持久组表面可能依赖初始零值；PNG interlace 合成也可能读旧行，不能全局删除所有 memset。池化首先解决浪费和分配/映射抖动，不保证一次 memcpy 也不需要。

## 实包灰度 rule 又被展开成 RGBA

29 个 codec 7 都是 960×540、PNG color type 0 的灰度图（14 个 RULE 在两个归档的槽位，加 parts 的一张）。`decode_image_limit` → native PNG 路径调用 `png_set_gray_to_rgb`，再填 alpha，最终得到 4B/像素；`Pixels::Rgba` 也按 4B 上传。现有“raw R8 不展开”的分支针对 BNTX R8，不会自动覆盖这些 KIMG PNG。

一张这类 rule 的 payload/拷贝由可行的 R8 518,400 B 变成 RGBA 2,073,600 B；CDRAM 从约 512 KiB 变成 2 MiB。`effects.cg::rule_at` 只读 `.r`，后端也已有线性 `U8_RRRR` 支持，因此保持单通道有明确切入点。仍应核对 raw/gamma、采样及 rule 反相/翻转语义；此结论不适用于需要彩色或 alpha 的普通 atlas。

## 稳定低 FPS 更要看 GPU 整面复制和同步

`prepare_deferred` 约 2239 行用 `texture.id.is_none()` 筛选缺失项；驻留命中只更新时间并 pin，不读取图片，不解码，也不重新上传。因此“缓存命中、画面仍每帧很慢”应优先检查以下持续路径：

1. 每个 PS quad 都结束 pass，整面复制 target → backdrop，再开 pass。即使只画小区域，当前复制也不是小区域。
2. 组路径仍是 pixel → scratch 复制、MaskAlpha 写 scratch、scratch 合成，尚未切到已有的融合 shader。
3. `Game::render` 每帧 stage → scene 复制；之后 scene → canvas、canvas → display 仍是 GPU pass。
4. `kv_gxm_copy_texture` 对 rendered/target 来源先 Finish/TransferFinish，再用 GPU quad 复制；未渲染的线性来源走 TransferCopy。它没有在这些常规路径把屏幕像素读回 CPU 再上传。
5. 每个 target 开始、present 以及销毁/更新等同步点会打断 CPU/GPU 重叠；具体完成协议见前篇，不能直接删除 Finish，因为当前 pass 之间会复用同一顶点区。

一次完整 RGBA 源读取 + 目标写入的逻辑数据量模型：480×270 为 1,036,800 B，960×540 为 4,147,200 B。实际 DRAM 事务受 tile、cache、blend、gamma 和 store/load 影响，这不是物理总线流量的实测值。默认运行时 scene divisor=2；素材为 540p 不等于每个 RT 都是 960×540。默认 composite 按公式实际为 720×404（代码把尺寸截到偶数，注释写 720×405）；native 模式另算。

顶点也有 CPU→GPU 可见内存复制：普通无裁剪 quad 当前是 6 × 112 = 672 B，命令合批还可能 `extend_from_slice` 复制一次，然后 C 上传一次。100 个这样的 quad 最后上传约 65.6 KiB，通常与反复复制数 MiB 的表面不是同一量级。可优化顶点结构和 arena，但应先用计数确定成本占比。

## 现有性能日志漏掉了这里的重要成本

- `Archive::read` / `read_bounded` 记录 `record_inflate`；**`read_uncompressed_range` 的完整 NX 解压没有记录该指标**。UI 逐子图解压和 GXT 主线程重载的 inflate 时间/调用数因此可能没有进入 `nx_inflate_us/calls`。
- card read 计时在取得文件锁之后，之前的大 Vec 分配/清零和锁等待不计入 `card_read_us`；worker 汇总时间也不能直接与单帧主线程时间相加。
- `ImagePerf.uploads/upload_us/gxt_images` 包含 GXT“登记完成”，不代表那一刻已发生真正的 CDRAM 上传。后者发生在 deferred prepare。
- `deferred_upload_us` 包住 GXT native 创建，但之前的读取、解压、Vec/Arc 转换在 item 范围内。单看 upload 数值会漏掉主线程准备成本。
- `draw_cpu_us` 从顶点 memcpy **之后**开始；uniform/纹理绑定、验证和顶点复制被排除。`kv_gxm_copy_texture`、seal、texture update/destroy 等裸 Finish/TransferFinish 也没有全部进入当前 `finish_us/calls`。

所以不能用“日志里的 memcpy/解压/绘制都很少”排除它们，更不能把 Finish 等待当 GPU busy。需要增加按原因的 copy bytes、zero bytes、range inflate bytes/us、锁等待、residency hit/miss/eviction，以及完整 CPU 提交范围。

## 与原生 Artemis 和 MJA 的对应关系

前篇固定输入中的原生 `CGpuSurface::ScanLine`（`0x81032bc0`）直接返回已映射 surface 的行地址；`CJpg::Load`（`0x8100eb74`）通过输出对象的行接口写像素，**输出对象是实际 GPU surface 时**可省掉额外完整 CPU 图像。SO 的 CJpg（RVA `0x0055f080`）及后续 MOGL 上传需要另查是否共享像素；Hazuki 的 shared-pixel 适配正是把像素 owner 和纹理视图连起来，不能只复制一段 memcpy 优化。

对本仓库有用的是“解码/上传共享 owner、按规格复用输出容量、索引定位、只准备当前/未来需要的资源”。原生 MJA 自身也没有证明是异步流水线；不能因为叫 MJA 就推定没有上传、没有重复帧解码。本实包六个图像归档是 KIMG/KATL，电影目录为 MP4；需要优化的是当前 variant / atlas 的数据流，改成 MJA 容器不会自动减少组 pass。

## 建议按以下顺序改动和验证

| 优先级 | 改动 | 可观测验收 |
| --- | --- | --- |
| P0 | 补齐 range inflate、所有复制/清零及各原因等待的计数；区分登记与真实上传 | 同帧可解释 I/O、准备、提交和等待；不以累计 worker 时间充当帧时间 |
| P1 | 使用已读 atlas 的共享范围；固定有界 worker；合并在途需求；GXT 首次使用保留首次读出的 owner | 一次 UI 首次加载每个压缩 atlas 不再按子图重复 inflate；CG GXT 首次采样不再第二次读盘 |
| P1 | 去掉 C RGBA → Rust Vec 的强制复制；硬件 JPEG 缩短 CSC 输出 → 最终纹理链 | 软件路径完整像素复制从 2 次降到最多 1 次；硬解路径从 3 次降到可行的 1 次；输出像素与错误路径保持 |
| P1 | 缩小或消除 PS backdrop；验证组融合；修好帧存储生命周期后减少全局 drain | 驻留动画的 pass、整面 copy、等待次数下降；色彩/alpha/层次像素验证通过 |
| P2 | CDRAM 子分配/规格池，压缩 payload 不先清零再覆盖；实际灰度 rule 保持 R8 | 分配、映射、zero bytes、淘汰和重载量下降；内存有界且无采样覆盖竞争 |

真机验收至少分为：固定驻留画面、角色差分循环、首次进入 UI/图鉴、切场景和循环第二遍。记录 p50/p95/p99 帧时间，同时记录新上传字节和 miss；前两类若 upload bytes 为零而仍慢，收益应来自渲染图/同步优化。后两类更能验证资源链改动。所有数值要绑定实际运行 eboot/build、资源 manifest、scene divisor 和 canvas 尺寸。本次没有真机日志，不能确定上述各项在用户所见低 FPS 中的百分比。
