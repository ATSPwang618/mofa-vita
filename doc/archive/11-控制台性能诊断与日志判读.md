# 控制台性能诊断与日志判读

本次为性能疑点增加观测，未删除 Finish、改变绘制次序或实施纹理池等优化。设备端性能记录和 panic 直接调用 `sceClibPrintf`，不创建、追加或同步 `performance.log`；release 关闭原 DEV 文件追踪。游戏正常的素材读取和存档行为不属于本次日志改动。

## 使用

安装 `release/knife-vita-game-540p.vpk`，资源仍用原来的 `ux0:data/knife-woh-540p/assets`。本次诊断包编译时设置 `KNIFE_PERF_CONSOLE=1`，默认开启控制台采集；启动时若根目录的 `perf-enable.txt` 存在，只有内容 `1` 开启，`0` 关闭。根目录没有该文件才检查 `assets/perf-enable.txt`；两处都没有则使用编译默认值。读取开关只发生在启动时。

输出 schema 3：一次 header、一次 startup 计数快照，之后每五秒输出帧时间汇总、累计计数、最多八条资源热点，以及该窗口最慢一帧的增量。记录绑定 build tag、资源 profile 的 manifest SHA256、时钟请求结果、实际 scene/composite 尺寸、scene divisor 和所处 scene/PC。

控制台捕获保存在电脑后，可运行：

```sh
python3 tools/read-vita-performance.py capture.log --console --environment hardware
```

`--environment emulator` 用于模拟器捕获。环境由调用者声明，工具不会从帧率猜测是真机。`--out` 可另存电脑端分析 JSON。旧 schema 1/2 文件仍可使用原入口分析。

这里没有逐 draw 的文本输出。每个 printf 片段不超过 900 字节；长 JSON 用 `audit_chunk` 的 seq/part/total 重组。这样也覆盖了 [Vita3K 中 sceClibPrintf 的 1 KiB 缓冲实现](https://github.com/Vita3K/Vita3K/blob/master/vita3k/modules/SceLibKernel/SceLibKernel.cpp)。解析器能去掉控制台前缀；缺片、缺 bank、重复片、损坏计数会明确标记或拒绝，不能当成零复制。一次捕获分析上限 16 MiB，多个启动应分开分析。

## 指标口径

`rust.*` 和 `native.*` 是累计 u64 计数。每项包含 `calls / us / bytes / aux`；未发生的零项省略。`audit` 结束标记给出本组 bank/热点数，只有完整组才计算增量。startup 与后续窗口分别列出，累计值不会在输出时清零；资源热点表每个窗口重置。

- `us` 是 CPU 侧墙钟时间，包括该作用域内的阻塞。跨 worker 会重叠，父子作用域也会重叠，不能把所有时间相加。
- CPU 复制/清零的 `bytes` 按被观测调用的长度统计；不是物理内存总线事务数，也不能据此声称编译器没有消除某次源码操作。零耗时可能只是低于计时分辨率。
- GPU copy 的 `bytes` 是单向逻辑像素 payload，既不是 CPU memcpy，也不是实测显存带宽。完成通知和 Finish 只表示 CPU 等待，均不等于 GPU busy。
- `block_alloc_cdram/main.bytes` 是请求长度，`aux` 是成功分配/映射后的对齐长度；失败另计 `block_failed`。纹理上传的 `aux` 是所属对齐分配长度。
- 多线程快照是逐字段近似观察；完整资源生命周期的累计字节在 worker 结束后核对。GXM 主线程字段在帧边界读，没有并发提交。

## 疑点与观测点

| 疑点 | 主要指标 | 怎样对照 |
| --- | --- | --- |
| UI 子图重复 inflate 整个 atlas | `rust.nx_range`，热点 `archive:index:entry`；`rust.range_select_copy` | `bytes`=完整解压输出，`aux`=选中范围长度。热点同一 atlas 多次、输出远大于选中量，结合 `card_read_bytes` 检查放大；range 解压现在也进入旧 `nx_inflate_us/calls` |
| 分配、清零和等待文件锁被漏计 | `rust.archive_buffer_zero`、`rust.archive_lock_wait` | 前者包括读缓冲分配/resize，后者仅锁等待；原 card read 仍只计 seek/read，不混入解压 |
| ByteStage 工作失控或重复需求读取 | `stage_request / skip_ready / skip_inflight / thread_start / complete / read_failed / spawn_failed / hit / miss / miss_inflight / evict` | `miss_inflight` 表示 take 未命中时同 key 仍在途。请求数、启动数、命中数不可混为一谈；需求端是否随后重读需结合 range/reload 和热点 |
| staging 内存峰值 | gauges `stage_inflight / stage_requested_bytes / stage_ready_bytes` 的 value/peak | requested 是在途请求的**选中输出范围**，不包含完整 NX 输入、线程栈、codec scratch；不能拿它冒充总 heap 峰值或内存上限 |
| Arc/Vec 来回复制、无用 retained | `stage_vec_to_arc / stage_arc_to_vec / ui_gxt_unused_retain / ui_other_retain` | 比较这些调用的 bytes/us；`Arc::clone` 不在复制计数中。`ui_gxt_unused_retain` 是源码构造/释放点的观测，不声称优化器必然保留底层拷贝 |
| GXT 初读被丢弃，真正使用再次重读 | `gxt_register / gxt_reload` 的同资源热点；`native.upload_gxt` | register.bytes=KIMG envelope，register.aux=GXT payload；reload 只计 loader 与长度验证，之后的 parse/reserve/native upload 不计其中。登记不是实际上传；同一窗口计数相等本身不能证明是相同资源 |
| PNG/JPEG C 输出又复制到 Rust | `rust.decoded_c_to_vec`；`native.png_decode / jpeg_software_decode` | C→Vec 字节与实际解码尺寸对应。初次非 GXT 的 `rust.image_first_upload` 热点给出资源名、实际 WxH、bpp、alter，便于确认 RULE 是否仍走 RGBA |
| 硬件 JPEG 的额外搬运 | `native.jpeg_stream_copy / jpeg_hw_decode / jpeg_hw_csc / jpeg_rgba_to_heap` | 再结合 C→Vec 与最终 upload；用旧 `jpeg_hw_ok` 和 fallback 原因区分成功硬解与回退，不能把 598 个 JPEG 都当硬解 |
| codec 内部清零/编码流复制 | `native.decode_output_zero / decode_work_zero / png_input_copy` | work zero 是显式 decoder 工作分配清零，不含所有库内访存；PNG input 只计 read callback 的 bytes/calls，没有给每个输入块增加时钟采样 |
| 语言裁剪与 CPU grade | `rust.language_crop / cpu_grade` | crop.aux=选择后的长度；源与目标重合（top=0）时 bytes=0。grade.bytes 是处理像素长度，不是 memcpy |
| CDRAM 上传、更新及清零 | `native.upload_rgba / upload_r8 / upload_gxt / texture_update / zero_linear_source / zero_render_target / zero_gxt` | 对 GXT 单独比较 zero.bytes 与 upload.bytes，避免把新 render target 的必要初始化混入“重复上传” |
| 分配粒度与反复回收 | `block_alloc_cdram/main / block_free / block_failed`，`rust.deferred_evict / deferred_reserve` | 对齐长度与请求长度比较；evict 热点含资源名、字节、退休/等待耗时。free.bytes 只计成功释放 |
| 驻留命中还是新上传 | `gxt_resident_hit/miss / image_resident_hit/miss`；`resident_deferred_bytes / retained_encoded_bytes` gauges | hit/miss 按每次 prepare 中的唯一 deferred 纹理计，不按 draw 次数；缓存整个 stage 时可能没有相应的图片 draw。累计值只在完整帧 pin 集建立后统计 |
| PS 全面快照、组 scratch | `rust.copy_ps_snapshot / copy_group_scratch / copy_target` 的热点；`native.copy_gpu_quad / copy_gpu_transfer` | Rust 计数在命令执行时提交，丢弃的 encoder 不会计为实际 copy；generic target 热点为 `from -> to`，可识别 stage → scene |
| 顶点构造、合批、上传 | `rust.quad_build / command_merge_copy`；`native.vertex_copy / basic_vertex_write` | 区分 CPU Vec 构造/复制和最终 GPU 可见 MAIN 的数据写入；不能拿 672 B quad 与数 MiB 全面 copy 等量归因 |
| CPU 命令录制和舞台复用 | `rust.draw_record / command_append / stage_reuse / stage_redraw` | record/append 包括各自输入验证和命令组织。reuse 只在实际提前返回处计数；旧 stage_repeats 只表示旧指纹相等，且该指纹字段不完整，不能作为像素等价或实际省略 pass 的证明 |
| 提交计时漏掉大量工作 | `native.draw_validate / draw_program / draw_bind / draw_uniform / vertex_copy / draw_submit / draw_total / draw_basic_total` | draw_total 是完整 effect 调用；旧 draw_cpu_us 口径保留用于兼容，不再用它代表总提交时间。draw_* 分项可能在错误返回前不完整，应先看 total.aux |
| shader/组路径实际使用情况 | `native.draw_ps / draw_mask_alpha / draw_group_fused / draw_alter / draw_blur / program_patch` | shader 分类是完整 CPU 调用的子集；program_patch 计成功的 effect 程序首次创建，不是 GPU shader 执行耗时 |
| scene 切换、等待及 present 串行 | `native.begin_scene / end_scene / finish_* / transfer_finish_* / display_queue_enqueue / display_queue_finish / present_total` | Finish 按 target、copy、present 前后、destroy、update、seal、readback、ring、DEV、close、movie 分开；所有原有调用点保留 |
| 意外读回屏幕 | `native.cpu_readback` | 与截图/显式 DEV 操作对照；普通绘制若出现大量 readback 需继续追踪，不把 GPU quad copy 当 CPU 读回 |

## 慢帧、热点与测量开销

每个窗口保留最慢一帧的 frame/scene/PC、work/update/render，以及该帧主线程的 deferred miss、loader 时间、实际纹理上传调用字节、GXM 清零字节、GPU 逻辑 copy 字节、等待和完整 draw 时间。此处不把后台 decoder 的全局累计耗时塞进该帧。

帧时间给出 p50/p95/p99 的直方图上界及精确最大值；超过 100 ms 的区间也细分到 125/150/200/250/333/500/750 ms、1/1.5/2 s。它不是每帧精确百分位，也不是跨窗口合并后的全局百分位。

热点最多存 128 条，同一指标最多 16 个名称，每次只输出 CPU 时间最高的八条。`hotspots_omitted` 是未输出的已收集行数，`hotspot_dropped_updates` 是表容量/同类上限拒绝的更新数；全局计数不受热点截断影响。没有出现某个名称不能当作它从未运行。

`probe_snapshot_us` 是每帧前后快照的累计取样耗时；`previous_console_us` 是上次五秒汇总的采集、格式化和输出耗时，startup 输出也会出现在首次窗口的该字段。work 计时排除这部分日志聚合/快照及 pacer，wall/FPS 保留它们对实际帧间隔的影响。热路径计时器与 atomic 更新本身仍在被测工作中，需要用开关 0/1 在同一场景做 A/B 才能量化全部观测开销。

建议按顺序采集：驻留不变画面、角色差分循环、首次进入图鉴/UI、循环第二遍与切场景。先判断慢帧是否有 upload/miss；没有则优先看 GPU copy、scene/Finish 和提交。如果有，分别比较 range 放大、重复 loader、decode、C→Vec、CDRAM copy/zero、allocation/eviction。不要直接把不同线程和嵌套作用域的 us 相加后除以帧时间。

## 构建与验证

使用 Docker 镜像 `${HISTORICAL_BUILD_IMAGE}` 内的 `nightly-2026-05-28` 和 `/usr/local/vitasdk`，按仓库 `game release` 脚本构建 native540。编译参数额外设置 `KNIFE_PERF_CONSOLE=1`，build tag 为 `mofa-perf-console-20261030-r2`。生成 VPK、对应 ELF/SELF、map、收据和完整验证日志；最终产物身份以 `.work/perf-audit/verification.json` 为准。VPK 为 4,950,522 字节（约 4.72 MiB），SHA256 为 `21024e9cc9b4ca8b476bd9edf5ead8ef364c8279d78cabd42bf856012251e4d3`。

验证包含：schema 1/2 兼容及 schema 3 分片/缺片/u64/reset 解析，Rust 并发 range 的完整输出/选中范围计数，C 并发大于 32 位的累计字节与 disabled/ABI 检查，帧直方图，原 renderer host 回归，以及真实 C 的 copy/viewport/compressed/present SDK 边界测试。旧夹具中缺失的时钟/uniform 声明，以及两缓冲和未扣 JPEG reserve 的旧边界已同步到当前生产契约，生产缓冲数量和预算没有变更。

这些检查不执行真实 GPU，不提供硬件 FPS、GPU busy 或像素等价结论。真机运行的控制台输出到位后，再按上表逐项归因。
