# mofa vita 真机日志耗时归因与优化计划

这次日志把问题分成了两条：**约 5 FPS 的持续慢帧主要耗在大量离屏场景与同步等待；首次使用 UI 和 CG 的长停顿主要耗在重复读取和完整 NX 解压。** 删除额外 CPU 像素复制有价值，但它不能解释本次重场景在纹理全部驻留后仍需要约 208 ms/帧。

本计划按“先提高重场景持续帧率，再消除加载与演出停顿，最后收敛内存和剩余 CPU 开销”排序。表中的时间是当前路径观测到的成本，**不是保证能收回的时间**。PS、组复制和 Finish 包含共同的工作，收益不能相加。本文记录 r2 日志分析时的基线结论；其不可变副本已保存。后续 r3 实现与新包见 [13-渲染优化实现与基线对照](13-渲染优化实现与基线对照.md)，勿把下列基线耗时当作新版本收益。

## 最后重场景窗口的完整耗时账

所有等待合计 **187.124 ms/帧，89.82%**；target 与 copy 两类 Finish 就有 **152.630 ms/帧**。最慢的 frame 2450 则为 work=216.849 ms、wait=195.450 ms、draw=7.301 ms。

这是 CPU 在这些边界观察到的等待，里面包括尚未完成的 GPU 工作与调度。日志没有 GPU busy 或逐 shader GPU 时间，不能把 187 ms 全叫作“空转驱动开销”，也不能假设删调用就能收回 187 ms。

同一窗口的复制链如下。Rust 行是相应 native copy 的上层分类，彼此与 native 计时有包含关系。

| 路径 | 次/帧 | 逻辑 payload/帧 | 包含等待的 CPU ms/帧 |
| --- | ---: | ---: | ---: |
| PS：`group pixel -> backdrop` | 8.5 | 4.202 MiB | 62.999 |
| 组：`group pixel -> scene` scratch | 3 | 1.483 MiB | 10.576 |
| `stage -> scene` | 1 | 0.494 MiB | 3.768 |
| native GPU quad copy 总计 | 12.5 | 6.180 MiB | 77.114 |

这些是 GPU 内部采样绘制的复制，**不是 CPU 每帧把 6.18 MiB 图片重新上传**。12.5×480×270×4 正好为 6,480,000 B。前面个别最慢帧有 13 次复制，所以是 6,739,200 B；两者不要混用。

PS copy 的 62.999 ms 也不是该 copy 自身的 GPU 执行时间：它先在 Finish 中等待前序绘制。删除 copy 后，仍有必要的前序工作可能改在后面的完成点等待。排序依据是可删除的整面 pass、依赖边界与实际覆盖次数；具体收回多少 ms 必须逐项 A/B。

该窗口实际 upload、GXM 清零、reload、deferred miss、deferred eviction、readback 均为 0；`deferred_prepare` 只有 0.083 ms/帧。后段相邻窗口也维持同样的高等待、零上传状态。这排除了“持续低 FPS 主要由图片反复 CPU→GPU 上传或驻留抖动造成”的解释。

## UI 和 CG 停顿的具体来源

已输出的 `allui:6:DISP_PARTS_EN.NXZ` 热点累计就有 **54 次**，处理 1,109,346,408 B 解压输出，作用域累计 37.543 s。每次完整输出 20,543,452 B；取一个小 KIMG 也必须解完全部流。

| 资源/帧 | 已测重载 | 同窗口直接证据 |
| --- | ---: | --- |
| `mode_help` / frame 239 慢帧所在窗口 | 785.086 ms | 该慢帧 work=1101.090 ms，只有一次 deferred miss，实际上传仅 41,840 B |
| `lineBreak_a` / frame 374 窗口 | 779.341 ms | 同 atlas 的完整 range 解压仍发生 |
| `pageBreak_a` / frame 1301 窗口 | 781.218 ms | 完整输出 20,543,452 B，仅选中 131,168 B，**156.62 倍** |
| `txtwindow01_en` / frame 2089 窗口 | 780.034 ms | 该窗口最慢帧 984.232 ms，reload 780.034 ms |
| `IMG2326/2327/2328` 等 CG | 约 88–91 ms/张 | 约 1 MiB KIMG 的 range inflate 自身约 69 ms，之后才做约数 ms 的真实 GXT 上传 |

源码仍是 `ui_textures` 已持有完整 atlas，却为每个子图启动 ByteStage；之后拿不到 staged 子图，又在 prepare 回主线程从完整 atlas 解压提取。常规 CG 的 `Pixels::GxtAlter` 则在 worker 已拿到 encoded 后，只登记 `DeferredBytes::Reload` 并释放 encoded，首次 prepare 再读一次。

因此加载链首要操作是**消除已经做过的读取和解压**，不是先换更快 memcpy 或增加图片线程。frame 239 除 reload 外还有约 316 ms 工作，单帧现有探针不能把它全部归给某个 codec/分配器；这里不把 1101 ms 全部许诺为可消除的重载时间。

当前 Hazuki 基线仍为 `deaa8402a1e5ee0d40b1f9fe0144c107c3f7b6e3`。以下是实际 Vita port 代码，而非只凭 Android GLES 接口推断：

1. [native_blend hook](${REFERENCE_PORT_ROOT}/platform/vita/port/render/gpu/hooks/native_blend.c) 在 so `DisplayInner+0x005d57b8`、进入 EnableCopy 前接管，成功路径直接执行原生混合。保留 ABI 字节检查和不支持状态的原路径回退。
2. [native_blend adapter](${REFERENCE_PORT_ROOT}/platform/vita/port/render/gpu/vitagl/native_blend.c) 使用 16 B position/UV 顶点、`gpu_alloc_mapped_temp` 帧内映射存储，直接绑定 source/可选 mask，**没有额外 destination 纹理**。已有 GXP 包 193/193 与参考原生 ELF 完整字节相同，五个已核对 USSE 样本确有读取目标颜色的编码。这提供了替换 PS snapshot 的具体方向。
3. [image_storage](${REFERENCE_PORT_ROOT}/platform/vita/port/render/image/storage/image_storage.c) 已处理 PNG/字形 ScanLine 直接写映射像素、接管已上传存储及写时复制；[native_pixels](${REFERENCE_PORT_ROOT}/platform/vita/port/render/gpu/vitagl/native_pixels.c) 使用映射池、view/CPU 所有权、generation 和实际释放回调记账。互斥锁只保护元数据，不在锁内等待 GPU。
4. native_pixels 的退休先进入现有 `mark_as_dirty` 回收链，真正 fence 保护的释放发生后才归还预算；不能只仿照“过两帧再 free”。上游 [vitaGL 的 scene_end/scene_reset](https://github.com/Rinnegatamante/vitaGL/blob/master/source/gxm.c) 也展示了 EndScene notification 和连续 BeginScene 的实现参考。上游当前源码是协议参考，不冒充本机静态库逐字节实现。

Artemis 的 192 个 FS 是自身目标格式、混合、mask、反相、灰度和着色的组合；**不是魔夜 24 个 PsOp 的一一对应实现**。mofa 还有 sRGB target、HALF 输出、特殊 alpha 与 rule/haze/soft clip。应迁移机制和协议，按 mofa 的现有公式生成自己的等价程序。

## 按预期收益排序的实现方案

### 1 PS 目标颜色读取替代全屏快照

**收益范围：持续重场景，证据强。** 当前末窗 PS snapshot 为 8.5 次、62.999 ms/帧；此外还打断目标 pass，引入恢复后的 target Finish。62.999 ms 已包含 copy Finish，不能再加一次相同等待。

实现入口是 `vita.rs::try_draw` 的 `Blend::Ps` 分支与 `effects.cg::fs_ps`，参考 Hazuki `native_blend_try`/`vglDrawNativeBlend`：

- 先为每种 PsOp 增加固定数组频次与目标分类，保持窗口汇总。现有日志只有 PS 总数，不能诚实地声称某个具体 op 已被证明最热。
- 用最小 GXM 样例验证目标颜色输入，核对输出格式、目标原生编码与线性化行为、alpha、相邻透明绘制次序；检查生成 USSE 确实读目标颜色。**不能把正在写的 target 当普通纹理采样来代替这一步。**
- 按 op 编译等价变体，保留 shade、rule、haze、soft clip 与源 alpha 的全部契约；已通过的组合才删掉 `Command::Copy` 和 backdrop sampler。未支持组合继续走现有 snapshot。
- 保持 source/mask 资源所有权、GPU 可见内存和绘制次序。不要把所有透明层按纹理重排，也不要用“alpha 为 0”一概跳过那些忽略纹理 alpha 的 op。

验收：高覆盖后 `copy_ps_snapshot` 从 8.5 次/帧向 0 下降、PS draw 数和画面保持，scene/Finish 随之减少。每个 PS 至少对应一个可删除的 copy scene；能否再合并恢复目标的 scene 取决于原命令边界，不能直接把 39 次 scene 许诺成固定的 22 次。

先验证现有着色器工具链能够生成所需目标颜色读取程序。原版 GXP 证明机制存在，不证明当前 Cg 配置已支持；如果这个最小样例尚未跑通，组融合和安全连续提交可以独立推进，保留 PS snapshot 回退。

### 2 完整 arena 与资源退休协议后减少全局等待

**收益范围：所有场景，潜力大，必须先保证生命周期。** 当前 target/copy Finish=152.630 ms/帧；显示三项 begin/end/drain 另有 34.074 ms/帧。这些成本会被方案 1、3 同时降低。

按下面顺序改造，而不是直接启用旧 `pass_finish_flags`：

1. basic/effect 顶点按整个提交批次单调分配，copy/clear 同样纳入，先保留全部 Finish 做像素对照。当前 `effect_scene` 每 scene 将 `used=0`，clear/copy 又复用 basic 顶点区，直接删等待会覆盖 GPU 尚未读取的数据。旧 effect arena 溢出分支被更早的容量检查挡住，不能依赖它自动保护。
2. 为 Begin/Draw/Copy/transfer/update/clear/readback 统一记录读写与存活范围，覆盖 RAW、WAR、WAW、render/transfer 跨队列可见性，以及 uniform、索引、depth、纹理和 target。只按 Begin/End 扫描无法覆盖现有 pass 外的 Copy。
3. 采用同一 GXM context 内按序提交与有根据的表面依赖协议；CPU 等待保留在真正要覆写、销毁、读回或复用内存的位置。不能用一个 CPU notification 代替所有 GPU 数据可见性条件。
4. 引入有预算的两槽或三槽 frame arena，最终提交有 completion；在槽复用时等待。槽持有所有纹理/target 引用及退休列表，失败路径保留 owner。支持容量预检、受控 drain 和退出排空。
5. 接通有界显示队列背压，在安全的槽复用/退出位置 drain，取消每帧无条件 `DisplayQueueFinish`；显示缓冲和 CPU arena 的槽数与所有权分别管理。

容量必须预检：现有 native effect arena 为 32760×112=3,669,120 B，而 CPU 记录上限是 16 MiB 顶点。不能假定任意合法 CPU 帧都装得进 native arena，也不能直接给每个 frame slot 各预留 16 MiB；应按整帧字节量、MAIN/索引预算和受控分段制定上限。

验收：固定场景下 Finish 次数明显降低，完成事件能证明无提前覆盖/释放；帧槽、显示队列、退休内存均有上界。像素、错误回收和长时间切场景通过后，再看 p50/p95/p99 与 CPU/GPU 重叠。VBlank 及必要 GPU 工作不会因换等待位置自动消失。

### 3 将组 scratch 和 MaskAlpha 融入最终合成

**收益范围：组密集场景，证据强，现成候选可用。** 本次每帧 3 次组 scratch copy，10.576 ms/帧，加上独立 MaskAlpha scene 及关联 Finish；后者与方案 2 的成本池重叠。

`game.rs:6187` 仍调用 `try_group_composite_via_scratch`。候选 `try_group_composite` 已存在，但代码明确说明未通过精确像素对比，不能直接改调用就算完成。

先保留 pixel/mask 两张持久输入面，将“pixel→scratch、scratch 上 MaskAlpha、scratch→stage”替换成一次读 pixel/mask 的最终合成。普通 blend 先通过，PS 组合再接方案 1 或继续保留原 snapshot 回退。逐项重现旧链的 RGBA8 alpha 量化、RGB 的 sRGB 写回/再采样、HALF 精度与像素中心；仅 `round(pixel.a*mask.a*255)` 不能证明 RGB 等价。

验收：组数不变而 `copy_group_scratch`、`draw_mask_alpha` 向 0 下降，fused draw 与已支持组对应。每个成功替代的组减少 copy 和 MaskAlpha 两个 scene；末窗全部三组成功时可少六个 scene。所有 256×256 alpha 组合、彩色透明边缘、opacity=0/0.37/1、gamma、PS、清屏与持久 mask 轨迹分别对照。

### 4 复用已解压 atlas 并改为有界按需 staging

**收益范围：初始化、首次 UI 和约 780 ms 的卡顿；对驻留后的 208 ms 慢帧没有直接收益。** 这是加载路径收益最高的一项。

在 `Assets::ui_textures` 把现成 `data: Vec<u8>` 移入共享 owner，子图只保存 range、元数据及 locator。可用 `Arc<Vec<u8>>` 等移动原 Vec 的 owner，避免每个子范围再次分配/复制；不要误以为 `Arc::from(Vec)` 必然零复制。

按 atlas 整块的实际字节数收费，多个 view 共享一次占用；冷 atlas 被淘汰后采用一份同 key 在途任务，按当前页需要批量提取。用固定 worker、任务/在途字节上限和 generation 取消，替代每子图一线程。需求端加入已有请求，不能另起一份完整解压；不对未显示的全部子图提前读盘。

把无用 `ui_gxt_unused_retain`、Vec→Arc→Vec 的往返一起删掉。预算不足时允许释放大 owner 并有界重载，不能为了“零复制”永久保留所有 atlas。DISP_EN 约 19.59 MiB，24 MiB 的旧 staging cap 不能同时容纳任意多个完整大 atlas。

验收：同一 atlas 在一次有效缓存生命周期内只读/解压一次；`pageBreak_a` 等命中时不再出现主线程全 atlas inflate；线程数有固定上界、57 次预读淘汰和大量未消费结果明显下降。先保持压缩素材不变；本包外层 NX 对部分 atlas 压缩率很高，不能全局去 zlib 交换成几十倍读盘量。

### 5 首次 GXT prepare 消费 worker 已完成的 payload

**收益范围：CG 切换的约 90 ms 停顿，证据强。** 不需要把 GXT 改成 JPEG 或运行时 RGBA。

`upload_pixels(Pixels::GxtAlter)` 应把 worker 读好的 encoded owner 移交 deferred source；第一次 prepare 借用该 owner 解析和上传，成功后按预算释放或保留。之后真正发生 GPU eviction 才走 locator 重载。UI 和 CG 可共用 owner+range 模型，但不能混淆 CPU 编码缓存预算和 GPU 驻留预算。

增加固定预算的 ready/pinned 编码块，预取只针对近期可见的 variant；保留现有 frame admission、尺寸/格式校验及过期 generation 检查。所有 GXM API 仍由渲染线程提交，worker 不擅自操作 context。

验收：首次 GXT resident miss 仍发生一次正确上传，但不再新增相同资源的需求端 card read/NX inflate；worker 完成后首次使用不出现 86–94 ms 的 reload。真实冷 miss 与淘汰重载单独统计。

### 6 精简 CPU 命令和顶点流并保留有序合批

**收益范围：结构性问题收敛后的数 ms/帧。** 末窗 `draw_record=3.376 ms`，其内的 `quad_build=2.266 ms`；native effect draw=7.055 ms，其中 validate=1.882、vertex copy=0.554、bind=0.387、uniform=0.397 ms。父子作用域不能相加。

对无 clip/haze/soft 的普通 quad 使用固定数组生成，整帧复用命令与顶点容量；将不可变输入检查前移到明确信任边界。借鉴 Hazuki 16 B position/UV 专用流，为 mofa 增加保留所需颜色的紧凑格式；复杂效果继续走原 112 B 通用流。每 draw 不再总是绑定四个无用 sampler，状态缓存只在自己的 owner/scene 约束内生效。

Hazuki 的 16 B 流把颜色留在 uniform；mofa 的合批顶点仍可能需要各自的浮点颜色。可先用 position/UV+float4 color 的 32 B 路径，不为追求 16 B 把颜色精度或原本可合批的不同颜色丢掉。

末窗每帧约 252 个 quad、247 个 effect draw、只合并约 6 次，值得加“因纹理、shader、blend、params、haze、pass 边界不能合批”的固定计数。现有日志不足以断定究竟哪个条件阻断合批，不能直接以纹理少为由跨透明顺序重排。

PS op 专门化可与方案 1 同做，但 shader GPU 算术成本需要 completion/USSE 证据；`draw_program`、`program_patch` 的 CPU 时间不能代替它。

### 7 减少必要性已证明消失的 stage 到 scene 中转

**收益范围：本次可定位 3.768 ms/帧的 copy 父作用域，加上相关依赖；优先级低于 PS/组。** 普通复制全程 2477 次，末窗每帧一次。

先建立哪些消费者必须写 scene、哪些只需读 stage 的显式条件；无 scene 写入、快照、ghost、focus、transition 等需求时，可直接消费只读 stage 视图。其余路径保留一次明确的 copy，或者在已证明无 stage 缓存/独立读者的情况下直接渲染进最终目标。

**不能简单把 `scene_rt` 与 `stage_rt` 设成同一张纹理。** stage 会跨帧复用，scene 还承接 UI/特效；别名会污染缓存或产生反馈采样。还要保存 FADS 捕获→组 scratch 读者→stage-to-scene 的现有顺序。

分段/组缓存也在此阶段研究，但先修完整输入签名；本次重场景没有整 stage reuse，缺乏逐组 mutation 轨迹，无法把分段缓存排在已测 PS/组中转之前。

### 8 CDRAM 子分配与有条件清零

**收益范围：小纹理和长时资源切换的容量/抖动，本次稳态收益低。** 峰值驻留 21 MiB、小于 32 MiB，且零 deferred eviction，不应先粗暴扩预算。

按规格复用分配；再在较大映射 block 内按格式地址对齐做子分配，并同步修改 Rust admission 对实际池占用的收费。退休区间在 GPU completion 前继续计费，不允许只改 C 分配而 Rust 仍每纹理向上取整 256 KiB。

对于立即完整覆盖的压缩 payload，只清必要 padding；render target、持久 mask、PNG interlace 等依赖初始值的路径保持初始化。参考 Hazuki `vglNativeTextureOverwriteRGBA` 的受限入口，不能全局删 memset。

验收以实际池占用、分配/映射次数、碎片、退休预算及热切换 p99 为准。本段 GXT 清零总计只有 24.531 ms，不能包装成解决 5 FPS 的主修复。

### 9 解码 owner 移交和单通道保留

**收益范围：本段零散 PNG，未来灰度 RULE/JPEG 场景需重新测。** 先用具有 C 析构器的独占 owner 或明确 decode-into 契约，消除 C→Rust 全图复制；现有 `DecodedImage` 是 `!Send`，必须审计 worker 移交，而不是把 C malloc 指针伪装成 Rust Vec。

灰度 RULE 可在证明只读 `.r`、采样/gamma/反相一致后走 R8。组 mask 改单通道还要新增 render-target 与 alpha blend/channel 映射契约，现有 source R8 接口不足以直接替换。硬件 JPEG 当前没有样本，暂不改 CSC 输出与 GXM pitch/缓存协议。

验收：受影响资源的 bytes 按实际尺寸下降，画面/alpha 不变；硬解与 fallback 分开测试。不能凭素材库有 598 个 JPEG 就把当前慢帧归给 JPEG。

### 10 借鉴 MJA 的有界动画资源窗口

**收益范围：未来确认有持续动画 miss 的片段；本次重场景加载停止后收益很小。** 保留已知 variant 的定位索引、current/next/retiring 槽、重复帧命中以及时间直接定位，避免为已经过时的独立图像解码。

MJA 自身在所选 Read 入口没有同帧提前返回，Display 也未恢复出异步 worker；没有理由把它当成直接可移植的高性能队列。魔夜现有 DXT/GXT 已免去了运行时 JPEG 解码，不改回 JPEG 动画。跳过视觉帧不能跳过脚本回调、随机/震动推进和完成 listener；循环末帧语义也不能随意改成取模。

## 实施顺序与每步验收

收益排序不等于可以越过正确性前置条件。建议每项独立保留对照开关，形成以下里程碑：

| 阶段 | 具体改动 | 成功标准 |
| --- | --- | --- |
| 0 固定对照和测量口径 | 固定 scene=1/PC=246 附近轨迹与 UI 首用；补 PsOp/合批原因分布；修 stage 完整签名与旧 pass 标签统计；保留 console 0/1 对照 | 原版和变体资源/输入一致，完整累计组可解析，窗口/累计口径明确；签名修正造成的重画须重新建立基线 |
| 1 安全 arena 与快速资源修复 | 帧内 basic/effect 单调 arena，先不减 Finish；同时实施 4/5 的共享 atlas、固定 worker、首次 GXT payload 移交 | 多 pass 不覆盖顶点；UI/CG 首用不再重复读取，线程/内存有上界；此阶段不以稳态 5 FPS 大涨作为资源修复验收 |
| 2 最大渲染收益 | 实施 1 的目标颜色混合，先高频且通过等价验证的组合；实施 3 的组融合 | 同场景 copy 从 12.5/帧下降；全覆盖的结构目标是先去 8.5 个 PS copy，再去 3 个 group copy，仅余约 1 个 stage copy，而不是承诺固定 FPS |
| 3 GPU 连续提交与呈现 | 在阶段 1 生命周期基础上实施 2 的依赖、completion、frame slots 与显示队列背压 | 同等工作下 CPU 全局等待/串行边界下降；内存、队列和错误回收均有界；逐项检查黑屏、闪帧、错色和提前 free |
| 4 复测剩余热点 | 重测后实施 6–9；动画 miss 真正出现时做 10 | 以新的时间构成选择下一项，避免优化已经消失的旧热点 |

像素验证与性能采样分开运行：像素 fixtures 可用独立 DEV 读回检查 RGB 和 alpha；正式 FPS 对照保持零 readback、零设备端性能文件 I/O。覆盖 PS 各 op 的 alpha=0/1、源/目标 alpha、彩色边界、rule/haze/soft、组持久状态、scene density、UI/菜单、FADS/ghost/blur、快进、保存/加载及退出错误回收。只优化已证明等价的组合，其余继续走原路径。

每个阶段比较主线程 work/render、最慢帧与窗口 p50/p95/p99 上界，以及实际 copy/scene/Finish、reload/upload、并发与退休峰值。预期高收益先以结构指标兑现，再报告真机 ms/FPS；没有把尚未实现的方案写成已测提速倍数。

## 本轮发现的测量限制与后续补点

1. **旧 `pass_top` 不能作逐目标 GPU 排名。** `execute_with_admission` 的 draw 计数使用 `last_pass_label`，它在上一个 End 才更新；当前 Draw 可被记到前一个 pass。Copy 夹在两个 target pass 中时，下一次 Begin 的等待归属也可能仍标给更早的 pass。End 内“Finish”的旧注释已不符合当前代码。此次排名使用独立 native 原因计数、完整 draw 作用域及真实 copy 热点，不使用该旧字段推导 shader GPU 成本。
2. **`probe_snapshot_us` 是累计值。** 最后 190.281 ms 覆盖 2467 帧，约 77 μs/帧，不是最后 24 帧花了 190 ms。`previous_console_us` 则是上次汇总，末条为 119.873 ms；已看到超过 200 ms 的批次，不能称控制台“完全无开销”。它们不在 work 内，wall 会受影响，热路径计时/atomic 的额外开销仍需开关 0/1 A/B。
3. **窗口有缺片。** 精简 frame 主摘要、对关键小摘要避免多片依赖，保留累计 bank 和丢片检测；不要因为控制台丢 sample 把缺失帧当零耗时。当前不增加每 draw 文本打印或设备落盘。
4. **GPU 实际执行与资源等待还需 completion 关联。** 可增加有界的提交序号、目标/操作类别、完成通知和槽复用等待，单独观察 CPU build/submit 与 GPU retire；仍不能用 CPU 等待比例宣称 GPU 利用率。
5. **stage 缓存签名仍缺字段。** 目前只混入纹理地址、R/A、position 和 composite alpha，没有完整覆盖 UV、G/B、blend/shade/rule/haze/soft/clear 等。进一步缓存和动画复用前，必须换成完整渲染签名或覆盖所有修改的 mutation version。修复可能使此前错误命中的帧重新绘制，这是正确性修复，不能隐藏其基线变化。
6. **音频出现一次明显实时性异常。** 最后累计 11 个 underrun 块、一次 late mix、最大 mix 300.079 ms；相邻完整 sample 将增量定位在 frame 2063–2089 区间，其中也出现 `txtwindow01_en` 的 780 ms 重载。mix 包含解码，但不含所有控制/file-open 工作，现有证据不能确认两者因果。图像并发与读取修复后必须复测，必要时分别观察音频读盘/锁、decode 与调度延迟。`audio_queue_full=86757` 是生产端背压次数，不是 86757 次断音；不要增加无界音频队列掩盖 20 ms 块的实时期限。音频线程时长不能再加到主线程慢帧上。
