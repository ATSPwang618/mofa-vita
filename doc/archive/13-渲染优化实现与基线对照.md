## 启动编译与缓存

启动先读取 `ux0:/data/knife-vita/shader-cache/` 中与源码 SHA 和 ABI 匹配的 GXP；缺失或校验不通过才尝试设备已有的 `libshacccg.suprx` 编译器。编译产物经过边界/元数据/反射检查后以临时文件和重命名写缓存，后续启动直接复用。VPK 不分发编译器模块；各候选路径和导入绑定检查见着色器说明。

GXM 还会验证 RegisterProgram 及对应 UCHAR4/HALF4 patch。控制台 `shader_capabilities` 的 `ps_fetch17=1` / `group15=1` 才表示该程序已可提交；`optimization_mask` 表示用户选择，二者不可混同。编译/注册失败继续旧 snapshot/scratch；op18 的既有 GXP 快捷路径仍可工作。`compact_stream.enabled` 表示 32 B stream patch 是否成功。

这轮没有成功生成离线 full-fetch GXP，也没有真机像素等价证明。运行时签名候选受严格能力门限限制，但**门限通过不能替代画面确认**，不得把它写成已测加速或保证全 24 op 必定在设备上启用。

性能记录仍只使用 `sceClibPrintf`。只有首次编译后的 shader 缓存使用设备文件写入，符合用户新增授权；不会写逐帧性能文件。冷启动编译与热缓存启动分别观察，不混作稳态收益。

## 同一 VPK 的逐项开关

默认启用已实现的全部选项。540p 读 `ux0:data/knife-woh-540p/optimization-profile.txt`，270p 则读 `ux0:data/knife-woh/optimization-profile.txt`；文件只在启动读取一次，修改后重启游戏。内容支持逗号/空白分隔、`baseline`、`all`、功能名及 `-功能名`。未知项明确报错，避免默默测试错配置。

示例：

```text
all
```

```text
all -ps-fetch -group-fused
```

```text
baseline batch-arena async-submit
```

`async-submit` 与 `compact-stream` 必须同时保留 `batch-arena`。第 0 项正确性修复和计时修复始终生效；同一新版的 `baseline` 是关闭可选优化的控制组，不能宣称它复现旧版所有 bug。原版 r2 仍有独立源码和 VPK 快照。

[profiles](../performance/profiles) 提供 00–10 累加配置。复制某一个文件的内容到上述 `optimization-profile.txt` 即可，名称不参与解析。这些配置用于后续用户可比片段采集，本轮不要求用户提供自动重放或让代理进入设备。

## 后续每项提升数值

```sh
python3 tools/render-audit/compare-hardware.py /path/to/new-catlog.txt \
  --item 02-gpu-submit --scene 1 --pc 246 \
  --out doc/performance/results/02-gpu-submit.json
```

默认对比固定 r2。加 `--baseline /path/to/previous-capture.txt` 可对比上一项或同新版控制组。脚本要求分辨率、资源 manifest 和时钟一致，只采用完整 sample/frame_window + audit 窗口，输出每帧 work/render/update、FPS 变化、实际节省 ms/百分比以及各计数的每帧量。会保留真实 shader/compact 能力记录。

仍然无法自动重放，因此相同 scene/PC 是取样筛选条件，**不是相同输入轨迹的证明**。长演出、加载缓存、语言和用户操作不同，不能强行将差异归到单项开关；用完整计数核对结构变化。

异步后的等待合计包含 `batch_slot_wait`，避免把等待移动当成消失。`batch_capacity_drain` 包含内部等待，不能重复相加；发生容量 drain 时，draw 的父作用域也可能包含这部分等待。旧 `gpu_finish_us` 仅代表 Finish 类，不能独自代表全部等待。

机器可读状态见 [implementation-status.json](../performance/implementation-status.json)。所有硬件收益字段在新日志出现前保持 `null`。
