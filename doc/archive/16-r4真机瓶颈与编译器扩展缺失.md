# r4 真机瓶颈：核心 fetch 未成立，反馈链和过度等待仍在

这轮日志证实，r4 没有解决最重的持续瓶颈。组融合、紧凑顶点、依赖图和rename确有运行证据；**最关键的PS目标颜色读取仍因编译器初始化遗漏而失败，重绘继续停在group pixel的EndScene链上**。此前的“P0–P6实现完成”只能描述代码接入／构建，不能作为这些路径在实机成立的结论，当前状态已据新捕获修正。

原始日志、计算与逆向证据存于 [r4 capture目录](../performance/captures/2026-10-31-r4)。本轮先做分析，没有修改运行时代码、编译VPK、启动Vita3K或连接设备。

## 根因一：漏掉了Hazuki真实使用的Cg扩展初始化

本次模块SHA、LoadStart、7个导出归属、allocator全部成功，编译器确实已经可用。随后发生：

| 程序 | 编译输出 | 最终能力 |
| --- | ---: | ---: |
| PS19，ID18 | 0 B，4条语法错误 | 0 |
| 通用fetch，ID17 | 0 B，同样4条错误 | 0 |
| group，ID15 | 1032 B，无诊断，缓存／patch成功 | 1 |

两条fetch均在Cg第517、522行报告expected type specifier / identifier，随后destination未声明与return错误是声明解析失败的级联。**失败尚未到GXP反射／patch，不能再归因导出绑定或寄存器接纳。**

已对实际同SHA的编译器和Hazuki现有静态库交叉逆向：

- 编译器词表中`__nativecolor` token=`0xE6`、`__regformat` token=`0xE2`，两者flags均`0x11`，包含扩展bit4。
- keyword注册代码在module offset `0xAA38`检查bit4，`0xAA3C`读取配置`+0x14`；该字节为0时，`0xAA3E`跳过注册。它们于是被当普通identifier。half/float不受此bit控制，group成功使用half也与此一致。
- Hazuki现有`libvitashark.a`的`shark_init+0x4E`真实重定位到`sceShaccCgExtEnableExtensions`；现有Ext库wrapper机器码确实将该配置字节写1。本机模块NID `0x6C3C7547`属于Ext接受版本。
- r4自行完成load/export后直接CompileProgram，**没有这一步**。此前只从编译器诊断字符串读出了FRAGCOLOR合同，遗漏了前端扩展关键字默认关闭的条件。

因此这是确定的runtime集成缺陷，不应再靠更换COLOR、half/uchar或改变混合公式试错。修正方向是接回既有Ext启用／返回检查／释放生命周期，明确记录extension-ready，再编译原FRAGCOLOR入口；缓存身份也应包含扩展策略／ABI。启用后仍须实际GXP、反射、patch与像素确认，不能预先声称全部后续阶段已通过。

本次启动编译总673.128ms，不是持续帧率成本。持续代价在于全部3446次PS（全部op19）仍走旧快照，共1,786,406,400 B逻辑GPU copy。这些不是CPU上传字节。

完整指令、库身份及上游固定commit见 [shader诊断](performance/captures/2026-10-31-r4/shader-diagnosis.md) 与 [机器码证据](../performance/captures/2026-10-31-r4/r4-shader-evidence/compiler-disassembly.json)。

## 根因二：PS真实反馈链仍在反复结束／重开group pixel

当前链为：

```text
结束 group pixel → GPU复制旧目标到backdrop → 重开group pixel → PS draw
                         ↑每个PS重复，形成真实RAW/WAR/WAW依赖↑
```

PC212 audit窗口EndScene总20.583s，其中group pixel为20.129s，占97.79%；其1700次结束恰好等于1256次PS重开，加3×148次重绘的初始组pass。组融合写出的是stage，它虽删掉scratch，**并没有删掉组内PS反馈**。

目前target分类尚未区分初始组pass与PS-resume，因此不能把20.129s全说成某个shader的GPU运算时间。它是CPU停在API内的墙钟，可能含驱动资源复用、提交背压或等待；日志缺GPU timestamps／RT和PB占用，尚不能唯一拆开。

但命令结构的可删除部分很明确：实际class里148次重绘有4730个scene、1255次PS快照。按当前源码，每次fetch成功可删2个scene，得到：

```text
4730 − 2 × 1255 = 2220 = 15 × 148
```

即现有约32 scene/重绘可望缩到15，这是结构验收目标，**不是预测FPS倍数或保证回收全部139ms**。下一轮首先应让真实capability成立、快照计数归零，再比较EndScene＋wait＋整帧时间。

## 根因三：slot条件检查旧批次，却等待全局最新批次

“仍然全串行”不完全准确：全段17,460个scene有4,866个（27.87%）实际省掉VERTEX_WAIT；重PC212也省1,214／4,924（24.65%）。缺计划与arena容量溢出计数均0。依赖图已经运行。

不过另有明确的保守等待：

- `gpu_lifetime.inc:162`检查待复用slot的`last_sequence`是否完成。
- 调入的`wait_submitted`（:41）却等`g->sequence`最新全局提交，而非只等该旧slot。
- 两槽中旧槽尚未完成时，CPU可能把较新的另一个batch也一起等完。PC212有31次batch wait，平均每次53.934ms；96个复用帧平均有16.991ms卡在这里。

这是单提交线程与GPU重反馈链之外，另一处限制流水并行的代码边界。应建立per-slot／per-batch实际完成身份，收窄到安全可复用点，同时保留纹理退休和scanout合同。**不能直接把单地址等值NotificationWait改为旧seq**：该值可能已被更新completion越过，造成永等。

也不能把16.991ms全视为可回收：本日志没有等待前slot目标／completion／latest的差距；GPU吞吐不足时，更早enqueue只会挪动等待。图本身遇到必要hazard仍等待最新global SET，也存在保守覆盖可能，但无need/latest差距数据，不能量化。

RenderTarget的`scenesPerFrame=1`及默认rings值得在热点残留后调查；vitaGL默认也为1，所以目前没有依据把它定为根因、直接扩缓冲。应先拆初始group／PS-resume，消掉已证实的多余链，再判断剩余驱动背压。[GPU逐项证据](performance/captures/2026-10-31-r4/gpu-diagnosis.md)

## CPU复制：有新增，但解释不了持续慢帧

用户担心的额外复制确实发生了：6次rename复制完整backing，共6 MiB、91.098ms，约15.183ms/MiB。rename父scope为100.820ms，不能再加91.098ms。1 MiB形状与字体页吻合，但当前native日志缺owner标签，不能唯一认定六次全部是字体。

同资源进度39次／153,621B dirty updates中，旧finish_update为402.834ms，新为0.018ms；加入rename等互斥局部项，404.829→101.369ms。它证明等待换成了有界复制，并非零成本，也不是已证明端到端省303ms，因为等待可能转移到batch等位置。

PC212持续慢帧的上述资源计数已经不再增长。全段紧凑顶点覆盖174,597／174,597次draw，输入120,111,936→实际47,003,776 B，少60.87%；PC212顶点复制只有0.154ms/混合帧。**继续优化这些CPU拷贝，无法解释或消除此时反复出现的165ms EndScene。**

CPU低占用与这种低FPS可以共存：提交线程在API等待，依赖链中的GPU阶段也可能出现空泡。增加CPU线程不能自动解除读旧目标再写原目标的顺序；本日志也没有各核busy、GPU阶段busy或真实heap使用峰值，不能将overlay百分比直接换算为可提升倍数。

## 采集本身还有约3%–6%的观察开销

PC212完整sample的`previous_console_us`为169.107–309.293ms/轮，相邻通常约五秒；它是前一轮输出成本，不能直接减当前同编号窗口。18次完整计时中部分sample缺失，也不能把收到的15个值当全程总成本。

这项足以影响墙钟FPS几个百分点，应在保留关键证据的同时精简重复／不变统计输出。当前work明确排除logger，重绘138.902ms EndScene仍发生在work内；不能把主瓶颈归给打印。`probe_snapshot_us`是累计额外快照成本，末值274.009ms／2201帧约0.124ms/帧，亦不是139ms主项。

## 独立长停顿：32MiB atlas预算和启动工作集不匹配

atlas按真实need回收的bug修复成立：r3同启动8项evict7次，r4只evict1次。但Game先加载DISP，然后Ui提前登记TITLE/MENU/SAVE/CONF等8个atlas，解压工作集合计44,045,768 B。前五项33,325,083 B与日志peak精确一致；加入CONF后超32MiB，最旧的20,543,452B DISP被淘汰。

随后frame523需求一个131,072B成员，却重新等同一DISP完整解压：work868.506ms，atlas wait863.570ms，占99.43%。启动同key已经加载876.210ms；本轮直接有archive/index/entry热点标签，因果比r3更明确。

这需要修页面登记／首用工作集：离线小metadata或按需登记，保留当前及即将使用DISP的热度。TITLE+DISP+BORDER仅27,207,321 B，本可同驻32MiB；提前处理未用页面把它挤掉。增加有界预算可作对照，但不能替代先识别live set，更不能解决PC212持续EndScene。

同进度r4较r3已经少两次TITLE/BORDER整解压、6,663,869B输出；grade和旧PC425/601尚未覆盖。[资源对照与字节模型](performance/captures/2026-10-31-r4/resource-diagnosis.md)

## 后续处理顺序及成功条件

1. **补回Cg扩展初始化，使op19 fetch真正成立。** 先看真实GXP与patch、capability，再要求该片段PS快照1255→0、scene4730→约2220；最后看重绘EndScene和work。保留数学、混合顺序、gamma及alpha，不能再以“请求flag开启”作验收。
2. **收窄slot/global过度等待。** 用真实完成身份保护arena，记录所需与实际等待点；看复用帧work和EndScene＋batch总量，不能仅把等待从一个API搬到另一个。
3. **消除DISP重复冷准备。** 调整登记／metadata／首用工作集；要求相同key不再为131KiB需求重复inflate20MiB，确认frame523型约0.86s停顿消失。
4. **再减少glyph类whole rename。** 识别owner、合并同帧更新或有界CPU shadow；同时计dirty/full-copy/wait，不盲删保护旧内容的copy。
5. **到相应剧情再判断grade与PC425/601。** 当前结论是未覆盖，不是0ms或已解决。其他驱动容量调查放在第1项成立后的残留上。
