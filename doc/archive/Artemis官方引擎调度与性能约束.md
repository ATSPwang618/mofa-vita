# PCSG01127 官方 Artemis 调度分析与 Vita 性能约束

日期：2026-10-27。本文记录本机官方 eboot 的静态分析、由此审查的 knife 路径、本轮有限修改和后续实机门槛。最终渲染继续直接调用 GXM。

用户提出的风险成立：PC 上能跑的解码、命令构造和缓存维护，不代表 Vita 上有足够的 CPU 时间。当前工作应先固定资源所有权、阶段工作集和异步队列上限，再用实机数据决定纹理编码与细节优化。模拟器用于状态、错误路径和资源生命周期回归，其宿主 FPS 不作为 Vita 性能证明。

## 2. 动画队列：只更新当前项，完成与取消分开

RTTI `N7artemis11CTweenQueueE` 位于 `0x81393690`，typeinfo `0x813f530c`，vtable `0x813f406c`；step 槽为 `0x812ebb0c`，取消/完成槽分别为 `0x812ebbf4`、`0x812ebca0`。证据：[队列 step 指令与伪代码（原证据目录 .work 已清理）、[按需构造路径（原证据目录 .work 已清理）。

可确认行为：

1. 队列对象使用分块存储，`+0x08` 为块表、`+0x0c` 为索引容量、`+0x10` 为队首、`+0x14` 为数量。step 仅定位当前队首并调用其虚函数。
2. 队首返回“未完成”时立即返回。观察到的这条路径没有遍历剩余动画、排序或 GXM 调用。
3. 队首完成后析构当前项、移动队首，再以相同时间参数继续处理下一项。可见实现采用递归；本项目若需要串行动作队列应使用有界迭代，不能照搬递归深度风险。
4. 懒构造路径实际调用 `operator new(0x18)`。本次没有恢复全部入队扩容路径，**不能把它描述为固定容量、从不分配的动画系统**。

`TTween<float>` step 为 `0x8121d478`，有开始时间、延迟、持续量、完成标志及值回调。`0x8121eaec` 只标记结束，`0x8121eaf8` 则选择终值、应用值并可能调用完成回调。证据：[step（原证据目录 .work 已清理）、[取消（原证据目录 .work 已清理）、[强制完成（原证据目录 .work 已清理）。时间参数的单位、全部插值分支和精灵帧动画调度尚未完整证明。

对 knife 的实际审查：`stage.rs` 已有 `LAYERS = 40`，每层 x/y/zoom_x/zoom_y/alpha/rotation 六个内联补间槽，普通更新没有每帧新建一个通用堆对象队列。该处不因 Artemis 使用队列就整体重写。后续若整合串行动作，必须保留本游戏的并行动画、快进、延迟、cancel/finish 和脚本阻塞语义；先以原状态轨迹作为对照。`Stage::advance` 的时间累积追赶循环以及命令/文本构造仍需单独量测，不宣称整帧已无堆分配。

## 4. 显存池与缓存：先减少重叠工作集

`CGpuMemoryPool` RTTI 为 `0x81396040`，vtable `0x81395d6c`。分配入口 [0x8102e7e0（原证据目录 .work 已清理） 将大小向 64 B 对齐，在空闲块中寻找能容纳的项、分裂余块并更新已分配记录/剩余字节；这条函数内未见逐次 OS 分配。释放入口 [0x8123a8e0（原证据目录 .work 已清理） 查找已分配记录并合并相邻空闲块。池初始化大小和全引擎纹理策略未恢复。

这些证据支持“减少频繁大块分配和资源重叠”的设计，**不能推导出官方全引擎没有 LRU**。当前工程也不立即改成新通用分配器：GXM 对齐、纹理格式、隐式分配与退役时点已有专门约束，替换池需要另一组实机证据。

本轮落实三类有限修改，均已进入同一份 DEV 包：

- **驻留计数与稳态快速路径。** `knife-render/src/vita.rs` 新增已驻留 deferred 纹理字节计数。准入仍查询原生 headroom，但缓存预算和 headroom 足够时不遍历所有 Weak 条目、不建立淘汰列表、不排序；实际压力下才收集未 pin 的候选。已驻留纹理只更新时间戳，加载排序只包含本次缺失项。上传/Alter 完成并成功退出原生 pass 后才登记驻留字节；最后一个命令引用退出且原生退休成功后才扣减。失败不能虚增缓存或未确认的余量。
- **菜单/存档目标归属。** `Ui::update` 在进入 Game 渲染前检查菜单/存档阶段及 Witch 在栈状态。离开这两个阶段便释放两张 960×540 RGBA 目标（按本机块对齐共 4 MiB）；仍被编码器引用的资源按既有 GPU 完成约束退役。阶段内继续复用。
- **缺失图集的帧准入衔接。** 先验证 deferred 描述/解码并 pin 完整提交列表，再通过 `Assets::admit_frame_upload` 尝试已有的空闲 CG 回收策略。只有余量检查失败才收集候选；释放一项后重新查询。原生上传、bake 失败发生在准入回调之外，不能借重试重复上传或提交半幅游戏画面。目标在 present 之前分配的路径不受此回调覆盖，仍须单独调整生命周期。

此前回想首开已冻结复现：`bg_backlog` 上传和 Alter 的合计临时峰值需要 4 MiB，原生准入只剩 786,432 B，并且没有可淘汰的空闲图集。证据：[修改前冻结（原证据目录 .work 已清理）。仅释放菜单/存档目标后的中间快照仍失败，新增余量会被其他仍允许驻留的 CG 使用；不能把“释放 4 MiB”直接当作峰值降低 4 MiB。

三类修改后的回想运行仍在第 2,296 帧失败：释放最后一块 900×540 RGBA 纹理后，原生余量从 0.75 MiB 增至 **2.75 MiB**，仍小于所需 **4 MiB**。证据：[当前失败冻结（原证据目录 .work 已清理）。这说明增加一个回收入口还不足以解决同时存活的工作集。没有提高 48 MiB 应用准入或 32 MiB deferred 上限，也没有改用高清回退。

源码中值得优先处理的目标持有期如下。表中是对应字段创建后的显式块大小，不代表这些字段都在每一帧启用，也不能将原生日志 UID 无证据地对应到某个字段。

| 当前字段/路径 | 持有目标及块大小 | 后续审查重点 |
| --- | --- | --- |
| `Game::new` 的 `stage_rt`、`scene_rt`、`old_rt`、`canvas` | 4 张全画布目标，共 8 MiB | 逐项证明旧场景、快照与当前 pass 的内容存活区间，不能盲目合并 |
| `group_targets` | 首次创建后保留 3 张全画布目标，共 6 MiB | 非 group 阶段是否仍需保存其像素；可否在确认完成后复用 |
| `menu_rt` | 1 张全画布目标，2 MiB | 菜单/回想捕获结束后是否仍需保留；仅清捕获标志不等于释放目标 |
| `menu_quarter` | 2 张 240×135 目标，共 0.5 MiB | 同一效果内复用，离开需要模糊的阶段后审查持有期 |
| `WUi::backdrop_rt` | 2 张全画布目标，共 4 MiB | 本轮已在离开 Menu/Save 时释放；帧内命令仍保护引用 |
| 人物 Alter 输出、ghost/noise/freeze 等 | 尺寸和数量依场景而变 | 当前帧、后续脚本和 GPU 退休引用均须计入，不能只看 alpha=0 就释放 |

失败时的显式账本中，9 块 960×540 RGBA target 标记块共 **18 MiB**，9 块 900×540 RGBA target 标记块也共 **18 MiB**，另有字体页、显示/未标注块、条带及小目标。Alter 输出同样带 target 标记，不能把它们全部解释为独立的特效 pass。首要后续工作是**阶段资源所有权 → pass 内容存活区间 → 经 GPU 完成点保护的目标复用**，之后才调整 LRU；不继续靠缓存反复腾挪掩盖结构问题。

## 5. 固定后续实现边界

| 部分 | 固定约束 | 触发后续改造的依据 |
| --- | --- | --- |
| 阶段资源 | 剧情、菜单/存档、回想、影片分别声明拥有的持久目标和临时峰值；阶段退出释放，阶段内复用 | 进入阶段需要的峰值超出预算，先减少同时存活项，再考虑共享池 |
| 纹理工作集 | 当前完整提交列表先 pin；源图、Alter 输出、上一帧/旧场景未退休纹理一并算峰值 | 不允许淘汰本帧纹理来勉强通过准入 |
| LRU | 只在真实压力下作为回收空闲纹理的后备；稳态不能靠每帧淘汰/重读维持 | 记录同一画面重复 upload/read、淘汰后立即回装；一旦出现，先修预算/生命周期 |
| 异步资源 | 文件读/解析使用有界请求、结果和解码队列；取消跳转时使旧请求失效；生产者必须接受背压 | 不用无界预读堆积结果掩盖主线程慢；GXM 注册/上传仍在所属线程 |
| 原图与压缩 | PNG/JPEG 的磁盘身份和 DXT/PVRTC 的 GPU 表示分开；透明边缘、调色板/tRNS、字体例外逐类验证 | 真机解码/上传时延和画质决定转 DXT1/DXT5/PVRTC；编码不自动等于磁盘更小 |
| 动画 | 现有 40×6 内联补间保留；串行/并行/取消/完成语义显式化；避免递归 drain | 以实际计时和状态差分决定是否增加活跃表；不因 PC 循环快就允许无界任务 |
| CPU 命令构造 | 测量 Vec/HashSet、顶点和文本布局分配；必要时再改固定容量或复用 arena | 现阶段仍有这些分配；本轮 fast path 不等于整帧零分配 |
| GPU 生命周期 | 只有 completion 证明已不再采样后才能释放/复用；保持有界退休队列 | 帧环与 fence 专项通过前保持当前同步，不用猜测删等待 |
| 超预算 | 报出阶段、资源、尺寸、当前/峰值预算；可定义降级或预烘焙替代 | 不静默读取高清备份、不无限扩大缓存、不依赖模拟器额外内存 |

当前 64 MiB CDRAM 策略预留 16 MiB，应用显式块准入 48 MiB；32 MiB deferred 上限仍须同时受原生 headroom 约束。原生显式块账本不覆盖全部 GXM 隐式分配、Rust 堆或宿主内存。MAIN、CDRAM、音频、电影和临时 CPU 像素各自记录，不把一种池的空闲抵扣另一种池。

## 6. 本轮验证及实机验收

本轮 `knife-render` host 单元测试 **52/52 通过**，其中新增五项：有余量时不扫描候选且只排序缺失项；最终编码器引用释放前驻留计数不归零；GXT/Alter 失败不登记为已驻留；缺失图集准入可以先回收空闲 CG 而不重解码/提交部分游戏绘制；完整帧 pin 和原生上传失败不重试。证据：[渲染日志（原证据目录 .work 已清理）。另有 [图片缓存/预取 14/14（原证据目录 .work 已清理） 和 [资源、输入、保存及证据工具 55/55（原证据目录 .work 已清理） 通过。这些测试检查算法和所有权边界，不是 ARM CPU/GPU 计时。完整 host 游戏检查仍受本机 GStreamer 开发包缺失限制，完整 ARM 游戏交叉构建已单独执行。

ARM `armv7-sony-vita-newlibeabihf`、`vita-gxm` 开发包构建及 SFO/VPK 审计通过。有限帧上限 7,200；包内为 8 个引擎条目，assets 外置。当前 [DEV VPK（原证据目录 .work 已清理） 为 **2,534,960 B**，SHA-256 `d944b79a8f525ce418f2c7ee0f32c3a421bdb51723c01d9b103fb1d027b4d072`。两次运行均绑定这一份包。证据：[构建收据](../vita-game-build.json)、[构建日志（原证据目录 .work 已清理）。这是有限运行 DEV 包，不能称为已完成的正式移植。

| 同包有限运行 | 客体与实际输入 | 原生显式块 | 宿主及最终判定 |
| --- | --- | --- | --- |
| [保存/读档冻结（原证据目录 .work 已清理） | 12 次真实控制器输入；空槽 0 保存，pc50→56→50，文字页/揭示计数恢复；保存与恢复的 4,175,872 B 文件 SHA 一致；7,200 帧 `RESULT PASS` | CDRAM 105/105、非 CDRAM 14/14，结束均归零；CDRAM 峰值 48 MiB | 客体自然停止，观察到 stopped 为 7 ms；宿主 `0xC0000374`，`runtime_verified=false` |

[结构化记录](../vita-artemis-performance-review.json) 由 [离线汇总工具](../../tools/summarize-vita-artemis-performance.py) 校验官方输入、13 份选定分析、测试日志、当前构建和两份冻结中的每个文件大小/SHA 后生成。冻结保存的是选定源码及产物身份，不是完整源码到二进制构建认证。使用独立内存计数诊断模拟器副本，原版模拟器未替换；本轮英语路线有状态证据，澄空路线未据此声称通过。

**实机尚未验证。** 接入 Vita 后按下列门槛验收；数字为设计目标，不是本轮已经测得的结果：
