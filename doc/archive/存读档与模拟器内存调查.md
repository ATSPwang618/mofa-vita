## 2. 保存、推进和恢复的证据

验证器发送并核对 12 次真实控制器按下/释放；由客体 `INPUT` 和后续 `STATE` 记录证明游戏实际收到输入，不能仅用桥接返回成功代替结果。

| 步骤 | 实际结果 |
| --- | --- |
| Triangle → Cross → Cross → Cross | 从 scene 1 pc50 打开菜单，进入空槽 0，确认保存；手动槽数量从 0 变成 1 |
| Circle → Circle | 关闭存档界面及菜单，回到 pc50，文字页为 1 条消息、59 字符 |
| Cross | 剧情实际推进到 pc56，文字页为 2 条消息、143 字符 |
| Triangle → Down → Cross → Cross → Cross | 选择读档、确认槽 0，恢复至 pc50；1 条消息、59 字符及揭示计数恢复 |
| 继续有限运行 | 恢复状态维持到客体完成 7,200 帧，输出 `RESULT PASS`；停止观察在 6 ms 内确认 stopped |

推进前后 replay point 都可能保持 scene 1 pc49，旧验证器仅比较这个点会误判“剧情没有推进”。现在分别核对实际 scene/pc 的变化，以及读档后的 scene/pc、文字页计数和 replay point；恢复记录出现在第 2,400 帧。

保存和恢复时各保留一份实际 `savedata000.bin`，大小均为 **4,175,872 B**，完整 SHA-256 均为 `0e45d6d6225e6ddc6ec2d1c3b5319842f74001376e9e2e8209dd4f8208206ef6`。槽 0 的记录哈希亦相同，magic=1000、used=1、scene=1、script offset=841、next=860，仅手动槽 0 被使用。全部字节及解析结果保留在运行收据和冻结中。

这证明所测槽位、选定状态和文件的恢复；没有比较完整文字内容、音频状态或 CG 像素。尚未覆盖覆盖保存、取消、多槽、重启应用后读档、分支及全章节。主机存档故障注入的 41 项历史测试也不能当作真机断电验证。

## 3. 显存改动和真实峰值

本轮没有提高显存预算，也没有移除帧内引用保护、Alter 上传峰值准入或 GPU 完成后回收规则。根据此前明确的准入失败，改了两处 Vita 资源生命周期：

- 菜单和存档界面的两张绘制目标交给 `WUi` 共用，两个界面在现有状态机中互斥绘制。相对各自保留一对目标，减少 **4 MiB** 常驻目标；目标仍由帧命令保持到 GPU 使用结束。
- 普通 Witch 菜单模糊使用 `menu_quarter`；通用 `blur_rt` 改为在 ghost、choice 或 legacy defocus 首次使用时创建，所测流程减少 **2 MiB** 闲置目标。相关三个借用位置已适配；桌面 cfg 维持原来的字段与创建方式。

合计是本条流程中 **6 MiB 的常驻目标节省**，不是整个游戏运行峰值下降 6 MiB 的测量。首次使用其他效果仍需分配 `blur_rt`，要另行覆盖。

| 本轮显式原生块账本 | 分配 | 释放 | 峰值 | 结束存活 |
| --- | ---: | ---: | ---: | ---: |
| CDRAM | 103 | 103 | 50,331,648 B / 48 MiB | 0 |
| 非 CDRAM | 14 | 14 | 8,212,480 B | 0 |
| 合计 | 117 | 117 | 两池峰值不可直接当作同一时点进程峰值 | 0 |

账本只覆盖显式记录的原生块，不包含全部 GXM 隐式分配、Rust 堆及宿主堆。应用仍保留 64 MiB 策略中的 16 MiB 余量；模拟器报告的空闲池不用于放宽这个策略。当前峰值仍达到 48 MiB 准入预算，不意味着后续所有场景都有余量。

失败历史保留，便于定位改动实际解决的边界：

| 历史快照 | 失败边界 | 本轮范围 |
| --- | --- | --- |
| [首次保存（原证据目录 .work 已清理） | `kusa` 上传峰值 1 MiB，余量仅 0.75 MiB，尚未写出存档 | 本轮该保存步骤通过 |
| [共用目标、旧验证器（原证据目录 .work 已清理） | 已写出存档；验证器未识别 pc50→56；稍后 backlog 目标准入失败 | 推进判断已改；backlog 失败仍是单独未完成项 |
| [读档对话框失败（原证据目录 .work 已清理） | `dialog_win` 上传峰值 2.5 MiB，大于当时 2 MiB 余量 | 通用 blur 按需创建后，读档对话框及恢复通过 |

本轮资源日志为 **IMG1227 DXT1 上传 1 次，menu_btn_en DXT5 上传 2 次**；均记录 `runtime_decode=false`、`runtime_alter=false`。之前另一个 3,600 帧 CG 场景记录了 IMG1227 三次上传，见 [该次冻结（原证据目录 .work 已清理），不能把不同运行的次数混写。

## 4. 模拟器内存计数与退出异常

原始模拟器的 SDK 探针实际分配后，释放 USER_RW、CDRAM、PHYCONT 三类块均只把空闲计数加回 **24 B**。两个 round 共六次相同；不是从游戏缓存日志推断出的泄漏。对应 fork 提交及 `ksceKernelFreeMemBlock` 代码显示，计数使用记录结构大小而不是 `mappedSize`，参考源码身份及指令证据见 [诊断清单（原证据目录 .work 已清理）。

本机创建了哈希锁定的独立 PE 诊断副本，改动上述普通释放函数的计数；这是局部字节补丁，**不是完整重编译的上游模拟器**。原路径 `${EMULATOR_ROOT}/Vita3K.exe` 仍保持 SHA-256 `8262786a3ea8007a3addb7b38e1e9863a7fa9299a862c30505ec41d750eeb242`；诊断副本 SHA-256 为 `901f6572fed58ee107750285eaaf3ae57392e48d000fca5bfafc8b95db5dad26`。`FreeMemBlockForVM` 未改、未验。

| SDK 池 | 每次分配 | 原版释放回收 | 诊断副本释放回收 | 实际 round |
| --- | ---: | ---: | ---: | ---: |
| USER_RW | 65,536 B | 24 B | 65,536 B | 2 |
| CDRAM | 1,048,576 B | 24 B | 1,048,576 B | 2 |
| PHYCONT | 65,536 B | 24 B | 65,536 B | 2 |

诊断副本的六次实际 SDK 分配/释放均恢复到操作前的三个池计数；合成原生指令 1,360 例及 2 项哈希锁负例另计。见 [实际 SDK 收据](../vita-platform-runtime.json) 和 [冻结（原证据目录 .work 已清理）。诊断清单中“完整 SDK 运行仍待执行”是生成时的历史限制，后续结果由这个独立收据补充；不回写旧清单。

`0xC0000374` 没有随计数修正消失。已在**原版字节、没有加载客体和素材**的独立空闲进程关闭中复现同码，见 [空闲对照收据（原证据目录 .work 已清理）。首轮及二次异常均保留转储，栈包含 Qt GUI 销毁路径；另有空闲运行正常退出，说明它并非每次必现。

因此可以确认这个宿主关闭问题也会在没有本游戏的情况下出现；仍未定位最早的破坏堆写入，不能直接认定 Qt、游戏某个析构函数或 GXM 为根因。本轮宿主实际退出 3221226356，完整验证器保持失败，不能用 guest PASS 或块账本归零覆盖该状态。

## 6. 复现入口

使用本机已验证 Python、Node、WSL 和 SDK。原版模拟器未替换；以下显式选用已存在、哈希锁定的诊断副本。验证器为每轮创建新的 DEV profile，不覆盖已有实验素材。

```powershell
wsl -d ${WSL_DISTRO} -- env KNIFE_VITA_DEV_MAX_FRAMES=7200 bash ${PROJECT_ROOT}/tools/build-vita.sh game
$env:KNIFE_VITA3K = '${PROJECT_ROOT}/.work/vita/emulator-memory-fixed/Vita3K.exe'
$env:KNIFE_VITA3K_DEBUGGER = '${PROJECT_ROOT}/.work/vita/debugger/vita3k-owned-debugger.exe'

```

上述命令重新构建和运行的是当前工作区，不会复现旧 VPK 的完整字节身份。当前保存/恢复仍可取得所测客体状态证据，宿主退出检查失败时保持非零退出。历史 `.work/vita/debugger/summarize-memory-save.py` 带旧 VPK 断言，不能拿最新可变构建路径重跑并冒充旧快照；保留的旧汇总及冻结继续作为历史证据。

最新两次冻结可以直接执行下列离线工具校验，它不运行游戏、不改写旧运行判定：
