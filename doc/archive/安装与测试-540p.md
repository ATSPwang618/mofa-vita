## 安装

1. 安装 VPK（与 270p 互不影响）。
2. 把 `dist/Witch-on-the-Holy-Night-Chengkong-540p-Vita/assets/` **整个目录**复制到 `ux0:data/knife-woh-540p/assets/`。
   - **9,565 个文件 / 3,292,065,952 B（约 3.07 GiB）**——比纯 PNG/JPEG 包（3.99 GiB）小 23%。
   - 少文件会在启动时报 `ASSETS REQUIRED` 并列出缺失路径。
3. 数据根、存档根、性能日志根都独立（`ux0:data/knife-woh-540p`），与 270p 存档不互通。

## 运行频率

启动时会把 ARM/BUS/GPU 提到 444/222/222 MHz，并把实测值写进日志头：

```
"arm_mhz":444,"bus_mhz":222,"gpu_mhz":222,"clock_rc":[0,0,0,0]
```

`clock_rc` 是 arm/bus/gpu/xbar 四个设置调用的返回值：0 表示接受，负数表示被系统拒绝。

此前整个移植从未改过频率，GPU 一直在 111 MHz 默认值上跑——这是每个 pass 12–20 ms 的主要原因。

## 文字清晰度下限

画布分辨率**不再下调**。720x405 是已确认可接受的下限（960x540 原生文字更清晰但慢 1.5 倍）。
后续所有优化（图集化、zero-uniform）都不得降低画布分辨率。

## 这一版做了什么

**画质与分辨率**
- 场景/特效链 480×270 → **960×540**，合成画布 960×540，扫描 960×544（上下各 2 px 黑边，不拉伸）。
- 素材原生 960×540（34,847 纹理 / 5,523,783,012 像素），不再放大。

**纹理：全量预压缩（本轮主体）**
- 新增 `tools/pack_dxt_540.py`：逐条读出 KIMG → 应用默认 Alter 烘焙 → DXT1（全不透明）/DXT5（含 alpha）→ `psp2gxt` 封成 GXT → 写回归档；每条都经 `validate_gxt` 按运行时解析规则校验。
- 结果：**23,054 张 GXT（66.2%）**；**12,671 张保留原 PNG/JPEG**（见下，这是修正后的正确取舍）。
- 归档体积：jallpac 1,775 → 814 MB、jallpachd 1,560 → 792 MB、allui 71.8 → 22.8 MB，全包 3.99 → **2.25 GiB**。
- 显存：满屏图 RGBA8 2 MiB → DXT1 512 KiB / DXT5 1 MiB；GXT 条目**不再经过 PNG/JPEG 解码，也不再跑 GPU Alter pass**。
- 转换条目用 NX(zlib) 包一层（DXT 可压 1.9–2.2×）；运行时只多一次 inflate，省下的是卡 I/O。

**扩展内存与堆（本轮新增，直接生效）**
- `param.sfo` 的 `ATTRIBUTE2` 从 0 改为 **12（0x0C）**：这是 VitaSDK `vita-mksfoex` 的默认档（+109 MiB 应用内存），此前被 `-d ATTRIBUTE2=0` 显式关掉。生效要求在**安装态**，FTP 热换 SFO 无效。
- 修掉一个真实缺陷（F1）：`platform.c` 的 `_newlib_heap_size_user / sceLibcHeapSize / sceUserMainThreadStackSize / sceUserMainThreadPriority` 之前**没有被链接进镜像**（ELF 里是 weak UNDEF，被 `--gc-sections` 丢弃），等于「堆 64 MiB」从来没生效过。现在四个符号都在 `.data`（已用 `arm-vita-eabi-nm` 核对），并把 newlib 堆提到 **96 MiB**、主线程栈 2 MiB。
- 日志头部新增运行时读数 `newlib_heap_bytes / libc_heap_bytes / main_stack_bytes / main_priority`：如果哪天又被丢，日志里会直接是 0，不用再猜。

**三段计时（本轮新增）**
性能日志把原来混在一起的时间拆开，全部以 CPU 观测为准：

| 阶段 | 字段 | 口径 |
|---|---|---|
| 卡读取 | card_read_us / card_read_calls / card_read_bytes / max_card_read_us | 只包 seek + read_exact，**不含** NX 解压与解码 |
| 内存处理 | nx_inflate_us / nx_inflate_calls | NX(zlib) 解压单独计时 |
| GPU 上传 | deferred_items / deferred_item_us / deferred_upload_us / deferred_bake_us | 预烘焙 GXT 的「注册句柄」与真实创建分开；RGBA 的 Alter bake 单列一段 |
| 同步等待 | gpu_finish_us / gpu_end_scene_us / gpu_display_finish_us / gpu_target_create_us | **CPU 被阻塞的时间**，不是 GPU 执行时间 |

read-vita-performance.py 的摘要新增 stages 块，直接输出这些毫秒数。

**日志与字体（本轮新增）**
- 性能日志升到 schema 2：头部新增 `title_id`，采样行新增 `gxt_images` / `decoded_images`——用来证明运行时确实走了预烘焙路径，而不是偷偷解码。
- 帧时间直方图在 12–16.67 ms 之间补成 1 ms 步长（原先是 4.67 ms 一个桶，无法判断离 16.67 ms 预算有多近）。
- zc 消息字体补 fallback：Chengkong 目录只有一个 OTF，超出它的汉字原先落到 `.notdef`；现在回退到菜单已在用的系统字体（字形会变字体，但不再缺字）。

**运行时修正**
- `PREFETCH_RGBA_CAP` 1→3 MiB、`PREFETCH_ENCODED_CAP` 2→4 MiB。
- 预取闸门不再用“像素×4”误伤 GXT：预烘焙条目本来就不产生 RGBA 缓冲，原逻辑会把 960×540 的每一张 GXT 都排除在预取之外。
- 540p 变体独立数据根/存档根/性能日志根/启动提示/标题 ID。

## 保留 PNG/JPEG 的 12,671 条（不是遗漏，是硬约束）

| 类别 | 数量 | 原因 |
|---|---:|---|
| **会被调色的图（4,164 个名字）** | 约 12,400 | 场景脚本对它们用 `_STEC`/`_SNX2`/`_SNX3`；codec8 只存默认烘焙色，命中调色会**直接报错而不是回退**。扫描见 `.work/graded-images.txt`（249 个场景） |
| 双语语言条带 | 160 | 运行时在 CPU 上按语言切行；codec8 命中条带会**直接报错而不是回退** |
| codec7 灰度/遮罩 | 29 | unorm 语义，codec8 恒 sRGB 无法表达（含 RULE 转场遮罩） |
| BORDER_PARTS 图集成员 | 12 | 软裁剪 LUT 要读它的像素 |
| 占位/空条目 | 约 50 | 2×2 占位与 NOFILE.EXISTS，转与不转等价 |

## 关于 PVRTC

工具链具备（`PVRTexTool.exe` 可编 PVRTC 2bpp/4bpp，`psp2pvrt`/`psp2gxt` 可封装），但这版**没用**，原因：
1. 现有 GXT 解析与 C 上传只认 PVRTC4/DXT1/DXT5，PVRTC 2bpp 需要扩解析器与上传白名单；
2. PVRTC 要求正方 2 的幂，960×540 必须填到 1024×1024，填充边缘会在缩放时引入色边；
3. DXT 这版已经把包压到 57%、显存降 2–4×，PVRTC2 的额外收益（再省一半显存/体积）要拿 UI 与文字边缘的画质去换。
需要时可以按“仅全屏 CG 用 PVRTC2、UI 保持 DXT5”做第二批。

## 仍未做

- `ATTRIBUTE2` 仍为 0（扩展内存 A/B 未做）；newlib 堆实际大小未测。
- 字体只做了 fallback；atlas 共享（3 个实例里 2 个重复）与页 LRU 仍未做。
- T4 直读 CDRAM（跳过 NX 解压后的 memcpy）未做：收益是每张省一次 0.5–1 MiB 拷贝，但要把 zlib 解压目标搬进 CDRAM，风险高于本轮收益，留到有实机基线之后。
- 60 FPS 未做（`sceGxmFinish` 收敛、三阶段计时字段都还在计划里 T5–T8）。
