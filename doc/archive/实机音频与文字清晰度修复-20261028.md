# PS Vita 实机音频与文字清晰度修复 · 2026-10-28

用户报告上一版在实体 Vita 上可正常运行，但大量轻微爆音，剧情文字、UI 和部分 RGBA8 图像模糊，放在数据包内的性能开关没有生成日志。本次完成有界音频输出修复、270p 场景与 540p 文字/UI 分层、两页字形缓存和双路径日志开关，并重建 ARM 发布 VPK。实机听音与画面复测尚未完成。

## 爆音的已确认问题与诊断边界

旧 AudioOut 工作线程提交临时 PCM 后，可能在驱动仍持有指针时回收缓冲区。测试 mock 故意把输入指针保留到后续输出/drain/release，以 ASan 复现旧实现的释放后访问，新实现通过同一受控测试。这个缺陷应修复，但用户设备上的所有爆音是否同源，仍须实测。

新实现：

- 48 kHz、双声道 S16，每块 960 采样帧即 20 ms；六个持久块组成 PCM 池，输出队列最多四块，即 80 ms 容量。23,040 字节 PCM 池和 7,680 字节欠载过渡缓冲只分配一次。
- 队列满先返回，不重复分配或复制整块 PCM；阻塞 AudioOut 在独立输出线程执行。
- 当前与上一已提交块保留所有权，后续阻塞输出完成后再复用，退出先排空、释放端口。驱动错误时保留仍可能被访问的数据；两种关闭操作持续失败时使用有界保留，避免悬空指针。
- 启动与欠载恢复预备两块，最长等待 40 ms；欠载两侧用 128 采样帧、约 2.67 ms 的短过渡减小突变。它不等于所有声源开始/结束都加淡入淡出。
- 保留原混音增益及硬裁切行为；新增计数，先区分真实供音不足和峰值裁切。

音频队列容量不等于精确端到端延迟。增加缓冲可承受短抖动，但持续的慢解码仍须针对日志修复。

## 文字/UI 清晰度

之前即使字体以 RGBA8/R8 表示，最终所有内容仍进入 480×270 画布再拉伸，文字细节在合成阶段已丢失。RGBA8 只描述每像素颜色存储。

现在绘制顺序是：270p 场景和特效 → 放大到 960×540 合成画布 → 绘制文字/UI → 960×544 屏幕居中呈现。文本布局和脚本坐标保留；字形无需先进入 270p 场景目标。

每个字体 atlas 保留当前及上一张 1024×1024 R8 页，命中字形复用其原页纹理。绘制队列持有具体页的 TexRef，换页不会覆盖队列中尚未提交的字形。缓存本身最多持有两页、共 2 MiB；不同字体有各自 atlas，排队或 GPU 使用中的旧页可能短暂存活，不能把两页当成所有字体分配的绝对峰值。

从保留的 540p 基线重新生成 238 张欠采样 UI 图；其余 805 张小 UI 保留原编码。没有改变 PNG/JPEG/灰度 PNG、语言标签、逻辑裁切或条目顺序。PNG 在预乘 alpha 下重采样，防止透明边缘混色。新 UI 归档及全局清单成套更新，增加约 14.15 MiB。剧情背景/立绘保持 270p，其原有模糊属于已选择的分辨率限制。

540p 合成目标按平台对齐占 2 MiB，比旧 270p 目标多 1.5 MiB；按需冻结画布同样增加 1.5 MiB。场景特效仍走 270p。CDRAM、MAIN 和堆预算保持原值，因此需实机确认新工作集及多菜单切换。

## DXT 与多级缓存的实际状态

codec8 GXT 路径把已有 DXT/PVRTC 压缩数据直接交给 GXM，未统一拆成 ARGB。当前交付的数据统计为 31,338 PNG、3,480 JPEG、29 灰度 PNG，**不是 DXT 生产图包**。这些资源先解码为 RGBA，再由主线程创建 RGBA8 纹理；PNG 的调色板/透明表会按实际颜色正确展开。

| 层级 | 当前实现与上限 |
|---|---|
| 文件/归档 | 持久句柄及 HED/MRG/KATL 索引，按范围读取；不把整套归档装入内存；操作系统页缓存不由游戏精确控制 |
| 编码资源 | 现有延迟资源编码缓存策略 32 MiB；不是一个覆盖所有文件读取的独立大缓存 |
| 后台图片 | 一个工作线程，8 等待、2 已解码、最多 1 同时解码；预取窗口最多 32 项 |
| 推测加载 | 单项编码不超过 2 MiB、RGBA 不超过 1 MiB；每帧最多主动上传一个预取结果 |
| GPU 纹理 | 现有驻留策略 32 MiB，受原生池准入约束；帧内使用的资源保活，压力下回收空闲缓存 |
| 呈现 | 双显示缓冲、最多一个 pending；场景/合成/按需冻结目标分别承担明确用途 |
| 字体 | 每个 atlas 缓存当前和上一页；已排队页独立保活 |
| 音频 | 持久 PCM 池、四块输出队列、独立混音/输出线程 |

额外堆叠全屏帧缓冲会消耗有限 CDRAM，无法代替下一张动画图片的读取、解码和上传。当前保持双显示缓冲，主要通过有界预取及纹理复用覆盖短抖动。仍未命中的前台请求可能等待。

CDRAM 策略总额 64 MiB，分为参数预留 16 MiB、JPEG 工作预留 3 MiB、GXM 显式映射预算 45 MiB；映射 MAIN 16 MiB。现有 32 MiB 缓存是策略上限，不能与映射预算直接相加当成独立可用显存。性能日志也不覆盖整个 Rust/newlib/codec 堆或全部系统分配。

## perf-enable.txt 为什么没产生日志

提供的 `${CAPTURE_ROOT}/perf-enable.txt` 是单字节 ASCII `1`，文件内容有效。此前只读取 data 根目录；用户称放在实机数据包内，若实际位于 assets 目录，就不会命中旧版开关。没有取得实机文件树，不能断言这是设备上的唯一原因。

新版本依次读取以下位置，首个存在的文件决定结果：

1. `ux0:data/knife-woh/perf-enable.txt`
2. `ux0:data/knife-woh/assets/perf-enable.txt`

允许 ASCII/UTF-8、UTF-8 BOM、首尾空白，trim 后须为 `1`，最多 512 字节；UTF-16 不支持。根目录 `0` 或无效内容会关闭，不再尝试 assets。修改后要重启应用。

日志写在 **`ux0:data/knife-woh/performance.log`**，不是 assets 里。启动时在资源/GXM 初始化之前创建并写/flush 头；之后每约 5 秒写一条汇总，总计最多 256 KiB，达到上限后停止记录。每次启动重建，测完先复制回 PC。头内应包含 profile `270p-scene-540p-ui-audio-pool-v1`、scene_size [480,270]、composite_size [960,540]。

没有头时先核对是否安装当前 VPK、文件路径/扩展名、根目录优先开关及目标目录写入是否成功。启动头写入改善可观测性，但不把任意掉电情况下文件持久化作为保证。

## 新日志怎么定位爆音

| 字段 | 含义 |
|---|---|
| audio_underruns | 活动流没有就绪 PCM 的欠载次数；与正常空闲静音分开 |
| audio_mix_late | 混音一块（含其解码）超过 20 ms 的次数 |
| audio_mix_max_us | 已观察到的混音单块最长耗时，累计最大值 |
| audio_clipped_samples | 混音幅值超过允许范围的有限样本数；增益/裁切策略未改 |
| audio_queue_full | 生产者遇到队列满的次数，重试也计数；不是直接的播放欠载证据 |
| audio_peak_queued | 排队块数累计最大值，应不超过 4 |
| worker、demand、upload 及 GXM/JPEG 内存字段 | 同期图片等待和已跟踪工作集；不是独立 GPU 时间或整个进程内存 |

音频计数是异步读取的累计 u32，可能回绕；工具已兼容回绕、重置及缺字段旧日志。`audio_underruns` 增长先看供音/调度；`audio_mix_late` 同步增长则关注混音与解码预算；只有 clipping 增长时才有证据再评估混音余量。多个问题可同时出现，不能只凭一项计数证明听感原因。

使用相同设备时钟、存储介质、音量和存档位置，复测同段配音/BGM、连续转场、菜单/回看开关和视频返回，并检查文字、透明边缘与条带颜色。记录设备/时钟/剧情位置，复制 performance.log 后运行：

```powershell
python -X utf8 tools/read-vita-performance.py '${CAPTURE_ROOT}/performance.log' --environment hardware --out '${CAPTURE_ROOT}/summary.json'
```
