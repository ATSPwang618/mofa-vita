# PS Vita 图片、帧动画加载与实机测试

更新：2026-10-28。当前 knife 0.9.4 本地修改版直接调用 GXM。剧情图片/场景特效为 480×270 档，放大到 960×540 合成画布后绘制文字/UI，再居中显示到 960×544。最新音频、字形/UI 与性能日志变更见 [专门记录](../03-交付与实机/实机音频与文字清晰度修复-20261028.md)。

## 图片格式和解码

| 资源 | 当前路径 | 边界 |
|---|---|---|
| JPEG | 优先 SceJpeg Codec Engine，回退有界 libjpeg-turbo | baseline 8-bit YCbCr 4:2:0/4:2:2，宽 64..480、高 64..540、编码 ≤512 KiB |
| PNG/灰度 PNG | 有界 libpng | 保留 PLTE/tRNS、Adam7、灰度和 alpha；调色板索引按颜色表展开 |
| 已预烘焙 codec8 GXT | 保留压缩 GPU 内容，直接 GXM | 当前生产资源未批量转成 DXT；CPU grade/raw/条带仍有用途限制 |

SceJpeg 路径为 GetOutputInfo → DecodeMJpegYCbCr → MJpegCsc，独立对齐 Y/色度 pitch，按真实宽高裁切到拥有独立生命周期的 RGBA，随后主线程上传 GXM；它不是零复制。忙碌、格式、预算、初始化、分配、驱动及输出契约拒绝分别计数，失败不静默扩大内存。

公开 [libvita2d_sys JPEG 实现](https://github.com/GrapheneCt/libvita2d_sys/blob/master/libvita2d_sys/source/vita2d_image_jpeg.c) 提供相关接口参考。该库 [PNG 实现](https://github.com/GrapheneCt/libvita2d_sys/blob/master/libvita2d_sys/source/vita2d_image_png.c) 使用系统接口，但系统入口并不证明存在 PNG 专用硬件解码单元；本机公开 VitaSDK 没有可直接链接的 ScePng stub/header，当前 PNG 仍使用 libpng。

当前资源为 31,338 PNG、3,480 JPEG 和 29 灰度 PNG，共 34,847 张。离线 JPEG 头准入审计与当前资源清单绑定，详见 vita-270p-jpeg-admission.json；准入候选数不代表这些图已在实体设备全部解码成功。238 张 UI 从原始基线恢复到 540p 档，805 张小 UI 原样保留，剧情图片仍为 270p。

## 连续归档、有界预取和缓存

HED/MRG 已提供连续归档与偏移索引，KATL 中的多图按范围定位，复用文件句柄；没有重新发明另一种 MJA 容器。后台一次只解码 1 张，固定 1 个图片线程、512 KiB 栈，等待请求最多 8、完成结果最多 2，预取窗口最多 32。

motion 预测后续 2 个 variant，动画候选最多 8 项，另检查后续最多 24 个 STCH/SCH2 引用；不推进脚本时钟或执行副作用。窗口/语言变化丢弃旧结果，前台可复用同一在途任务。单项推测编码 ≤2 MiB、RGBA ≤1 MiB，每帧最多主动上传 1 个预取结果。前台未命中仍可能等待读取/解码。

延迟纹理编码缓存及 GPU 驻留策略各 32 MiB，实际受原生池准入约束。纹理按帧所有权保活，压力时回收空闲项，避免每帧全量 LRU 遍历。后台结果不携带 GXM 指针，创建/上传纹理仍在主线程。两页字形缓存减少邻近页面文字重复光栅化；排队纹理持有独立所有权。

显示使用 2 个缓冲区、最多 1 个 pending。增加全屏帧缓冲消耗 CDRAM，不能替代动画帧读取、解码和纹理复用；当前没有无上限增加帧缓存。

## 工作集边界

| 项目 | 预算/大小 |
|---|---:|
| CDRAM 策略总额 | 64 MiB |
| GXM 参数预留 / JPEG 临时预留 / GXM 显式映射 | 16 / 3 / 45 MiB |
| 映射 MAIN | 16 MiB |
| newlib / sceLibcHeapSize / 主线程栈 | 64 / 4 / 2 MiB |
| 270p 场景 / 540p 合成 RGBA8 目标，含对齐 | 512 KiB / 2 MiB |
| PCM 池 / 欠载过渡缓冲 | 23,040 / 7,680 字节 |
| 每个字体 atlas 缓存页 | 最多 2 张 1024² R8，2 MiB；在途旧页可短暂保活 |

JPEG 工作块按 256 KiB 原生粒度分配，退出释放；包含最终 RGBA 的路径另受 4.25 MiB 工作量上限约束。Codec Engine 用非阻塞锁串行；忙碌时可软件回退。日志中的 GXM/JPEG 分配不覆盖普通 Rust/newlib/codec 堆、栈、音频和全部系统内存，不能当作全进程峰值。

## 实机测量入口

当前更新需要新 VPK 与 allui.mrg、allui.hed、allui.270p.json、vita-270p-assets.json 四件套；完整首次安装见运行目录 README。保留 saves，退出游戏后覆盖。

在 `ux0:data/knife-woh/perf-enable.txt` 或 assets 内同名文件写 UTF-8/ASCII `1` 并重启。根目录优先；根目录 0/无效内容不会由 assets 覆盖。支持 UTF-8 BOM 和首尾空白，不支持 UTF-16，最多 512 字节。日志写到 `ux0:data/knife-woh/performance.log`：启动立即写头，每约 5 秒汇总，最多 256 KiB，每次启动重建。新 profile 为 270p-scene-540p-ui-audio-pool-v1。

用相同设备时钟、存储和存档位置，对照冷启动、5 分钟配音/BGM、重复菜单/回看/存读档、连续帧动画、透明立绘、语言条带和 3 个 MP4 返回。记录听感、文字边缘和实际剧情位置，复制日志回 PC 后运行：

```powershell
python -X utf8 tools/read-vita-performance.py 'D:/Vita-test/performance.log' --environment hardware --out 'D:/Vita-test/summary.json'
```

jpeg_hw_ok/fallback 区分硬解候选成功和回退，最后驱动错误/pitch 契约字段协助定位；pending/ready/active 上限 8/2/1。音频 underruns 是活动供音欠载，mix_late 是混音含解码超过 20 ms，clipped_samples 是幅值裁切候选，queue_full 可能只是正常生产者等待。

work 排除主动限帧等待；render 是 CPU 提交及相关等待，不是独立 GPU 时间；worker 包括读取与解码。p95 是各窗口直方图上界，不能当成全局精确百分位。新实现还没有对应实机性能日志，不能承诺固定帧率或全游戏永不 OOM。若确认 PNG/回退 JPEG 是实机瓶颈，再针对明确用途比较 DXT1/DXT5 和必要无损纹理，保留字体、遮罩、调色板及精细 alpha 的颜色语义。
