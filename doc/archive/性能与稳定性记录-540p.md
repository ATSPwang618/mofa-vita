# 540p 实机性能与稳定性记录（2026-10-29）

> 原 `性能分析-20261028.md` 在整理中丢失，此文件为重建版，数据全部来自实机日志。

## 参考实现调研：Art3m1sPSV / art3m1s-core-psv

两个仓库的宿主与核心都读过（代码依据，非文档声明）：

1. **每帧一个 scene、一次 Finish**（`host-direct/README.zh-CN.md`）：960x544、三个 stride=1024 显示缓冲、无深度/MSAA。
2. **顶点流一次绑定**：索引表启动时生成，每次绘制只传 `indices + offset`（`gpu.cpp:240-256,1202-1210`）。
3. **同 context 内切 RT 不需要 Finish**：注释明确提交顺序已保序，只在 Begin/回读/更新/销毁 drain（`gpu.cpp:415-433`）。
4. **普通路径零 uniform**；9 族 x 11 混合在启动时 patch 一次（`gpu.cpp:280-335`）。
5. **alpha 证书**：上传时建 64x64 opacity tiles + alphaBounds，绘制时四角裁剪、全不透明白切 BLEND_NONE、被不透明全屏覆盖的批次直接丢弃（`gpu.cpp:738-792,1140-1200`）。
6. **中性组展平**：无 mask/滤镜/独立裁剪的组直接画进父 target，不占离屏；每帧上报 total/flattened（core-psv `native_effects.rs`）。
7. **脏帧复用**：仅在 visual_dirty / 纹理 revision 变化 / 转场时重建 DrawList，其余复用；DrawList 四缓冲原地复用（core-psv `render_gxm.rs`）。
8. **压缩纹理直通 + POT 计费 + 稀疏上传**；CDRAM 32MiB 池，失败 defer 下帧重试而非崩溃。

## 绘制/纹理比（r39 实测）

`quads/draw = 0.90`，重场景 42–52 个四边形对应 44–62 次绘制 —— **几乎一四边形一次绘制**。
合批条件（同纹理/同状态）基本一次都不满足，图集化确实能把绘制次数压下来，
但需要把图层纹理重新打包并改 UV 映射，是 2–3 天的活。

同时确认：重场景 141 ms 里 `present` 占 25 ms（显示队列等待）。

## r38 展平实测：画面错误，已关闭（r42）

实机反馈：祖父救猫的闪耀特效**露出了精灵矩形边框**。原因是展平时丢弃了 `Mask` 绘制，
而该组的发光本应由遮罩限制在形状内。r35 的组形状统计（2/2、3/2、5/1）表明**每一组都带遮罩**，
因此展平必然丢效果。r42 已把 `flatten_groups` 关闭，代价是重场景回到带遮罩的合成路径。

## r41 实测：零 uniform 收益有限

重场景 137–143 ms（展平后），`draw` 38–54、`pass` 20.8、`finish` 12 ms。
相比 r39 的 190–199 ms 主要来自展平；uniform 精简本身只贡献约 4 ms（每次绘制省 3–5 次驱动调用，
但每次调用的实际开销低于预估）。平均帧率 16.9 FPS、中位 49 ms。

## r50 实测：真凶是每 pass 的 Finish

重场景（PC 212，33 pass）：`begin_target` 65.2 ms（含 `finish` 68.7 ms）、`end_scene` 2.3 ms、
`draw_cpu` 0.0 ms、`draw_gxm` 0.2 ms、`clear` 0.1 ms。

即：**绘制提交几乎不花时间，成本是每个 pass 开头的 `sceGxmFinish`（约 2 ms × 33 ≈ 66 ms），
而 GPU 总工作只有 12 ms** —— 那 2 ms 是驱动的固定往返开销，不是等 GPU。

之前之所以每次 pass 都要 finish：顶点环在每个 pass 开头被重置，若 GPU 仍在读上一轮顶点就会画出垃圾。

## r54 实测：黑屏 —— 屏障与「每 pass 重置顶点环」冲突

跳过 77% 的 pass finish 后，画面在开头短暂显示后黑屏、部分区域残留图像。
根因：r52 回退时把顶点环恢复成「每个 pass 开头 `used = 0`」。一旦某个 pass 不再 finish，
下一个 pass 就会覆盖 GPU 仍在读取的顶点数据。

## r56 实测：仍黑屏，屏障方案终止（r57）

补上 WAR 依赖后仍然黑屏。三次尝试（r51 全去 Finish、r54 只按 RAW、r56 加 WAR）全部失败，
说明这套引擎与 GXM 之间还存在**未被我们建模的依赖**（可能是驱动内部对渲染目标重绑的要求，
或纹理线性/平铺转换的时机要求），在缺少官方文档与调试器的情况下无法安全推导。

**结论：每个 pass 的 `sceGxmFinish` 保留，屏障方案终止。**
r57 恢复「每 pass 必 Finish」，并保留 r53 的模拟统计（`pass_need`）作为记录，
方便将来有人拿到驱动文档时复用这份依赖模型。

## r56：补上 WAR 依赖

r55 仍黑屏，说明只建模 RAW（读后写）不够。组表面的使用顺序是
「合成 pass 采样像素面/遮罩面 → 下一组再写同一对表面」，这是 **WAR（写后读的反向）**：
必须等采样该纹理的在途 pass 完成，才能把它当渲染目标覆盖。

r56 的判据同时考虑：

- **RAW**：本 pass 采样的纹理，被本帧更早的 pass 写过；
- **WAR**：本 pass 的目标，被本帧更早的在途 pass 采样过。

任一成立即 Finish，并清空两个集合。

## r55：屏障 + 整帧顶点环

- 顶点环恢复整帧增长（present 时重置，present 自带 Finish）；
- 保留 r54 的按依赖 Finish；
- 顶点用满时先 `sceGxmFinish` 再重置（已有的兜底）。

## r54：按依赖决定是否 Finish（屏障系统）

编码阶段为每个 pass 计算 `need_finish`（它采样的纹理是否被本帧更早的 pass 写过），
执行时通过 `begin_target_flags` 传给后端；只有需要时才调用 `sceGxmFinish`。

这也解释了 r51 的黑屏：当时是**全部**跳过，包括那 23% 真正需要同步的 pass。

## r53：屏障依赖分析（离线模拟，不改行为）

在命令编码阶段对每帧的 pass 序列做模拟：

- 记录「本帧内哪些目标被写过」；
- 对每个 pass，检查它采样的纹理（`Draw.textures` 与 `Copy.src`）是否在集合里；
- 只有命中时才「需要 Finish」，并在需要时清空集合（Finish 会排空在途写入）。

输出 `pass_need` = `需要Finish的pass数:总pass数`（累计值）。
该比例即「屏障系统」的收益上限：若 33 个 pass 里只有 12 个需要 Finish，
重场景可省 21 × 约 2 ms ≈ 42 ms。

注意：本版仍保留每 pass 的 `sceGxmFinish`（r52 已回退），因此**画面正确**，仅多输出统计。

## r51 实测：部分场景黑屏，已回退（r52）

去掉每 pass 的 Finish 后，**部分场景黑屏**（其余正常）。证明存在至少一条「pass 写入的目标
在本帧内被采样」的依赖链，无法只靠提交顺序保证。

r52 已恢复每 pass 的 `sceGxmFinish`，画面恢复；顶点环重置也一并恢复。
结论：**每个 pass 约 2 ms 的 Finish 成本在这套「多目标 + 组表面」结构下不可省**，
除非能证明并消除所有同帧读改写依赖（需要对每个 pass 的目标/纹理依赖建模，属于重写渲染器）。

## r51：顶点环按帧增长，去掉每 pass Finish

- 顶点环 `effects->used` 不再在 `effect_scene` 重置，改为**整帧增长**，由呈现路径
  `kv_reset_effect_ring` 重置（呈现本身有 Finish，能保证上一帧的读取已结束）；
- 同 context 的提交顺序保证「先写的目标 → 后读的纹理」的次序，因此 pass 之间不需要 CPU 同步；
- 兜底：一帧内顶点用满 32760 个时，先 `sceGxmFinish` 再重置环，不会越界。

风险：若某些路径确实需要中间同步（例如 CPU 回读、纹理更新），可能黑屏或残影。

## r50：pass / 绘制提交的分段计时

此前「每 pass 约 2 ms」是按整帧时间推算的估算值。r50 在 C 侧分段实测：

| 计数 | 含义 |
|---|---|
| `begin_target_us/calls` | 整个 `kv_gxm_begin_target`（含 BeginScene、视口、清屏） |
| `clear_us` | 其中清屏四边形 |
| `draw_cpu_us` | 每个绘制的 CPU 部分（顶点拷贝 + 设置顶点流） |
| `draw_gxm_us` | `sceGxmDraw` 调用本身 |
| `draw_calls` | 绘制次数 |

加上既有的 `finish_us`、`end_scene_us`、`exec_us`、`present_us`，
即可把 190 ms 拆成「pass 开销 / 绘制 CPU / 提交调用 / GPU 等待 / 呈现」五段，而不是估算。

## r49 实测：中性组 0 命中

`layer_changes` 的第五个字段（中性组命中）在整段运行中为 **0**：
本作的遮罩都是真实的渐变/形状纹理，**不存在「纯白全屏遮罩」的组**。

因此「组合成重写」在这款游戏里能精确成立的情形并不存在：

| 方案 | 结论 |
|---|---|
| 中性组直接绘制（m≡1、α=1） | 命中 0 次 |
| 逐层乘遮罩 | 与整组合成**不等价**（r43 已实测失败，且有代数证明） |
| MRT 同时写像素面与遮罩面 | GXM 的 `sceGxmBeginScene` 只接受一个 color surface，**硬件不支持** |

要再降 pass，只能引入画面近似（例如把渐变遮罩近似成实心裁剪），这属于画质换帧率，
且已证明会在此前的尝试中出现明显错误（r38 露出精灵边框、r43 背景消失）。

## r49：组合成重写（第一刀：中性组）

先给出等价条件，再实现：

- 组内合成 `P = Σ Li·∏(1-aj)`（第 i 层被前面各层遮挡）；
- 组合成 `C = m·α·P`；
- 当 **m ≡ 1 且 α = 1** 时 `C = P`，而「各层依次 over 画进舞台」的结果恰好也是 P
  ⇒ **逐层直画与整组合成严格等价**。

这也解释了 r43 失败的原因：那里 m 是任意遮罩，逐层相乘得到
`Σ(Li·m)·∏(1-aj·m)`，与 `m·ΣLi·∏(1-aj)` 不等。

实现判据（全部满足才算中性，任一不满足走原路径）：

- 该组恰好 1 个遮罩四边形、无裁剪、颜色 alpha ≥ 1、混合为 Opaque；
- 该遮罩四边形使用引擎的 1×1 白色纹理、且覆盖整个画布；
- 组合成不透明度为 1，混合为 Alpha/Over。

命中时：图层直接进舞台，跳过像素面、遮罩面、合成三个 pass。
命中数记入 `layer_changes` 的第 5 个字段（`neutral`）。

## r48 实测：局部分段重画不值得做

3082 个有效帧：

| 分类 | 帧数 | 占比 |
|---|---:|---:|
| 无任何图层变化 | 2325 | **75%** |
| 只变 1 层 | 418 | 14% |
| 变 2 层以上 | 339 | 11%（其中 z 序连续仅 40%） |

- 75% 的帧已经被 r47 的整块复用覆盖；
- 剩下的 25% 里，一半是单层变化，另一半是多层变化且**只有 40% 连续**；
- 高动画面（PC 848）出现「每帧 40 个图层变化」的窗口，全部散布，无法分段。

结论：**分段缓存最多影响 25% 的帧、且其中半数无法分段**，预期整体收益 <10%，
却要改动合成结构并引入新的画面风险。**不做。**

重场景（PC 206–304）的 190 ms 来自「每帧几十个图层都在变」，这是动画本身的成本，
在现有合成模型下没有进一步空间。

## r48：逐图层变化分布（为「只重画变化部分」做判据）

舞台哈希只能回答「整块变没变」。要按用户提出的「只更新差值部分」思路优化，
需要知道**每帧有几个图层变了、变化的是否相邻**（相邻才能合成一段缓存）。

每帧对每个绘制条目单独哈希并与上一帧比较，统计：

- `frames`：有效帧数；
- `singles`：只有 1 个图层变化的帧数；
- `some`：2 个及以上变化的帧数；
- `contiguous`：其中变化图层在 z 序中**连续**的帧数。

判据：`singles` 占比高且 `contiguous` 占比高 → 可把静态部分切成 1–2 段缓存，
每帧只重画变化的段，重场景有希望从 190 ms 降到 60–80 ms。

## r47：舞台复用（跳过重复重画）

`render_stage` 在记录任何命令之前判断：绘制列表哈希与上一帧相同、`stage_dirty` 为假、
无 ghost、无转场、无噪声层时**直接返回**，复用上一帧的 stage 目标内容。

保留的部分：清屏由首帧绘制完成（跳过时内容本就在）、`stage→scene` 拷贝照常、
ghost/转场/文字/UI 全部照常绘制。因此只省掉约 40 次图层绘制与对应 pass。

重场景重复率为 0，因此不受影响；对白场景是主要受益者。

## r46：舞台复用可行性统计

`render_stage` 每帧无条件重画全部图层。为评估「舞台未变则复用上一帧」的收益，
每帧对舞台绘制列表做哈希（纹理指针 + 位置 + 颜色 + 合成透明度），
统计「与上一帧完全相同」的帧数，输出到采样行的 `stage_repeats`（`总帧:重复帧`）。

判据：重复率高 → 缓存舞台可直接省掉约 40 次图层绘制；重复率低 → 该场景确实每帧在动，
只能在合成与提交层继续优化。

## 图集化实测结论：不可行（r45）

106 秒、1383 帧的绘制分桶：

```
small(≤256²) 1807 (4%)   mid(≤512²) 465 (1%)   large(>512²) 38141 (94%)
quads 40490  draws 50165  quads/draw 0.81
```

**94% 的绘制来自大于 512×512 的纹理**（背景层就是 960×540，一张占满 1024×1024 图集页）。
把少量小图打进图集最多只能影响 5% 的绘制，**对绘制次数没有实质帮助**，因此不做图集化。

重场景的每帧绘制分布也一致（large 36–74 次，small/mid 各 0.2–1.6 次）。

## 图集化的几何约束（r45 测量准备）

背景层是 960x540，一张就占满 1024x1024 图集页，**无法与其它图共享**。
只有小图（立绘局部、表情、UI 部件）才可能进同一页。因此先按源纹理面积分桶统计每帧绘制：

- `quads_small`（≤256x256）
- `quads_mid`（≤512x512）
- `quads_large`（更大，基本是背景/整屏层）

判据：若 `quads_large` 占多数，图集化对绘制次数无帮助；若 `quads_small+mid` 占多数且相邻，
则值得把同场景的小图打进 1–2 张图集。

## r43 实测：画面错误，已关闭（r44）

实机截图显示背景大幅变黑，只剩一条与遮罩形状相同的竖条可见，文字与 UI 仍正常。

原因判断：把组的遮罩逐层乘到每个图层上，**与「先合成再整体乘遮罩」并不等价**。
原来的合成是对整组结果施加遮罩（`group_alpha(pixel, mask)` 作用在合成后的像素上），
而逐层相乘会让每个图层的 alpha 都被独立削减，背景层因此整片消失。

结论：这条路径在语义上就不成立（除非能拿到「组内已经合成完毕」的结果），已置 `mask_as_texture = false` 回退，
画面恢复为 r42 的状态。相关着色器入口保留但不启用。

## r43：遮罩作为纹理（替代合成 pass）

新增片元入口 `fs_sprite_mask`：把组的遮罩表面当 tex2 采样（画布空间 `pos.xy / params.zw`），
每层绘制时直接乘上遮罩 alpha，因此**不再需要像素表面与合成 pass**，每组 3 pass → 1 pass（仅遮罩）。

启用条件（保守）：

- 组的合成不透明度为 1 且混合为 `Alpha`/`Over`（其它混合的合成会对整组施加混合与透明度，不能逐层等价）；
- 该组所有层都没有 rule，且 `shade == Sprite`（遮罩路径会占用 rule 槽并固定用 sprite 着色器）。

其余组走原来的「像素面 + 遮罩面 + 合成」路径。着色器参数改用插值器（r41）后，
`fs_sprite_mask` 只剩 4 个参数。

## r41：几乎零 uniform

着色器改为从**插值器**读取每四边形常量（每个四边形的 6 个顶点值相同，插值结果即为原值）：

- `uQuadHx`/`uQuadHy` → `FragmentInput.hx/hy`（TEXCOORD2/3），仅 `fs_rim_text` 仍用 uniform
  （打包的 RGB24 必须精确，插值可能改掉最低位）；
- `uSoftLutSize` → 着色器常量 `float2(257, 18)`（软裁剪 LUT 尺寸固定）；
- 未被引用的 uniform 由编译器丢弃，C 侧查不到句柄即跳过设置，因此**无需改 C 代码**。

重新编译结果（`tools/compile-vita-effects.ps1`，16 个入口全部通过重复性校验）：

| 入口 | 参数个数（改前 → 改后） |
|---|---|
| fs_sprite | 6 → **2** |
| fs_text | 4 → **1** |
| fs_blur / fs_rule / fs_transition | 6 → **4** |
| fs_rim_text | 3（不变，保留精确打包色） |

## r40：三缓冲

参考实现用三个显示缓冲（960x544、stride 1024）。我们把 BUFFERS 从 2 改为 3，
多占约 2.2 MB CDRAM（当前余量充足），预期降低 `present` 里的显示队列等待。

## r38：实验性「砍图层组」（质量换帧率）

`render_stage` 增加 `flatten_groups`：`Pixel` 图层直接画进舞台、`Mask` 丢弃、`Composite` 跳过。
每组 3 个 pass 全部消失，12 组 = 省约 36 个 pass。

代价：失去遮罩与 PS 混合的图层效果（角色遮挡、反光、渐变遮罩等），可能出现图层穿透或颜色偏差。
这是**质量换帧率**的实验包，需人工比对重场景画面后再决定是否保留。

## r37 实测：合批未生效

重场景 `gxm_draws` 仍是 **57–117 次/帧**（改前 63–95），`exec` 仍 162–164 ms，帧时间 190–199 ms。

原因：**相邻绘制几乎不共享状态**。舞台每个图层来自各自的纹理，纹理不同的四边形无法合并；
参考实现能合批，是因为它的 UI/立绘大多在同一张 atlas 里。

结论：在不合并纹理的前提下，按状态合批没有收益。透明剔除同理——重场景里那些图层都是可见内容。

## r37：按状态合批 + 透明剔除

参考实现「同 texture/rule/variant/blend/clip 才续批」的做法，在命令层实现同样的合并：

- `CommandEncoder::append` 里，如果上一条命令是 Draw 且 **着色器、混合、四张纹理、uniform 参数、
  首顶点 haze** 全部相同，就把顶点追加进去，合成一次提交；
- 单次合并上限 16000 顶点（16 位索引约束）；
- 回归测试 `identical_draws_in_one_run_are_coalesced` 验证两四边形合成一次绘制，
  `recording_is_deferred_and_each_quad_keeps_flat_uniforms` 验证 haze 变化**不会**被错误合并
  （haze 的首顶点值会作为 uniform 使用，这是必须守住的边界）。

同时加入透明剔除：`color.a <= 0` 且无 rule 且混合为 Alpha/Over/Footprint 的四边形不提交。

## r34 实测：黑屏，已回退（r36）

把顶点流提到 scene 开始绑定、每次绘制只传索引的形式，在实机上黑屏，
与参考实现「索引表启动时生成」的差异可能在于：他们的索引表在**创建时**就写好了，
而我在绘制时逐条写索引到同一个 GPU 映射块。无论原因如何，**该改动已完整回退**，
绘制路径恢复为「每绘制绑定顶点流 + 静态索引表」。

教训：参考实现的可照搬程度取决于上下文，这次只搬了形式没搬时序。

## 组形状实测（r36）：内联不可行

`group_shapes` 实测（一次 128 秒运行，871 个组）：

```
total:871  inline-able:0
5/1:141   2/2:210   3/2:478   4/2:42
```

- **inline-able = 0**：没有任何组是「≤1 个 pixel 四边形 + 恰好 1 个 mask 四边形」的形状；
- 主体是 **3/2**（3 个 pixel + 2 个 mask，55%）与 **2/2**（24%），即每组必然需要
  pixel 表面、mask 表面和合成三个 pass。

**结论：「单层组内联」在本作不可行**，此前基于「多数组只有一层」的假设不成立。
每组 3 个 pass 是场景语义决定的，除非重写组合成（用 MRT 或在 shader 内合并 mask），
否则 pass 数降不下来。

## r35：内联候选统计（实测无候选）

`group_shapes` 前增加两个累计值：`total:<组数>` 与 `inline-able:<n>`
（后者 = pixel 四边形 ≤1 且 mask 恰好 1 个的组）。若 inline-able 占比过半，
即可按参考实现的「中性组展平」把每组 3 个 pass 压到 1 个。

## r34：顶点流一次绑定 + 索引偏移

按第 2 条实现：`effect_scene` 里把整条顶点环绑一次，每次绘制只写自己的索引并传给 `sceGxmDraw`，
去掉每绘制一次的 `sceGxmSetVertexStream`（重场景 88 次/帧）。

## 组结构统计（r33）

为决定「单层组内联」能否实现，先测每组的形状。`render_stage` 在每次 composite 时记录
（pixel 四边形数 / mask 四边形数），采样行输出 `group_shapes`，形如 `1/1:120 2/1:40 0/1:30`。

判读：`1/1` 占比越高，内联改造收益越大（每组 3 pass → 1 pass）。

## 默认档（r23）：场景 480×270 + 画布 960×540

实测对比（同一台机、GPU 222 MHz）：

| 配置 | 平均 | 重场景最慢窗口 | pixel+stage 每帧 |
|---|---:|---:|---:|
| 场景 480×270 + 画布 960×540 | **12.2 FPS** | **210 ms** | 20 ms |
| 全部 720×405 | 8.9 FPS | 631 ms | 45 ms |

720 档把场景链像素提到 2.25 倍，而画布只省 6 ms，净亏 26 ms/帧，因此**没有采用**。
720 仍保留为可选档（`scene-mode.txt` 写 `720`）。

重场景的主要开销仍是 `group pixel`（2.98 pass/帧）与 `stage`（2.76 pass/帧）。

## 重场景的真相（r25 实测）

PC 197–304 每帧 **50 个 pass**（普通对白 9 个）：

| pass | 次数/帧 | 每次 | 合计 |
|---|---:|---:|---:|
| group pixel | 22–23 | 4.3 ms | ~97 ms |
| group mask | 12 | 1.9 ms | 22 ms |
| stage | 8 | 2.3 ms | 19 ms |
| scene | 6 | 1.9 ms | 11 ms |
| canvas | 1 | 15 ms | 15 ms |

`mask` 有 12 次但合计不到 5 次绘制 ⇒ **空 pass 约 1.9 ms/次**，50 次即 ~95 ms 纯同步开销。
同一次测量里 `card_read` 多数 < 2 ms/帧，只有单次切图出现 82 ms 的 deferred 尖峰
⇒ **资源加载不是重场景的主因**（异步化能消切图卡顿，但救不了 5 FPS）。

## 重场景 194 ms 的构成（r26 实测）

PC 240：`work 194 = exec 165 + present 27`；exec 内 `finish 84.5` ⇒ **CPU 提交约 80 ms / 39 个 pass ≈ 2 ms/pass**。

单个 pass 的成本几乎全是固定的：`begin_target` 的 7 次状态设置 + `sceGxmTransferFinish` + 一次 finish。
r26 去掉结束 finish 后，pixel 单 pass 从 4.3 → 1.86 ms，但总帧时间不变——等待转移到了下一次 begin。

**结论：重场景要 20 FPS 需要 ≤10 个 pass/帧，而当前场景本身就产生 39 个**（6–12 次 group composite × 4 pass）。
这是引擎的合成结构决定的，不是同步或分辨率问题。

## 纹理准备的实测代价（异步预加载的依据）

每次「准备一个延迟纹理」的实测耗时：

| 时间点 | 一次准备的条目 | 每条耗时 |
|---|---:|---:|
| 51s (PC 212) | 3 | 286 ms |
| 91s (PC 402) | 7 | **668 ms** |

这 300–700 ms 全在主线程上：卡读 + NX 解压 + 解码 + 上传。GPU 在此期间是空闲的（同窗口 finish 只有 5 ms）。

## r30 实测：未改善

PC 402 仍是 **674 ms/条**，同窗口卡读 435 ms——32 MiB 的保留预算被第一批发满，
后续全部退回读卡路径。**字节常驻只对「再加载」有效，首次加载仍需异步。**

## r31：后台读取（ByteStage）

新增 `ByteStage`：24 MiB 上限的环形缓存 + `in_flight` 去重。

- KATL 图集创建时立即把「读该归档区间」投给工作线程（`std::thread`，`Arc<Archive>` 可跨线程）；
- `load` 闭包先查缓存，命中则零卡读，未命中仍退回同步读（不比原来差）；
- 图集通常在创建后数帧才被采样，因此读盘可以与渲染重叠。

局限：只覆盖 KATL 图集这一条路径；CG 的 `adopt_image_reload` 仍未接入。

## r30：图集字节常驻（消除卡读）

KATL 图集条目在创建延迟纹理时**字节本来就在手上**（`assets.rs` 刚读完整个条目），
原实现却立刻丢弃并留下一个 `Reload` 读卡描述符。现在优先用 `defer_altered`（保留字节），
在使用渲染器既有的 32 MiB 编码源预算；放不下时退回原来的读卡路径。

效果：重新准备这些纹理时不再读卡，只剩解压/解码/上传，预计单条 300–700 ms → 50–120 ms。

## r29 实测：仍未生效（负结果，保留记录）

画面正常，但 `mask` 在重场景仍是 **12 pass/帧**，总 pass 仍 39，帧时间仍 192–196 ms。
说明这些 composite 要么 `pending[1]` 非空（每层确实画了掩码），要么混合模式为 Opaque 而被排除。

**结论：在这段场景里，跳过条件一次都没命中。** 继续在这条路上加条件只会增加画面风险，
因此停止该方向。重场景的 39 个 pass 是引擎合成结构（每组 4 pass × 6–12 组）决定的，
在不动合成算法本身的前提下无法显著下降。

## r28 实测：未生效

`mask` 仍是 12 pass/帧、重场景仍 39 pass。原因是跳过条件写成了
「掩码表面当前为零」，而每组的清屏旗标在**合成之后**才被消费，判断时永远读到上一组的非零状态，
所以一次都没跳过。

r29 修正为：**只要本组有待执行的掩码清屏且没有任何掩码四边形**，合成必然为零，即可跳过；
跳过时把两张表面标记为需要清屏，避免脏数据流入下一组。

## r28：跳过掩码为空的图层组（未生效）

`fs_group_composite` 的 alpha = `pixel * mask`（`group_alpha`）：掩码全零时整组合成等于目标本身。
日志里 `mask` 12 次 pass/帧却合计不到 5 次绘制，即大量组没有掩码内容。

实现：跟踪掩码表面是否仍为全零（清屏后未绘制任何掩码四边形），满足且混合模式非 Opaque 时
跳过该组的 pixel/mask/composite 共 4 个 pass，并标记两张表面在下次使用前清空。

## r27 实测：无收益

去掉 `TransferFinish`、缓存 viewport 状态后，重场景仍为 192–195 ms（PC 246：exec 162、finish 85.5、27.9 pass）。
那 80 ms 的 CPU 提交主要在**每次绘制**（86 draws/帧 × 约 0.6 ms），不在 pass 状态设置。

## r27：削减每 pass 的 CPU 提交（已被上节实测否定）

- `begin_target` 不再调用 `sceGxmTransferFinish`（上传路径自己已经 finish）；
- viewport/cull/depth 七个状态调用按目标尺寸缓存，仅在尺寸变化时重新设置，present 路径负责失效。

预计每 pass 省 0.5–1 ms，重场景 39 pass ≈ 20–35 ms。

## r26：每个 pass 只保留一次同步

`kv_gxm_end_target` 不再调用 `sceGxmFinish`：`kv_gxm_begin_target` 与
`kv_gxm_begin`（呈现入口）在采样前都会 finish，所以删除是安全的。
预计重场景 195 ms → 约 150 ms。

## r25：只降画布（默认）

场景链保持 480×270，合成/UI 由 960×540 降到 720×405：
`canvas` 单 pass 23–30 ms → 预计 15–17 ms，重场景约 200 → 187 ms。

`scene_size` 与 `composite_physical` 已解耦，画布缩放不再把场景链一并抬高
（r22 的错误就是两者绑在一起，场景链从 480 涨到 720，净亏 26 ms）。

## r24：group 绘制批量提交（实测无收益）

批量提交没有减少 pass 数（8.81 → 8.86）：`stage` 每 pass 已有 14.5 次绘制，
pass 数实际由**每帧 2–3 次 group composite** 决定，每次 composite 都要
「刷 stage → 刷 pixel → 刷 mask → 合成」四步。改图层批量不影响 composite 次数。
改动保留（无副作用），但不计入收益。

`render_stage` 原来每遇到一个 `Pixel`/`Mask` 图层就先把 stage 刷一遍、再开一个 group pass，
于是 10 个图层组就是 20 多次 pass。现在把同目标的四边形缓冲起来，在每次 composite 前各刷一次：
stage 一帧一次、`group pixel` 一次、`group mask` 一次。

- 不同目标之间没有依赖，重排只影响提交顺序，不改变最终像素；
- `clear` 会先刷新旧批次，避免被后面的清除覆盖；
- 非 Vita 分支保持原逻辑不变。

## 已定位的根因与修复

1. **每 pass 全量同步**：pass 从 42 降到 8；每个 pass 实测 12–20 ms，固定代价为主。
2. **每绘制 8 次按名查找 uniform**：改为创建时解析一次，`exec` 133.8 → 41.6 ms。
3. **GPU 频率**：移植从未设置频率；CPU 可提到 444，但 GPU/BUS 在用户态被系统拒绝（返回 0 但读数不变），需插件超频。
4. **中文界面每帧读 32 MB 图集**：`WTex` 失败即重试 → 每帧重解码；改为 0.5 秒限流。
5. **`sysmes` 每帧重读**：解析结果按语言缓存。
6. **中文界面崩溃（字体内存）**：三份系统字体全量读入 + 每份克隆 → 堆耗尽 → newlib assert；改为逐个读入、UI 优先用语言字体、单字体 24 MiB 上限。
7. **音频解码崩溃**：`decode_fwav` 按文件头声明分配无上限；加 4M 样本与双声道上限。
8. **堆太小**：96 → 192 MiB（ATTRIBUTE2=0x0C 给 365 MiB 主内存）。
