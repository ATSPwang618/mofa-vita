我扒完之后，发现了一个非常关键、而且和我们上一条判断不一样的事实：

> Azahar 的 Vita 版并不是 Interpreter → JIT → IR → Renderer 这一条链。

Vita 上实际运行的是：PICA shader → GXM USSE IR → USSE 指令/GXP → SceGxm → Vita GPU。

而 shader_jit_a32_compiler.cpp 虽然存在，而且确实是一个很漂亮的 ARM32 JIT，但 PS Vita 编译时明确禁用了它。



这反而比“Interpreter 比 Sony 官方快”更有意思。

3. 但是：PS Vita 根本不用 A32 Shader JIT

这个地方是这次扒代码最大的发现。

你之前问：

> Azahar 的 shader interpreter / JIT 是不是很强？



答案是：

A32 JIT 确实很强，但 Vita 版根本没有启用。

看：

src/common/arch.h

这里直接写死：

#if (x86_64 || arm64 || arm32) && !defined(__vita__)
#define CITRA_HAS_SHADER_JIT 1
#else
#define CITRA_HAS_SHADER_JIT 0
#endif

注释甚至直接解释原因：

> PS Vita 映射 executable memory 需要 kernel plugin，因此这个 build 不要求它，所以使用 shader interpreter。



所以：

普通 ARM32 Linux
       │
       └── A32 JIT = YES

PS Vita
       │
       └── A32 JIT = NO
             ↓
       Interpreter

4. 但 Azahar 又确实写了一个 ARM32 JIT

这个非常值得你注意。

文件：

src/video_core/shader/shader_jit_a32_compiler.cpp

不是摆设。

它是真正的：

PICA bytecode
      ↓
ARM32 machine code

JIT engine 会：

ShaderSetup
    ↓
program code hash
    +
swizzle hash
    ↓
cache lookup
    │
    ├── hit → 直接执行
    │
    └── miss
          ↓
       JitShader
          ↓
       Compile()
          ↓
       ARM32 machine code
          ↓
       executable memory

而且它不是简单的 C++ switch interpreter。

它直接生成：

ARM32
  +
NEON

例如寄存器分配：

R0  = uniforms
R1  = ShaderUnit
R2/R3/R12 = scratch

Q1 = SRC1
Q2 = SRC2
Q3 = SRC3

Q4 = constant 1.0
Q8/Q9 = scratch

也就是说：

PICA ADD
 ↓
ARM32 VADD

PICA MUL
 ↓
ARM32 VMUL

PICA DP4
 ↓
NEON dot/vector sequence

它甚至针对 PICA 的：

swizzle
mask
relative uniform addressing
MOVA
LOOP
CALL
IF
CMP
MAD

做了专门处理。

5. A32 JIT 最后怎么执行？

这一段非常漂亮。

编译完之后：

mmap(
    ...,
    PROT_READ | PROT_WRITE | PROT_EXEC,
    ...
)

把生成出来的 ARM32 machine code 放进 executable memory。

然后：

program =
    reinterpret_cast<CompiledShader*>(code_mem);

运行时：

program(
    &setup.uniforms,
    &state,
    entry
);

也就是说：

PICA shader

     ↓ compile once

ARM32 machine code

     ↓ cache

直接 CALL 函数指针

完全跳过：

decode
dispatch
switch
instruction interpretation

但是 Vita 因为 executable-memory 问题没有走这条路。

9. 这个 IR 做了什么优化？

这里是我认为最值得你研究的地方。

源码自己列出来了。

① Dead Store Elimination

比如：

r0 = MUL(...)
r0 = ADD(...)

如果第一个 r0 根本没人读取：

MUL

直接删。


---

② Load folding

例如：

load r0, uniform
mul r1, r0, r2

变成：

mul r1, uniform, r2

如果硬件指令允许直接读取。


---

③ Internal register reuse

比如：

load → i0
use
load → i0
use

如果第二次 load 前 i0 仍然保存正确值：

第二次 load

直接删。


---

④ Two-wide optimization

这个尤其适合 Vita USSE。

比如 PICA：

mul.xyzw

最终发现结果实际上只需要：

xy
zw

而 USSE 对 pair 操作更友好。

于是：

4-wide operation

可能被拆成：

2-wide op
2-wide op

并且把原来用于搬运数据的 load 一起消掉。

这些优化都明确写在 usse_ir.h 的注释和 Lower() 设计里。
