# 兼容补丁（patch.tjs）

`patch.tjs` 是游戏的 TJS 兼容脚本，用来声明插件替代实现、扩展已有插件，或在游戏脚本加载后修改类和函数。这些接口由 krkr-rs 提供，不是原版 Kirikiri 的通用接口；`Plugins.link` 选择引擎注册的实现，不执行游戏 DLL 的机器码。

本文的接口行为对应当前代码。插件本身的支持情况见[插件兼容清单](插件兼容清单.md)，内部职责见[软件设计与架构](软件设计与架构.md#插件与兼容补丁)。

## 放置与加载

### PC

把补丁保存为游戏根目录下的独立文件 `patch.tjs`。`play` 的顺序是：安装可选的 `xp3filter.tjs` 资源过滤器，执行补丁，再执行游戏入口（默认 `startup.tjs`）。过滤器在独立运行时中工作，兼容补丁在游戏运行时中工作。

```text
krkr-rs play "D:/Games/MyGame" --debug
krkr-rs play "D:/Games/MyGame" --patch "compat/my-patch.tjs" --debug
krkr-rs play "D:/Games/MyGame" --no-patch
```

`--patch` 的相对路径以游戏根目录为基准，也可指定绝对路径。默认的根目录 `patch.tjs` 不存在时跳过；显式指定的文件不存在时报错。自动补丁使用本地文件路径，XP3 内的同名脚本不会替代它。`engine run/eval` 不会自动查找游戏补丁。

脚本默认编码为 UTF-8；无 BOM 的脚本受 `--encoding` 和 `Scripts.textEncoding` 影响。补丁可以保存为带 BOM 的 UTF-8 或 UTF-16，避免受游戏脚本的默认编码影响。`patch.tjs` 和游戏资源包 `patch.xp3` 是两回事。

### PSV

把同一份补丁放到 `ux0:/data/KRKR/<游戏目录>/patch.tjs`。PSV 启动器会自动执行它，然后执行游戏设置中的启动文件；默认入口、手动选择的散文件和 XP3 入口都遵循这个顺序，无需额外引导脚本。

根目录补丁不存在时跳过，执行失败时停止启动并显示错误。自动加载使用明确的本地文件路径，XP3 内的同名文件不会替代它。不要再从游戏入口重复执行同一份补丁，否则可能出现优先级重复或已加载插件不能修改的错误。

PSV 的 patch 接口与 PC 共用引擎实现。资源过滤是另一项功能：当前 PSV 启动器不自动安装 `xp3filter.tjs`；资源应先在 PC 上解密、转换。资源处理与构建参见 [PSV 文档](PSV.md)。

## 选择接口

| 需求 | 写法 | 生效时机 |
|---|---|---|
| 明确跳过一个插件，不提供任何方法 | `Plugins.mock("name.dll")` | 游戏加载该插件时 |
| 用脚本替代一个插件 | `Plugins.mock("name.dll", spec)` | 首次加载该插件时 |
| 保留下层实现，添加或包装方法 | `Plugins.patch("name.dll", spec)` | 下层安装完成后 |
| 让另一个 DLL 名称指向相同实现 | `Plugins.alias("other.dll", "name.dll")` | 注册别名后，按原实现加载 |
| 等游戏脚本定义好类或函数再修改 | `Scripts.afterLoad("file.tjs", handler)` | 匹配脚本成功执行后、返回调用者前 |

`mock` 和 `patch` 的第二个参数是 **TJS 字典**，使用 `%["键" => 值]` 语法。安装函数写在字典的 `"onLink"` 字段中。`Scripts.afterLoad` 的第二个参数才是直接传入的函数。

插件声明必须早于对应的 `Plugins.link`；声明本身不会立即安装方法。补丁通常只负责声明，让游戏原来的加载代码调用 `Plugins.link`。如果游戏直接使用方法而没有加载插件，需要在使用前显式 link。

## 示例：G 弦的插件与对话框补丁

下面可以作为一份完整的 `patch.tjs`。前三个 mock 为五个图层方法提供空实现；最后一段沿用游戏的普通图层绘制确认对话框。

```javascript
Plugins.mock("LayerExMosaic.dll", %[
    "onLink" => function(p) {
        p.extend(Layer, %[
            "AddMosaic" => function() {}
        ]);
    }
]);

Plugins.mock("layerExAlpha.dll", %[
    "onLink" => function(p) {
        p.extend(Layer, %[
            "AlphaColorBlend2" => function() {},
            "AlphaColorBlend" => function() {}
        ]);
    }
]);

Plugins.mock("LayerExColor.dll", %[
    "onLink" => function(p) {
        p.extend(Layer, %[
            "TranslucentColorBlend" => function() {},
            "ExclusiveReplacementProcessing" => function() {}
        ]);
    }
]);

Plugins.mock("layeredwindow.dll");

Scripts.afterLoad("CustomYesNoDialog.tjs", function(storageName) {
    YesNoDialogWindow.updateButton = function() {
        if (typeof this.__krkrDialogBackdrop == "undefined") {
            primaryLayer.fillRect(
                0, 0, primaryLayer.imageWidth, primaryLayer.imageHeight,
                0xff101010
            );
            this.__krkrDialogBackdrop = true;
        }
        bgLayer.opacity = 255;
        pileLayer.visible = false;
    };
});
```

空函数接受调用但不绘制，返回 `void`；因此马赛克、颜色混合等对应效果会被跳过。如果调用方依赖返回值，需要按调用方的实际约定提供值。对话框部分依赖该游戏的类名和图层字段，不能直接套用到其他游戏。

五个空方法已在 PC 引擎中验证插件加载及调用；这不表示游戏的整段演出或对话框已经验证。`p.extend(Layer, ...)` 修改类成员，影响之后创建的实例；已经创建的实例不会自动换成新方法。

## spec 字典与安装上下文

| 字段 | 类型与默认值 | 说明 |
|---|---|---|
| `priority` | 正整数，默认 `100` | 数值越大越靠外；同一插件身份不允许重复优先级 |
| `globals` | 字典，默认无导出 | 安装时发布到全局的名字和值，可包含函数、类、字典等 |
| `onLink` | 函数或 `void` | `function(p) { ... }`，本层安装回调 |
| `onUnlink` | 函数或 `void` | `function() { ... }`，返回 `false`（整数 `0`）拒绝卸载 |

只支持表中的四个字段，字段名区分大小写。`Plugins.mock(name)` 等价于不给出 spec；它截断下层实现，不安装任何导出。`Plugins.patch` 需要提供 spec 参数，并且必须存在下层提供者。

`onLink(p)` 的 `p` 有三个方法：

| 方法 | 用途 |
|---|---|
| `p.export("name", value)` | 发布或替换一个全局成员 |
| `p.extend(target, %["member" => value])` | 向对象或类添加、替换成员；第二个参数必须是字典 |
| `p.hook(target, "method", handler)` | 包装已有函数；处理器收到 `next` 和原调用参数 |

这些方法先暂存修改，本层 `onLink` 成功结束后才提交。`globals` 也遵循这个规则，所以不要在同一回调中通过全局名字读取本层尚未提交的导出；需要时保留局部引用。`p` 只在本次安装期间有效，不能保存到全局或后续事件中继续调用。

### 发布全局函数与数据

```javascript
Plugins.mock("CompatInfo.dll", %[
    "globals" => %[
        "CompatVersion" => "1.0",
        "CompatReady" => function() { return true; }
    ],
    "onLink" => function(p) {
        p.export("CompatOptions", %["enabled" => true]);
    }
]);

// 自测时主动加载；实际补丁可交给游戏原来的 Plugins.link。
Plugins.link("CompatInfo.dll");
if (!CompatReady() || !CompatOptions.enabled)
    throw "CompatInfo install failed";
```

### 保留下层函数并调整参数

下面使用虚构插件构成一个可独立运行的例子：优先级 50 的 mock 提供下层，默认优先级 100 的 patch 包装它。对真实插件使用 `Plugins.patch` 时，目标对象与方法应是该插件已经提供的成员。

```javascript
Plugins.mock("ExampleMath.dll", %[
    "priority" => 50,
    "globals" => %[
        "CompatMath" => %[
            "bias" => 10,
            "add" => function(a, b) { return this.bias + a + b; }
        ]
    ]
]);

Plugins.patch("ExampleMath.dll", %[
    "onLink" => function(p) {
        p.hook(CompatMath, "add", function(next, a, b) {
            if (a < 0) a = 0;
            return next(a, b);
        });
    }
]);

Plugins.link("ExampleMath.dll");
if (CompatMath.add(-2, 3) != 13)
    throw "ExampleMath hook failed";
```

`next` 是包装前的函数；对通常未预先绑定的函数，调用会沿用当前接收对象作为 `this`，已有绑定则保留。返回值和异常正常传递。处理器可以不调用 `next`，也可以调整参数或返回值；原方法不存在或不是函数时，`p.hook` 会报错。

### 增加插件别名

```javascript
Plugins.mock("CompatBase.dll");
Plugins.alias("CompatLegacy.dll", "CompatBase.dll");
Plugins.link("CompatLegacy.dll");
```

真实适配中，如果已有正确的注册实现，直接以它作为 alias 的目标，不需要示例中的 mock。目标必须先注册，新别名必须尚未注册；目标已经加载后不能再添加别名。所有别名共享同一个插件身份、安装和卸载状态。

插件名称查找折叠 ASCII 大小写，但不会自动去掉路径或 `.dll` 后缀。使用游戏实际传入的名称；不要为仅有大小写差异的名称重复注册。link/unlink 最好始终使用同一个字符串：加载列表按传入名称记录，大小写不同的拼写可能作为不同的已加载名称保留。

## Scripts.afterLoad 的时机与匹配

`Scripts.afterLoad("CustomYesNoDialog.tjs", handler)` 在脚本成功执行后调用 `handler(storageName)`，其中参数是加载调用使用的存储名。可以像 G 弦示例一样直接赋值修改游戏类；这个回调没有 `p` 安装上下文。

| 登记的名称 | 匹配规则 |
|---|---|
| `CustomYesNoDialog.tjs` | 匹配同文件名，包括目录或 XP3 中的文件 |
| `scripts/CustomYesNoDialog.tjs` | 匹配加载调用使用的完整名称；不会自动补全绝对路径 |
| `data.xp3>scripts/CustomYesNoDialog.tjs` | 匹配包含该归档前缀的完整名称 |

匹配统一 `/` 与 `\` 并忽略 ASCII 大小写，不支持 `*` 通配符。同名文件可能来自多个目录，必要时先记录 `storageName`，再使用准确的完整名称。

回调针对 `Scripts.execStorage` 和 `Scripts.evalStorage`；纯内存 `Scripts.exec/eval` 与只编译不执行的 `Scripts.compileStorage` 不触发。加载失败不触发，回调抛错会传回加载调用者；正常回调不会替换 `evalStorage` 原来的结果。

同一个脚本每次成功执行都会触发已登记的回调，重复登记会追加而不是覆盖。回调列表在该次执行前选定，脚本内部新登记的回调不会追溯作用于本次加载。

该机制不能抢在目标脚本内部的代码之前执行：如果目标脚本自己定义类后立即创建实例并使用方法，加载后的回调可能已经太晚。需要选择更早的加载节点，或明确修改现有实例。

## 优先级、重复加载与卸载

内置实现的优先级是 0。解析时从高优先级向下寻找实现，遇到 mock 后截断更低层；实际安装顺序由下到上。例如 mock 50 → patch 100 → patch 200；若没有 mock，则先安装内置实现。更高优先级的 mock 会跳过低优先级的 patch 和内置实现。

同一插件身份（包括别名）内，优先级不能重复。普通补丁使用默认 100 即可；需要增加一层时明确分配其他优先级，或合并到同一个 spec。加载后再次 link 不重跑已安装层；成功卸载后重新 link 会再次安装。

`Plugins.unlink(name)` 返回真表示该名称已释放；其他已加载别名仍可保留实现。最后一个名称释放时，还要通过依赖、资源占用检查和 `onUnlink`。下面演示显式拒绝卸载：

```javascript
var compatBusy = true;
Plugins.mock("CompatLifetime.dll", %[
    "onUnlink" => function() {
        return !compatBusy;
    }
]);
Plugins.link("CompatLifetime.dll");
if (Plugins.unlink("CompatLifetime.dll"))
    throw "unload should have been refused";
compatBusy = false;
if (!Plugins.unlink("CompatLifetime.dll"))
    throw "unload should have succeeded";
```

卸载回调从外层向内层执行，没有参数，也没有安装上下文。拒绝卸载不应提前销毁仍在使用的对象。不要在 `onLink/onUnlink` 中嵌套调用插件注册、link 或 unlink，这些操作受到重入检查。

通过 `globals`、`p.export/extend/hook` 安装的成员由引擎记录：加载失败时回滚，成功卸载时逆序恢复，而且不会覆盖游戏后来替换的值。直接写 `Layer.someMethod = ...`、修改现有对象内部字段、文件 IO 等不属于这个事务；`afterLoad` 中的直接赋值也不会随插件卸载自动恢复。

## 排查与自测

| 报错或现象 | 检查方式 |
|---|---|
| `native argument requires a Dictionary` | `mock/patch` 的 spec 或 `p.extend` 的成员表不是字典；把函数放进 `%["onLink" => function(p) { ... }]` |
| `unknown plugin patch field` | 检查 spec 的字段名及大小写，只支持四个规定字段 |
| `cannot change a loaded plugin` | 声明晚于 link，或同一份 patch 被执行两次；把声明移到入口之前并排除重复加载 |
| `duplicate plugin patch priority` | 同一个插件身份重复使用优先级，默认都是 100；检查别名、重复加载和分散的声明 |
| `plugin patch requires a lower provider` | `Plugins.patch` 没有下层实现；需要完整替代时使用 mock |
| `hook member does not exist` | 下层没有提供目标成员，或目标对象、方法名、加载时机不对 |
| `plugin installation context is closed` | 在 `onLink` 结束后继续使用保存的 `p` |
| 类或方法仍不存在 | 检查对应 link 是否发生、名称与大小写是否正确，以及实例是否早于类扩展创建 |
| `afterLoad` 没执行 | 检查登记顺序、加载方式、实际存储名，以及目标脚本是否成功执行 |
| PSV 根目录有 patch 但未生效 | 使用包含自动加载支持的新构建，确认它是游戏根目录的独立文件；开启调试查看 `Compatibility patch:` 记录 |

PC 用 `--debug` 开启输出；PSV 在游戏设置中开启调试，脚本日志输出至控制台，由外部日志插件收集。可在补丁顶部、`onLink` 或 `afterLoad` 中暂时加入 `Debug.message(...)`，分别确认补丁执行、插件安装和脚本匹配；默认关闭调试时看不到这些输出。

不启动游戏即可验证接口例子：把一个独立例子保存为 UTF-8 的 `patch-check.tjs`，执行：

```text
krkr-rs engine run "D:/Temp/patch-check.tjs" --debug
```

单独执行只有声明的补丁，只能验证声明是否有效；验证 `onLink` 还需要追加对应的 `Plugins.link` 和方法调用。本文的全局导出、函数包装、别名、卸载例子已经包含这些步骤。需要游戏类或窗口的补丁，则放回游戏检查真实调用和画面。
