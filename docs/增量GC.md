# 增量 GC

堆继续使用 SlotMap 代际句柄和非移动对象记录。增量回收的直接收益是缩短一次安全点的暂停；目前的微基准没有证明脚本吞吐量提高，不能据此宣称游戏帧率提高。

## 接口与自动策略

- `Heap::collect_step(roots, budget)` 启动或继续一轮回收，返回阶段、本片工作量，以及可选的完成统计。预算为零不启动或推进回收。
- `Runtime`、`Scheduler`、`TimedScheduler` 提供相应接口；调度器自动加入活动、等待、完成及续体的根。
- `Heap::collect` / `Runtime::collect` 从当前根重新完整回收，即使之前有未完成的增量周期。`System.doCompact` 的立即回收语义保持不变。
- `Runtime::collect_auto` 在宿主决定需要回收后选择执行方式：未开始周期且对象、字符串、octet、符号合计不超过 4096 条时走完整扫描；较大堆每片处理 512–4096 个工作单位；未处理分配债务达到 4 MiB 时回退完整回收。
- `Engine::collect_if_needed` 继续采用与存活堆估算相关的分配阈值和空闲期限。正在进行的周期会让宿主继续调度，即使启动回收后分配债务已归零。只有周期完成时才返回 `Some(CollectionStats)`。

单个工作单位是一条堆记录的扫描或一个对象的追踪。预算不是毫秒上限：根枚举、原生复查、单个大容器的边、原生 `Trace`/析构，以及终结器集合的提交仍是不可分割操作。它不是硬实时 GC，也不是硬内存限制；一次原生调用本身仍可能分配大量内存。

```rust,ignore
// 只能在所有 VM / 原生调用都已退出当前执行片后调用。
let step = runtime.collect_step(all_current_roots, 512);
if let Some(stats) = step.completed {
    // 此处处理整轮回收统计。
}
```

## 阶段与不变量

1. **Mark**：每个安全点提交全部当前根，迭代追踪灰对象。普通数组、成员及函数池的写入直接标记新边，不因数值修改而重扫整个容器。无法枚举具体改动的原生状态借用会将对象重新加入灰队列。
2. **Finalizers**：分片发现候选，复查原生引用，重新筛选仍不可达的对象，再一起提交终结器集合。先确定整个候选集合，避免循环引用掩盖另一个终结器。
3. **FinalizerMark**：保留已提交对象及其依赖。脚本终结器由 VM 按原有暂停、异常、取消与复活规则执行，GC 自身不运行脚本。
4. **Sweep**：按对象、字符串、字符串缓冲区、octet、符号的顺序分片清扫；弱符号索引同步删除。灰队列有待处理工作时不会继续释放记录。

正常周期翻转一个标记位，无需全堆清零。仅显式完整回收打断增量周期时需要先规范化颜色。Arena 维护稠密句柄列表，反向清扫以常数时间删除；避免在每一片从头跳过 SlotMap 的空槽，也避免周期开始时复制全部句柄。

周期内的新分配存活到下一轮，分配债务不会在当前周期结束时被抹掉。增量 `retained_bytes` 是扫描周期起始记录时的容量估算，新增分配仍由债务反映；它不包含分配器、模块代码和外部图形/媒体资源。

共享成员快照在一轮追踪中保留 `Rc`，防止快照释放后地址复用造成错误去重。字符串标记直接更新共享缓冲区的存活前缀；清扫期间的追加也会更新长度，因此不会错误截断新字符串。后续周期仍可缩掉已放弃的大尾部。

## 根、弱引用与原生共享状态

每次 `collect_step` 都必须传入所有当前 VM、宿主临时结果和异步续体的根。裸 `Value` / `ObjId` 不自动保活，不能在遗漏根之后用仍未物理删除的句柄恢复对象图。跨安全点的宿主所有权应使用显式根；弱所有权使用 `WeakObjId`。

标记期间升级弱引用会登记待追踪对象，即使临时强引用随后被丢弃，也不会漏掉它的边或新安装的终结器。清扫期间对白对象的弱升级返回 `None`，因为其依赖可能已经释放。这个只读升级接口使用一条局限于 GC 记账的 `RefCell` 工作队列，不暴露业务状态的可变借用。

现有原生状态允许通过 `Rc<RefCell<_>>` 在 Heap 接口之外修改。收集器在提交终结器、进入清扫前复查已标记原生状态；如果追踪跨片，后续到达该边界时再次复查。**不会在每个标记或清扫片重扫所有原生状态。** 进入清扫时，合法持有的旧值已经标记，新值由分配保护，弱引用也不能重新引入白对象，因此清扫期间不需要重复原生全扫描。

`Layer`、`Window` 等服务已经集中保存记录并通过 ID 定位实例；服务级根主要由类状态追踪，实例追踪自己的边。`Rc<RefCell<_>>` 的数量本身不是性能归因。本次针对已发现的成本重构了写屏障和回收遍历，没有证据支持为这次 GC 改动全面替换共享服务。未来若游戏剖析发现原生复查成为热点，可以将含受管引用的服务修改集中到带通知的上下文；需要同时覆盖续体、宿主回执和析构路径，才能安全取消保守复查。

## 验证与测量

回归覆盖小预算的可达性模型、灰/黑对象之间迁移引用、原生共享状态改写、清扫中新分配、弱升级、各阶段被完整回收打断、字符串前缀缩容，以及等待中的终结器循环、动态编译和复活。原有语言、绑定、运行时、引擎、渲染测试继续运行。

```text
cargo fmt --all -- --check
cargo check --workspace --all-targets --locked --offline
cargo test -p tjs-core -p tjs-front -p tjs-bind -p tjs-runtime -p krkr-engine -p krkr-render --locked --offline
cargo run -p tjs-core --release --example gc_profile --locked --offline -- incremental
cargo run -p tjs-core --release --example gc_profile --locked --offline -- full
cargo run -p tjs-runtime --release --example gc_workload --locked --offline -- auto
cargo run -p tjs-runtime --release --example gc_workload --locked --offline -- incremental
```
