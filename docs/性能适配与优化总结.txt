mofa-vita-krkr —— PS Vita 性能适配与优化总结
最后更新：2026-09-15   目标平台：PS Vita 实机（Vita3K 仅作验证环境）

本文合并了此前三份文档（真机性能适配报告 / 优化方案-40fps / 计量层报告），
并把结论按"事实 → 测量 → 方案"重排。所有数字都标注了来源与单位。

====================================================================
0. 目标与约束
====================================================================

目标：PS Vita 实机稳定 40fps（25ms/帧），不接受 >33ms 的尖峰，更不接受
      位图分配失败导致的功能中断。

硬件事实：
  * CPU：Cortex-A9 x4 @444MHz，应用可用 3 核（引擎线程 + 2 个渲染 worker）
  * GPU：SGX543MP4+；无 dual-source blending（影响 ltAddAlpha 的 GPU 化）
  * 内存：ATTRIBUTE2=12，约 365MB USER_RW + 112MB CDRAM；
          newlib 堆 128MB、VitaGL 池 48MB、位图 memblock 保留区 32MB
  * 屏幕：960x544

当前合成面：1024x576 = 589,824 像素 = 全量 2.36MB/帧（游戏自己的 KAG 窗口
尺寸；呈现时缩放到 960x544）。

方向（与项目既定目标一致）：解释器只做 KAG 解析与关键帧求值，图片解码一次后
尽量交给 vitaGL 渲染，减少每帧的 CPU 像素活。

====================================================================
1. 当前管线（读代码得到的事实）
====================================================================

KAG/TJS 解释器
  → 图层位图（CPU 内存，tTVPSoftwareTexture2D，逻辑尺寸 1024x576）
  → tTVPLayerManager::CompleteForWindow（CPU 合成；>=512x512 的大块才走
    2 个 worker，小块在引擎线程串行）
  → BasicDrawDevice 完成 surface → VitaWindowLayer::UpdateDrawBuffer
  → 上传纹理（带脏区裁剪）+ 画一个全屏四边形 + 缩放

即：**GPU 目前只负责"贴一张已经合成好的图"**；图层混合、缩放、文字栅格都在
CPU 上。

====================================================================
2. 已经做过的优化（不要重复做）
====================================================================

  * 图像内核：NEON 表，且已改成"按设备实测选优"（见 3.2）
  * 呈现：5 张轮转纹理 + 脏区部分上传 + 光标/重复帧不重复上传
  * 内存：位图分级分配器（>=1MB 走 USER_RW memblock，留 32MB 保留区），
          失败时先回收再重试
  * 图形缓存：插入后也检查上限（原来会永久超限一张整图）
  * 渲染并行：只对 >=512x512 的原语开 worker；行分割的别名/一致性契约；
              缩放系数与行缓冲区在 owner 线程预分配
  * 文本：MS Gothic 度量缓存 + 未渲染 slot 复用 + HistoryLayer 文本宽度前缀
          复用 + ApplyFont 不再触发纹理分离
  * 引擎杂项：KAG 逐行 verbose 日志关闭、零参数事件免分配、ObjectList 稳定
              Compact、TJS 常量数组安全 downcast、saveStruct 8KB 缓冲、
              本地位图流走 SceIofilemgr
  * 效果：box filter 列和跨帧复用（复杂度与卷积核大小无关）

3. 测量能力（本轮新增）
====================================================================

3.1 三层日志（除注明外均为**每帧**单位）

  [mofa-meter]  ns/px blend=.. adddest=.. add=.. stretch=.. sadd=.. affine=..
                copyfill=.. cmap=..
                启动时一行；由设备上"真正装着的那个内核"微基准测出
                （1024/512 像素 x 64 次 x 3 轮取最小）。

  [mofa-stage]  frames=60 loop=.. busy=.. engine=.. script=..(events=.. timer=..
                kag=.. cont=.. tags=.. rest=..) composite=..(%,calls) present=..
                input=.. recycle=.. idle=..
                其中四个原生接缝：
                  events   = Application::ProcessMessages 的消息循环
                  timer    = TVPTimer::ProgressAllTimer（TJS 定时器）
                  cont     = TVPDeliverAllEvents（**KAG Conductor 就在这里面**：
                             标签派发、关键帧求值、图层属性写入）
                  kag      = KAGParser::GetNextTag（原生解析器，并统计 tags）
                  composite= LayerManager::UpdateToDrawDevice（软件合成）

  [mofa-pixels] frames=60 blend=..k stretch=..k add=..k adddest=..k sadd=..k
                affine=..k copy=..k cmap=..k calls=.. est=..ms
                100 个热点内核上装了"只做整数累加"的转发壳（relaxed 原子加法，
                因为行分割混合会跑在两个 worker 上）。est 用本机实测 ns/px
                折算成毫秒——所以主机和真机各测各的，不能互相外推。

  覆盖范围（P1a 补齐后）：普通/加法/缩放混合的 `_HDA`、`_HDA_o`、`_o`、`_d`、
  `_a`、`_do`、`_ao` 变体，常量 alpha 与常量色填充，拷贝与掩码，缩放常量混合，
  interp（双源）系列，调色（含 65 级与 HDA），以及 affine/线性变换（独立家族）。
  Kirikiri 的 `LayerBitmapIntf` 按 `basename / _o / _HDA / _HDA_o` 逐扫描线选择，
  而 `hda = true if destination has alpha`——也就是**往普通 alpha 图层里画全走
  `_HDA` 内核**，这正是 P1a 之前漏掉的那一块。
  仍未覆盖（本作脚本不使用，已确认）：Photoshop 混合模式族（`TVPPs*`，作品脚本
  没有出现 `blendMode`）、`TVPReverseRGB` / `TVPRedBlueSwap*` / `TVPUpscale65_255`
  / `TVPConvert32BitTo24Bit` 这类一次性格式转换。

3.2 设备自测的内核选择
   TVPGL_ASM_Init() 只根据 CPU 特性位装 NEON。真机上那是对的，但模拟器的 JIT
   可能把 NEON 指令退回解释器（结果正确但慢很多）。现在启动时对 8 个吃像素的
   内核各测一小段（单轮封顶 25ms），NEON 必须快 15% 以上才保留；测不出来就
   用标量版。ux0:data/mofa-vita/tvpgl-scalar 标记仍然是"永远不许装 NEON"的
   硬覆盖（真机数据目录里不要放它）。

====================================================================
5. 关键发现
====================================================================

① 稳态里 KAG 解析几乎不要钱。
   96 个标签/帧只花 0.06ms。上一轮担心的"标签派发"在稳态不是瓶颈；稳态脚本
   时间 93% 在 cont（KAG Conductor 的关键帧推进与它触发的图层属性写入）。

② 换页/加载尖峰的真实构成（P3 实测，原假设被推翻）。
   峰值窗口 cont=81.69ms、其中 kag=45.00ms，看起来像"解析主导"。于是把
   LoadScenario 拆成三段单独计时（92 个窗口的统计）：

     桶        平均     中位     峰值     含义
     kag       0.57     0.06    44.79    原生标签解析（GetNextTag 内部）
     kload     0.02     0.00     0.85    场景文件读取 + 切行（TVPGetScenario）
     klabels   0.00     0.00     0.02    标签缓存构建（EnsureLabelCache）
     khooks    0.00     0.00     0.00    游戏自己的 onScenarioLoad(ed) 回调

   结论：**场景加载、标签缓存、游戏回调全都不要钱**；45ms 全在 GetNextTag
   内部（那一个窗口只有 18 个标签 ≈ 2.5ms/个，对应本作序章那个大 [iscript]
   块——仓库里本来就有 yuri-kag-large-inline-assembly/execution 两条追踪标记），
   紧随其后的窗口是 cont=85.11ms 的**游戏自身脚本执行**。
   所以：
     * 原先计划的"预解析 / 缓存标签索引 / 软水位"**不需要做**——
       TVPGetScenario 本来就按 storage 名缓存，EnsureLabelCache 也只在首次构建
       （且实测 0.02ms）；
     * 剩下的是开局一次性的初始化（原生解析 + 游戏脚本），真机约 0.7~1.7 秒，
       属于"进入章节的加载时间"，不是每帧成本。

③ composite 的成本就是像素活——差额之谜已由 P1a 结案（原假设被推翻）。
   P1a 之前：活跃帧 composite 1.76ms/帧，但只计到约 8,133 像素/帧（折算
   0.05ms），差额 1.7ms 无从解释。
   P1a 之后（100 个内核覆盖，100 个活跃窗口）：
     composite 平均 2.16ms / 中位 2.01ms / 峰值 9.11ms
     混合像素 平均 385k / 中位 340k / 峰值 1,586k 像素每帧
     拷贝像素 平均 193k / 中位 147k / 峰值 827k 像素每帧
     折算 est 平均 2.67ms / 中位 2.28ms / 峰值 10.55ms
     **est/composite ≈ 1.24**（略高是因为部分像素活发生在合成区间之外、
     HDA 实际比探针的非 HDA 略贵、探针把每次调用的固定开销摊薄了）
   结论：**是"漏计内核"，不是"调用开销"**。漏掉的正是 `_HDA` 家族——
   `LayerBitmapIntf.cpp` 里 `hda = true if destination has alpha`，往普通
   alpha 图层里画走的全是 `_HDA`，而此前一个都没包；另外 `TVPCopyColor`
   （不透明源拷进 alpha 层）也一直不可见。补齐后混合像素量从 8k/帧跳到
   340k/帧（40 倍）。

④ adddest 家族在稳态调用量为 0 —— 被数据推翻的假设。
   上一轮设想的"写一版精确 NEON 加法 alpha 内核"因此降级：它不是当前热点，
   真机 NEON 也救不了没被调用的代码。

⑤ 启动窗口（第一秒）有约 228k 像素/帧 的 copy：启动时的大块填充/拷贝是稳态
   的几十倍，属于一次性成本，但解释了为什么开局那一秒最吃 CPU。

⑥ 位图内存耗尽（硬证据 + 已修复首刀）。
   症状：游戏在 1-0.ks:81（fgact）抛
     Cannot allocate memory for Bitmap : at TVPAllocBitmapBits
     (size=3010600(1120x672))
   即 3MB 位图分配失败，不是卡顿而是功能中断。

   诊断（新增 [mofa-mem] 快照拿到的关键一行）：
     [mofa-mem] before-reclaim free_user=32MB live_memblock=28MB
   也就是**内核报告的"空闲 USER_RW"恰好停在 32MiB 保留线上，而我们自己的位图
   memblock 只占 28MB**。真正的连锁是：
     保留线把所有 >=1MB 的 memblock 申请挡掉
     → 这些多兆位图被挤进**启动时就一次性预留好的** 128MiB newlib 堆
       （位图在堆里最多时达 59MB）
     → 堆填满 → 分配失败 → 触发全量压缩/回收（尖峰）→ 仍然失败 → 抛异常
   而这个后端里**除位图分配器外没有任何模块申请 USER_RW memblock**
   （脚本 / FreeType / SQLite / 音频 / 视频都从同一个堆分配，VitaGL 的池在初始化
   时一次性认领），所以那条大保留线保护不了谁，只是把内存从游戏手里拿走。

   修复（三处，规模都不大）：
     a) 分配策略改为"内核权威"：>=1MiB 先直接申请 memblock（由内核接受/拒绝），
        拒绝后才按保留线判断，最后才退回固定堆。free_user 查询只作诊断；
     b) 保留线 32MiB → 12MiB，紧急下限 8MiB → 4MiB；
     c) VitaGL 池 48MiB → 32MiB（软件合成下呈现只需约 20MiB），
        多出的 16MiB 让给位图（启动日志可见 threshold 205m）。

   验证：同一失败点（1-0.ks page6 / line 81）顺利通过，继续推进到 page13，
   整轮 **0 条内存压力标记、0 次 OOM 回收、无新 error.txt**。
   这一步同时消掉了"压力 → 全量压缩回收"的尖峰来源。

   仍未做：预取与图形缓存上限（若后续章节再次出现压力再做）。

⑦ 尖峰与内存压力的因果链（读代码定位）：
   游戏自己的 override/kagwindow.override.tjs:714 在重建图层后把
   System.graphicCacheLimit 设成 0 再恢复（整库丢图）→ 后续大位图撞 memblock
   预算 → TVPDeliverCompactEvent(MAX) 全量压缩/回收 → 之后按需重新解码。

6. 真机预算推算与优化方案
====================================================================

真机允许的每帧预算：60fps = 16.7ms；40fps = 25ms。

  * 一屏 589,824 像素：NEON 版 tvpgl 混合按 ~2-3 cycle/px 估 ≈ 3.3ms/次全屏；
    标量版再慢 4-6 倍 → 13-20ms/次。**一次全屏混合就能吃掉 60fps 的全部预算**
    ——这就是真机必须走 NEON 的原因（见 3.2）。
  * 全量上传 2.36MB：真机 USER_RW 上 CPU 侧写入 400-800MB/s → 3-6ms/帧；
    实测的 4%-90% 脏区上传对应 0.1-5ms。
  * 按主机/真机单核 8-20 倍的整体放大：A 状态 engine 2.97ms + present 0.24ms
    在真机上大约 25-60ms/帧 → 真机稳态大概率落在 25-30fps，尖峰帧是数百毫秒。

P1a 补齐计量覆盖（**已完成**，100 个内核 / 8 个家族）
    结果见第 5 节 ③：composite ≈ 像素折算（比值 1.24），确认此前是漏计内核。
    因此 **P1b（减少调用与几何开销）取消**：合成里每次完成只有约 30 次调用/
    帧，真正的成本是每行 300-400 像素的混合与拷贝本身。

P1b（已取消）原计划是"合并扫描线/脏矩形、把每次调用里的重复工作提出来"。
    数据不支持它：壳调用 1,003 次/帧里绝大多数是引擎内部 `while(h--)` 的逐行
    内核调用，不是可省的调度；合并脏矩形反而会多画像素。

P2 位图内存压力（**首刀已完成**，见第 5 节 ⑥）
    已修：内核权威的 memblock 优先分配、保留线 32→12MiB、紧急下限 8→4MiB、
    VitaGL 池 48→32MiB。验证：越过原失败点（page6 → page13），0 内存标记。
    剩余（若再次出现压力再做）：把脚本的"整库清零"当软水位（保留 8-16MB 冷副本）、
    空闲预取下一页要用的图、给解码尺寸设上限（显示尺寸的 1~2 倍）。
    验收：连续 10 分钟不再出现位图分配失败，>33ms 窗口为 0。

P3 加载期 KAG 解析（**已测量，结论是不需要改**）
    实测：kload/klabels/khooks 全为 0-0.85ms，45ms 全在 GetNextTag 内部，而它是
    本作那个大 [iscript] 块的一次性解析；其后 85ms 是游戏自己的脚本执行。
    场景缓存与标签缓存本来就存在且几乎免费，所以原先设想的预解析/索引缓存取消了。
    真机表现是"进入章节时一次 0.7~1.7 秒的加载"，不是每帧卡顿。

P4 分辨率档位 + 40fps 节流 —— 依赖 P1/P2
    节流：mofa::kYuriEngineTickUs 16667 -> 25000。
    分辨率：软件路径下砍分辨率**不是白赚**（图层是 CPU 位图，目标面缩小就要
    把 blit 换成拉伸采样，省下的像素被采样成本吃掉大半）。真正白赚的两种：
      a) 解码尺寸上限（并入 P2）；
      b) 等 GPU 合成之后由 GPU 缩放（GPU 缩放几乎免费）。
    fit_vita_render_surface() 这个"保 KAG 坐标、只缩渲染面"的机制仓库里已有，
    但目前只接在实验性 OGL 合成器路径上。
    40fps 在 60Hz 面板上是 3:2 节奏，要看卷轴/淡入是否有可见抖动。

    像素量的最新口径（P1a 后）：活跃帧 混合 385k + 拷贝 193k ≈ 578k 像素/帧。
    真机上 NEON 生效时按 2-4 倍于模拟器标量的估算，这部分约 0.5-1.5ms/帧——
    也就是说**只要 NEON 在真机上生效，合成不再是 40fps 的障碍**；把分辨率砍到
    0.66 倍能再省掉约三分之一，但收益已经不大。

P5 GPU 合成 —— 优先级继续下调
    现在 GPU 只做最后一层"上传+四边形式呈现"。仓库里那条整体 OGL 合成器
    （-DMOFA_ENABLE_OPENGL_COMPOSITOR=ON）注释写明对商业作品不稳，默认关闭，
    且有构建契约锁定软件渲染为默认。
    下调理由（P1a 后更新）：像素量是明确的（活跃帧约 578k/帧），但真机 NEON
    下折算只要 0.5-1.5ms/帧；而 GPU 化要付的是图层纹理化、ltAddAlpha 原型、
    回读通路这些结构性代价。收益/风险比不划算，除非真机实测显示 CPU 混合
    明显超出上面的估算。
    若将来要做，前置是 ltAddAlpha 的 GPU 原型（SGX543 无 dual-source
    blending，需两遍渲染或 alpha 通道分离），且必须保留脚本回读像素的 API
    （layerExSave / layerExAreaAverage / getMainImage）的 CPU 通路。

风险清单：
  * SGX 无 dual-source blending → ltAddAlpha 的 GPU 方案要先做原型。
  * 脚本会读回图层像素 → 提升到 GPU 的图层必须能降级。
  * 文本 subpixel 一致性 → 必须逐字节 golden 对照。
  * GPU 显存/带宽：112MB CDRAM + 共享内存，大图常驻要有上限与淘汰策略。
  * 数据目录里的 tvpgl-scalar 标记只适用于模拟器，真机不要放。

====================================================================
7. 建议的执行顺序
====================================================================

  P1a（补计量覆盖，已完成） → P2（内存压力/OOM，首刀已完成） →
  P3（加载期解析尖峰，实测后取消） → P4（分辨率档位 + 40fps 节流） →
  P5（GPU 合成，仅在真机数据要求时）

  P1b（合成调用/几何）与 P3（预解析）都已按数据取消；合成、上传、场景加载
  都不是真机的障碍。剩下的是 P4 的分辨率/节流，以及真机实测。

统一验收线：60 秒脚本化场景内 0 个 >33ms 的帧，主线程 CPU < 20ms/帧，
连续 10 分钟不出现位图分配失败。每一步都按现有约定交付：插日志点 → 跑一次
对照 → 出报告（区分新旧日志）。
