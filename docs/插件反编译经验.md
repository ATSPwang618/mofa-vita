# 无源码插件的静态还原经验

2026-09-14，来源：用户提供的魔法使之夜插件。本文保留可复用的静态分析方法；模块设计见[软件设计与架构](软件设计与架构.md)，插件差异见[插件兼容清单](插件兼容清单.md)。反编译出的C是分析结果，不能直接当成原源码。

## 从注册入口建立完整清单

1. 保存原文件SHA256，确认PE位数、导出表与模块名称。字符串出现某个名字，不代表它一定被注册。
2. 从V2Link追注册：旧手写插件通常构造Dispatch并写全局对象；NCB插件还可能通过静态初始化链安装Layer方法、属性和常量。
3. 区分注册包装、参数转换和业务函数。filter.dll有14个全局函数；layerExFilter.dll有五个Layer方法，两者的噪声算法不同，不能按名字设别名。
4. 对每个入口记录参数顺序、缺省值、返回值、状态寿命、读写对象及更新范围，再实现。粒子插件的min/max属性与成对setter应作为同一状态处理，不能只照游戏脚本里出现的少数名字补空方法。

## 分析工具与工作目录

使用本机Ghidra 11.4.2、Ghidra CLI 0.2.2和JDK 21，LLVM objdump辅助检查x86汇编。分析工程、临时脚本和导出放在仓库外的独立工作目录；不要放 target，cargo clean 会删除那里。

CLI使用绝对工程路径。每个DLL独立工程可避免本次遇到的第二次导入问题。基本用法：

```text
ghidra --project <绝对工程路径> --program <模块名> function list --json
ghidra --project <绝对工程路径> --program <模块名> decompile <入口地址> --json
```

批量反编译与分析类型修改可使用Ghidra自带的analyzeHeadless和Java GhidraScript：先关闭本任务对应工程的bridge，再用-process打开已有程序；-noanalysis避免每次重跑全量分析，修改后按需analyzeChanges。不要同时让bridge与headless写同一个工程，也不要结束用户自己的Ghidra会话。

```text
analyzeHeadless <工程父目录> <工程名> -process <模块名> -noanalysis
  -scriptPath <脚本目录> -postScript <脚本.java> -log <分析日志>
```

以上命令检查二进制和数据库，不执行被分析 DLL。静态还原与动态运行的证据分开记录。

## 最容易浪费时间的四个坑

**漏认回调。** filter.dll初次分析没有识别VTable里的14个FuncCall入口。CLI function create对未反汇编的入口报“Function body must contain entrypoint”。应先确认地址是可执行节中的真实函数开头，清理该处错误的分析数据、disassemble，再createFunction；不修改原文件字节。针对已知入口修复，避免盲目把所有整数都建成函数。

**猜错调用约定。** 本地tp_stub.h的TJS_INTF_METHOD是cdecl；导入的Variant包装方法常是stdcall。cdecl调用后的add esp是直接证据。本次即使补了VTable类型，反编译器旧的调用点推断仍使栈每轮漂移44字节，出现大量不存在的参数。对已核实的虚调用点，用HighFunctionDBUtil.writeOverride指定准确参数数目和cdecl，才恢复了可读代码。不能把这类堆叠的in_stack变量抄进实现。

**混淆Variant布局和整数宽度。** 本地SDK采用pack(4)，32位tTJSVariant的数据联合体8字节、类型4字节。tjs_int32与tjs_int64构造/转换是不同入口；必须看完整导入字符串和push数量，不能依据被截短的反编译标签判断。向量构造/析构辅助函数还需要正确的stdcall与四个参数，否则后面的update参数也会被推错。

**x87浮点运算被丢弃。** 旧CRT的_ftol通过ST0接收浮点数，不是普通栈参数函数。把它识别成无参数调用，会丢掉前面的距离、正弦和缩放计算。本次为转换函数设置自定义变量存储：ST0作为10字节浮点输入、EAX作为实际使用的低32位整数结果、栈清理为0，恢复了计算表达式。余下的extraout_ST0/ST1仍须回看fld/fmul/fdiv/fstp，不能假定已经全部正确；需要64位返回的调用应另外处理EDX:EAX。

## 从算法到跨平台实现

- 查明随机数常量、每行消耗次数、尾部像素和Alpha分支。layerExFilter使用0x7d2b89dd，filter使用0x5d588b65；相同seed不等于相同图样。
- 拆分整数行为和浮点误差：保留定点移位、截断、插值权重和区域端点；Rust/Shader与x87三角函数不承诺逐位相同。
- 更新范围与实际写入范围都要记录。原DLL可能忽略top、留下尾部像素，或在绘制时清掉初始化参数；须有汇编/调用链证据才能把它记为原行为。
- 对原版越界访问、悬空指针、极小尺寸导致的失控循环，采用受管图像边界和明确失败，不复现内存错误。源目标同图采用快照时，也应说明它与CPU就地反馈顺序的区别。
- 小型状态、波形和几何可在CPU计算；整图像素处理优先走GPU。波形生成使用已有后台队列，图像、表和临时纹理使用现有预算；不通过抬预算掩盖额外副本。
- 完成一个插件的完整入口和业务后，再统一做格式、编译、Clippy与WGSL静态检查。静态检查通过只证明代码和着色器可接受，实际效果与PSV性能仍需分别验证。

## 粒子插件补充

- 注册表中的多个getter地址相同，可能是不同模式共用偏移或真正的别名。结合构造默认值和写入位置核对；不能按属性名字分配互不相关的状态。本次确认18组范围、27方法、53属性及4常量。
- 成对setter与单独属性setter不一定等价。原Angle/AngleOmega属性只改端点，不改缓存差值；这类差别须同时看getter、两个setter和随机取值函数。
- 先确认初始化回调发生在共同参数生成之前还是之后，以及最后一次图集随机选择。顺序改变会让全部后续粒子取值偏移；用同一个随机常量还不够。
- `assignParticle`的虚函数只复制基类数据，新建派生对象的运动字段留有未初始化内容。不能把反编译中的随机值当成可复刻契约；受管实现使用完整深拷贝，并在插件兼容清单明确差异。
- 读取PE静态全局值时区分节的RawSize和VirtualSize。BSS没有对应文件字节，不能让地址映射读到下一节并误认为初始值；本次随机种子最终从静态初始化链中的TVPGetTickCount调用确认。
